Label: wayfinder:map

## Destination

A working, personally-used MVP Linux application, named **Acheron**, providing offline keybinding and macro control for the Razer Tartarus Pro. A Rust Daemon captures evdev and injects via uinput, implementing Profiles, Layers (Mode-key), and per-Binding Trigger modes (Fire-once, Hold-to-repeat, Toggle) for both Keypress and Macro Actions. A Python+GTK4 GUI edits configuration and shows a tray icon, talking to the Daemon over D-Bus. See CONTEXT.md for vocabulary and docs/adr/ for the architecture rationale (0001-0004).

## Notes

**This map carries execution** — resolving a ticket means actually building and testing against the real, connected Tartarus Pro, not only deciding. Task-type tickets are real implementation/investigation work, not just discussion.

**Grounding facts** (see CONTEXT.md for vocabulary, docs/adr/ for architecture rationale):
- OpenRazer's driver for this device exposes lighting only — no macro/remap DBus surface (ADR-0002).
- The device enumerates as three evdev nodes: `main` emits the Mode key (`KEY_LEFTALT`) *and* the thumbstick (`KEY_UP`/`DOWN`/`LEFT`/`RIGHT`, 4-way, no center click); `if01` emits the 20-key grid (4×5) as standard keycodes; `if02` emits the scroll wheel (`REL_WHEEL`/`REL_WHEEL_HI_RES`) and its middle click (`BTN_MIDDLE`). Full Input → (node, code) table: [Enumerate physical inputs](./issues/01-enumerate-physical-inputs.md).
- System: Ubuntu, GNOME Shell 50.1, Wayland only (other DEs/display servers are out of scope). `ubuntu-appindicators` extension is active, so tray icons render without extra setup. User is in the `plugdev` group; reading the three device nodes worked without extra permission setup during investigation. `uinput` write access also works without extra setup — `/dev/uinput` carries an explicit ACL (`user:justin:rw-`) — confirmed end-to-end (evdev grab -> uinput inject -> real text field) in [Prove evdev/uinput pipeline](./issues/02-prove-evdev-uinput-pipeline.md).
- No Rust toolchain currently installed; Python 3.14 with GTK3/4 (PyGObject) is available. No PyQt/PySide, no Rust/Go/Node currently installed.
- Tartarus Pro USB ID: `1532:0244`.

**Skills to consult**: default to `/grilling` and `/domain-modeling` for decision tickets, per Wayfinder's ticket types. Use `/prototype` for "how should it look/behave" questions (GUI layout, tray menu design). Keep CONTEXT.md and docs/adr/ updated as the model sharpens further.

**Standing architectural discipline — keep the Daemon's capture layer swappable**: analog per-key depth sensing is real hardware on this device but is deliberately out of scope for the MVP (see Out of scope — `open-tartarus-driver` research). It rides a raw-HID stream evdev can't see, requiring a second capture path and a continuous-input concept the current `Binding`/`Trigger mode` model doesn't have room for (see [research/analog-pressure-sensitivity.md](./research/analog-pressure-sensitivity.md)). Nothing needs building for this now, but when designing the Daemon's internal input-capture layer, don't hard-wire config schema, the D-Bus surface, or Binding logic to assume "capture == evdev" — keep capture behind an internal abstraction so a second source (`hidraw` analog) could be added later without a rewrite. A light discipline to hold while building the MVP, not a reason to build anything analog-related now.

## Decisions so far

- [Analog/pressure-sensitivity research](./issues/05-research-analog-pressure-sensitivity.md) — Tartarus Pro grid keys have real analog-optical depth sensing, but it rides an undocumented raw-HID report outside the evdev nodes the daemon uses, so it's out of scope rather than a cheap extension.
- [Enumerate physical inputs](./issues/01-enumerate-physical-inputs.md) — full Input → (node, evdev code) table for all 20 grid keys, Mode key, thumbstick, and wheel captured live; corrects the earlier assumption that the thumbstick is on `if02` — it's actually on `main`, alongside the Mode key.
- [Prove evdev/uinput pipeline](./issues/02-prove-evdev-uinput-pipeline.md) — grab-and-inject mechanism confirmed end-to-end live; `uinput` write access works for this user with no extra setup (pre-existing ACL on `/dev/uinput`); no change to the Rust Daemon choice in docs/adr/0003.
- [Decide config file format](./issues/03-decide-config-file-format.md) — Daemon owns `~/.config/acheron/config.toml` exclusively (single TOML file, `schema_version = 1`); GUI edits only via D-Bus, never touches the file. Also settled the tool's name: **Acheron**.
- [Decide toggle behavior across switches](./issues/04-decide-toggle-behavior-across-switches.md) — active toggles survive Layer changes but are killed on Profile switch; the physical key that started a toggle always stops it first, regardless of what its current Layer binds it to.
- [Decide Daemon data model](./issues/06-decide-daemon-data-model.md) — composite `Input` enum, sparse `HashMap<Input, Binding>` per Layer (passthrough when absent), Mode key is independently bindable per-Profile (`LayerSwitch` vs `Bound`) through the same lookup, Keypress and Macro both compile to one `Vec<MacroStep>` executor, and active Toggles track live held keys for a clean force-release on stop.
- [Design Daemon capture/injection event loop](./issues/07-design-daemon-capture-event-loop.md) — single `tokio` runtime, actor-style dispatch task owns all state via one shared channel (evdev, D-Bus, and firing tasks all feed it — no locks); firing spawns a task per Action with `uinput` writes serialized through one injector task; capture lives behind a `CaptureSource` seam. *Corrected by [Decide systemd service packaging](./issues/10-decide-systemd-service-packaging.md): only genuine capture errors are fatal-exit-to-systemd; a device-absent condition (boot-before-plugin or mid-run unplug) is non-fatal and polled for instead.*
- [Decide D-Bus interface surface](./issues/08-decide-dbus-interface-surface.md) — one flat object (`/com/acheron/Daemon`, one combined interface), atomic per-entity mutating methods that apply immediately (no draft/save step), bulk `GetConfig()` + separate `GetState()`, three live-push signals (`ActiveProfileChanged`/`ActiveLayerChanged`/`ActiveTogglesChanged`, full-snapshot toggles), `Input` reuses its existing TOML string form on the wire, `Action`/`MacroStep` marshal as `a{sv}` dicts with a type tag (not JSON), and a small set of named `com.acheron.Daemon.Error.*` errors. *Corrected by [Decide systemd service packaging](./issues/10-decide-systemd-service-packaging.md): `GetState()` gains a `device_connected: b` field plus a `DeviceConnectionChanged(connected: b)` signal.*
- [Design GUI information architecture](./issues/09-design-gui-information-architecture.md) — one main view, **Device Overview**, that visually mirrors the physical Tartarus Pro (grid + wheel-as-5th-column + rotated thumbstick diamond + circular Mode key + separate key-20 paddle, per Device Picture.jpg/layout.md); **Action Table** demoted from a standalone page to a closed-by-default collapsible sidebar off it, reusing the same Profile/Layer selection rather than duplicating pickers; a third "focused wizard" variant was built, compared, and dropped. Live prototype: [prototype/09-gui-information-architecture/prototype.py](../../prototype/09-gui-information-architecture/prototype.py).
- [Decide systemd service packaging](./issues/10-decide-systemd-service-packaging.md) — `systemd --user` unit, login-enabled (`WantedBy=default.target`) as the primary autostart trigger, `Restart=on-failure` with a burst guard, installed via a small `install.sh`; the GUI also ensures the Daemon on its own launch via systemd's D-Bus API (`ResetFailed` + `StartUnit`, not a `systemctl` shell-out) as a safety net. Device-not-present (boot-before-plugin or mid-run unplug) is redefined as non-fatal — the Daemon polls for the device rather than exiting — correcting [Design Daemon capture/injection event loop](./issues/07-design-daemon-capture-event-loop.md); a `device_connected` bit and signal are added to the D-Bus surface, correcting [Decide D-Bus interface surface](./issues/08-decide-dbus-interface-surface.md).
- [Decide first-run experience](./issues/11-decide-first-run-experience.md) — on missing `config.toml`, the Daemon creates it immediately with one empty seed Profile (`Default`, both Layers present but unbound, `mode_key_role = layer_switch`); a corrupt/unparseable file makes the Daemon refuse to start rather than silently reseeding; the GUI has no separate onboarding — Device Overview against the all-passthrough seed Profile is the first-run experience.
- [Design Daemon/device status indicators](./issues/12-design-daemon-device-status-indicators.md) — both a header badge on Device Overview and a matching tray line reflect Daemon-running/Device-connected status (not one or the other); the device grid additionally disables itself under a dimmed overlay whenever status isn't running+connected, blocking edits rather than leaving Bindings clickable while disconnected. Live prototype: [prototype/12-daemon-device-status-indicators/prototype.py](../../prototype/12-daemon-device-status-indicators/prototype.py).
- [Daemon skeleton: capture → passthrough injection](./issues/13-daemon-skeleton-capture-passthrough.md) — first real Rust code (`daemon/`, crate `acheron-daemon`): one `tokio` runtime, `CaptureSource` trait with a real evdev impl (three `spawn_blocking` grabs, one per node) and a fake/scripted impl for tests, a single injector task owning the one `uinput` virtual device, and a pure-passthrough dispatch loop (no Binding logic yet). Verified live against the real, connected Tartarus Pro — output identical to no-Daemon behavior. The ~2s device-absent poll loop from ticket 10's correction is intentionally not built yet; deferred to whichever ticket owns Daemon/device status (issue 12/20 territory).
- [Config file + minimal domain model + Base-layer Fire-once Keypress remapping](./issues/14-config-and-base-layer-fireonce-remapping.md) — the first user-visible remap: `Config`/`Profile`/`Binding`/`Action`/`TriggerMode`/`Modifiers` types (`src/config.rs`), `Input`'s `Display`/`FromStr`/serde (issue 01's flat strings, doubling as the TOML table-key form), `config.toml` load-or-seed-immediately/refuse-on-corrupt lifecycle (issue 11), and dispatch resolving each event against the `Default` Profile's Base Layer — a bound Input fires its compiled Keypress on `Down` only, an unbound one still passes through. Deliberately narrow (Base Layer only, no `Layer` enum yet — that's ticket 18; `Action::Macro`/`HoldToRepeat`/`Toggle` exist as schema-only stubs, not wired to fire — that's ticket 17). Verified live against the real, connected Tartarus Pro: seeded `config.toml` on first run, hand-edited a grid-key remap, confirmed the remapped key (not the original) appeared in a real text field.
- [D-Bus surface v1 (live mutation, no restart)](./issues/15-dbus-surface-v1.md) — the Daemon now exposes live config mutation over D-Bus (`src/dbus/`): `GetConfig`/`GetState`/`SetBinding`/`ClearBinding` on the one flat `/com/acheron/Daemon` object, per issue 08's decided shape (`Input` as a plain string, `Action`/`Binding` as tagged `a{sv}` dicts, named `com.acheron.Daemon.Error.*` errors, the three runtime-state signals declared and proven deliverable though nothing calls them yet). `src/dispatch.rs` was restructured to consume a second channel (`Command`s, alongside capture's `PhysicalEvent`s) so the dispatch task stays the sole owner of the now-full `Config` (issue 07's "D-Bus interleaving"); mutations apply in-memory then persist via `spawn_blocking` (keeps a slow disk write from stalling queued keypresses), rolling back on a write failure so disk and memory never diverge. Verified live against the real, connected Tartarus Pro: `busctl --user call SetBinding` remapped a grid key with no Daemon restart, `config.toml` and `GetConfig()` reflected it immediately, and the user confirmed the physical key change.
- [GUI MVP wired to the real Daemon](./issues/16-gui-mvp-wired-to-real-daemon.md) — a new `gui/` Python package (`acheron_gui`) adapts ticket 09's prototype (Device Overview, Action Table sidebar, shared Binding editor) directly onto a real `com.acheron.Daemon` D-Bus connection (`Gio.DBusProxy`, hand-written `GLib.Variant` encoding mirroring `dbus/wire.rs`), behind a `DaemonClient` structural-typing seam also satisfied by a reshaped `DaemonStub` for tests. Since `SetBinding`/`ClearBinding` have no Profile/Layer parameter yet (they implicitly target the Daemon's active Profile's Base Layer), the Profile sidebar and Held-Layer tab are rendered but disabled rather than left looking interactive while silently mis-targeting edits — a decision for tickets 18/19 to unlock, not redesign. Verified live against the real, connected Tartarus Pro: the user clicked grid key `r1c1` in the running GTK4 app, set it to Keypress `KEY_9`, and physically pressing that key on the device produced `9` instead of the stock `1` — full click-to-hardware path confirmed with no Daemon restart.
- [Full Action/Trigger-mode support](./issues/17-full-action-trigger-mode-support.md) — a new shared `src/executor.rs` compiles both `Action::Keypress` and `Action::Macro` into one flat `Vec<MacroStep>` walked by one executor (a Keypress is just a canned modifier/key sequence now); `Injector` shrinks to a single `set_key_state(key, down)` primitive so both Keypress and Macro steps emit through it identically. `TriggerMode::HoldToRepeat` fires on `Down` and every evdev-native `Repeat`; `TriggerMode::Toggle` spawns its own loop task per `ActiveToggle::spawn`, which owns its held-key set locally (no Mutex — nothing else ever needs to read it) and force-releases everything still held when `stop()`'s `.await` returns, covering even an unbalanced Macro's stray `KeyDown`. `dispatch.rs`'s `handle_event` stops an `Input`'s active Toggle on the very next `Down` before even looking at its current Binding, so the physical key that started a Toggle always stops it regardless of what it's bound to now. `/code-review` caught same-`Input` firings being able to overlap and interleave raw writes (a slow Macro outlasting a fast Hold-to-repeat autorepeat) — fixed with an `in_flight: HashMap<Input, JoinHandle<()>>` guard that drops a new firing if the previous one for that `Input` hasn't finished; a second finding (re-`compile`-ing on every firing instead of caching) was accepted as a negligible, deliberately-not-optimized cost. GUI needed zero changes — ticket 16 already built the Trigger-mode dropdown and Macro step editor inert, and this ticket is exactly what makes them functional end-to-end. Verified live against the real, connected Tartarus Pro: a grid key bound to a Toggle Macro looped visibly until a second press stopped it cleanly with no stuck key, and a grid key bound to Hold-to-repeat refired only while physically held.
- [Held Layer + mode-key role](./issues/18-held-layer-and-mode-key.md) — `Profile` gains a `held: HashMap<Input, Binding>` sibling to `base` plus `mode_key_role: { LayerSwitch (default), Bound }`; dispatch owns a new momentary `active_layer: Layer` runtime field (not persisted `Config`), and under `LayerSwitch` intercepts every `Input::ModeKey` event before any Binding lookup — `Down`/`Up` flip Held/Base and emit `ActiveLayerChanged` over a `SignalEmitter` now threaded into `dispatch::run` from `main.rs`, `Repeat` is a no-op, and no keycode is ever passed through for it (the whole point of Hypershift-style layering). Under `Bound`, `Input::ModeKey` instead flows through the identical `(Layer, Input) -> Binding` lookup and Trigger-mode dispatch as any other Input. `SetBinding`/`ClearBinding` gained a `layer` D-Bus argument so the GUI can edit Base/Held independently; a new `SetModeKeyRole` method flips the role. GUI: `device_overview.py`'s Base/Held tab row is now clickable (selects which Layer Device Overview/Action Table edit) and auto-follows a live `ActiveLayerChanged` push via a new `daemon_client.subscribe_layer_changed`/`daemon_stub.simulate_mode_key_press`-`_release` seam; a mode-key-role toggle sits alongside it, and the Mode key's own device button is only clickable/bindable once `Bound` is selected. `/code-review` caught three issues, all fixed: an active Toggle on the Mode key becoming permanently unstoppable if `mode_key_role` flips from `Bound` back to `LayerSwitch` mid-Toggle (dispatch's `SetModeKeyRole` handler now stops it explicitly), the GUI's mode-key-role toggle not reverting its visual state on a failed `SetModeKeyRole` call (now mirrors the Binding editor's error handling), and a dead wire-encoding wrapper (`wire::layer_str`, removed in favor of the existing `Layer::as_str` it just forwarded to). 72 daemon tests + 28 GUI tests passing. Verified live against the real, connected Tartarus Pro: holding the Mode key flipped the GUI's Base/Held tab live (real `ActiveLayerChanged` signal) and fired the Held-layer remap instead of Base's for the same grid key, releasing reverted both; then, driven entirely from the GUI, flipping the "Mode key: Layer-shift"/"Bound" toggle un-greyed the Mode key's own device button, and binding it to a Keypress there made pressing it fire that Keypress instead of switching Layers, with no Layer-shift and no daemon/GUI errors.

- [systemd packaging + launch safety net](./issues/21-systemd-packaging-and-launch-safety-net.md) — `packaging/acheron-daemon.service` (the ticket 10-decided unit) plus a repo-root `install.sh` that builds/installs/enables it idempotently; the GUI's `_ensure_daemon_started_on_launch` calls systemd's own `ResetFailedUnit`+`StartUnit` over the session bus on every launch as the safety-net half, best-effort so a failure there can never block the GUI opening. Both live demos performed on the user's real machine (a full reboot for login-autostart; a deliberately-tripped `StartLimitBurst` + GUI relaunch for crash-recovery). The crash-recovery demo caught a real bug: ticket 10/spec.md's `Manager.ResetFailed(unit)` doesn't exist — that method takes no arguments — the correct per-unit call is `ResetFailedUnit(s)`, confirmed live via `busctl introspect` and fixed; `spec.md`/ticket 10/ticket 11 corrected to match. Automated coverage: `packaging/test_install.sh` (unit-file content + two-run idempotency, cargo/systemctl stubbed) and `gui/tests/test_app.py` cases.

## Out of scope

- Lighting/RGB and any OpenRazer integration for it — other tools (RazerGenie, Polychromatic) already cover this, and even Synapse itself delegates lighting to a companion app.
- Automatic, focused-application-based Profile switching.
- Support for desktop environments or display servers other than this system's GNOME/Wayland setup.
- Live macro recording (capturing real keypresses/timing) — MVP Macros are hand-specified only; recording could become a separate future effort after the MVP ships.
- Analog/pressure-sensitive Bindings for the grid keys — the Tartarus Pro's keys are genuine Razer Analog Optical switches with a real per-key depth signal, protocol reverse-engineered by a community driver (`open-tartarus-driver`, Windows-only — Linux `hidraw` compatibility is a reasonable inference, not a verified fact), but it requires an undocumented vendor mode-unlock command and a separate `hidraw` capture path outside the evdev+uinput design (ADR-0002), plus a new continuous-input Binding concept beyond discrete Trigger modes. See [research/analog-pressure-sensitivity.md](./research/analog-pressure-sensitivity.md).
