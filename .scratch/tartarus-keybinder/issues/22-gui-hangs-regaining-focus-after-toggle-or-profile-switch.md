# 22 — GUI hangs regaining focus after a Toggle/Profile-switch interaction

**What to build:** Diagnose and fix a GUI freeze discovered during ticket 19's live hardware demo, in the tray quick-switch path of the multiple-Profiles feature. The Daemon side is confirmed healthy throughout every repro; this is a GUI-process hang.

**Blocked by:** 19

**Status:** resolved — root-caused and diagnosed; deliberately no code change (see 2026-08-15 decision comment below)

## Repro

1. Real Daemon + real GUI running against the actual Tartarus Pro (not a `DaemonStub`-backed test).
2. Two Profiles exist (`Default`, `Gaming`), `Gaming` active. `Gaming`'s `grid_r1c2` is bound to a Toggle Macro (`KeyDown(KEY_A)`, `Delay(1000)`).
3. Focus a scratch text field (not the GUI window). Physically press grid key "2" once — the Toggle starts (`a`s repeat into the scratch field, confirmed via a separate `GetState()` call showing `active_toggles: ["grid_r1c2"]`).
4. Switch focus back to the GUI window (before touching the tray's "Quick switch" popover at all) — **the GUI window stops responding to input.**

This reproduced twice, on a freshly-restarted GUI process both times (including after the fix below was applied and both processes were rebuilt/restarted).

## What's already ruled out / fixed along the way

- **The Daemon is not stuck.** Independent `gdbus`/`GetState()` calls against the running Daemon succeeded throughout every hang, including while the GUI was frozen — the single dispatch task that would need to be stuck for a Daemon-side hang was clearly still servicing requests.
- **A real, separate bug was found and fixed in `SwitchProfile`**, though it does not appear to be what's reproducing here (the hang above reproduces before any `SwitchProfile` call is even made — the user hadn't yet opened the tray popover): `dispatch.rs`'s `SwitchProfile` handler used to emit `ActiveProfileChanged` *before* sending the method's own reply. Since `DBusDaemonClient`'s calls are synchronous (`Gio.DBusProxy.call_sync`), a client's own in-flight `SwitchProfile` call could see its own subscribed signal arrive — and run the signal callback — before that same call had returned: a reentrant blocking D-Bus call nested inside another one still unwinding, on the same connection. Fixed by sending the reply first, signal after (`dispatch.rs`, ticket 19's `SwitchProfile` arm). As defense in depth, `app.py`'s `on_layer_changed`/`on_profile_changed` signal callbacks were also changed to defer their `rebuild()` via `GLib.idle_add` rather than calling it inline from within the signal dispatch — this protects against the same class of hazard regardless of ordering on the Daemon side, and is now also the pattern the demo above was tested against (i.e., it still hung with both fixes in place).
- `gdb -p <pid>` is not usable in this sandboxed session (`ptrace_scope` blocks attaching, even as the owning user) — no Python-level stack trace of the hung GUI process was obtainable here. `py-spy` isn't installed either.
- `/proc/<pid>/task/*/wchan` for the hung GUI process showed the main thread in `poll_schedule_timeout` (i.e., idle-waiting in `poll()`/`epoll_wait`) both times — consistent with either a genuinely idle main loop *or* a nested `call_sync` wait-loop stuck waiting for a reply that will never come; `wchan` alone can't distinguish the two.
- No output/errors in either process's log (`stdout`/`stderr` redirected to file) at the time of the hang, both times.

## What to try next

- Get `py-spy dump --pid <pid>` (or run the GUI itself with `python3 -X faulthandler` and send it a signal `faulthandler` is registered against) to get a real Python + native stack of the hung process — the ptrace restriction blocking `gdb` in the session that found this bug may not apply in whatever session picks this up.
- Reproduce outside of a background-job session against a real interactive desktop, to rule out anything specific to this session's display/process-spawning setup (the GUI was launched via `nohup ... &` from a non-interactive shell, not a normal terminal/desktop launcher — worth ruling in/out).
- Given the repro doesn't require touching the tray popover at all, focus first on what a plain window-focus change does in this codebase — GTK4 focus-in/out signals, any `Gio.DBusProxy` re-subscription or `NameOwnerChanged` watching that might fire on window state changes elsewhere in `app.py`/`daemon_client.py` (none is wired yet as of ticket 19, but worth double-checking nothing GTK does implicitly).
- Consider whether an *already-running* Toggle (a background `tokio` task on the Daemon side looping every 1000ms) interacting with the GUI's own D-Bus proxy in some liveness-check/keepalive way could be relevant — this repro's distinguishing factor from every previously-working live demo (tickets 16–18) is specifically that a Toggle is actively running at the moment of the hang.

## Automated tests

None possible yet — this is a real-process/real-focus-event hang not reachable through the `DaemonStub`-backed GUI test seam or the Daemon's own fake-`CaptureSource` seam. Once root-caused, add regression coverage at whichever seam the fix actually lives at.

## Comments

**2026-08-15** — Live-repro session against the real Daemon + real GUI + real Tartarus Pro (this session had an actual interactive desktop and hardware, unlike whatever produced the note above about `gdb`/`py-spy` being unusable). Environment: GNOME Shell 50.1, GTK 4.22.4, Wayland (Mutter).

**New technique — sidesteps the `ptrace_scope` block noted above:** launch the GUI via a tiny wrapper that calls `faulthandler.enable()` + `faulthandler.register(signal.SIGUSR1)` before `acheron_gui.app.main()`, plus a `GLib.timeout_add`-driven heartbeat print every 500ms. `kill -USR1 <pid>` then dumps a real Python-level thread stack to stderr on demand — signals aren't subject to the yama ptrace restriction that blocked `gdb`/`py-spy` attach, so this works even where those don't.

**Finding 1 — this is not a Python/GLib main-loop deadlock.** During three separate live freezes, the GUI process stayed at <1.5% CPU, `wchan` genuinely idle in `poll()`, the heartbeat kept firing on schedule without interruption (proving `g_main_context_iteration` was still dispatching sources normally), and `SIGUSR1` dumps taken minutes apart both showed the single thread calmly inside `Gio.Application.run()` — the ordinary idle location, not stuck inside any Python code (in particular, not nested inside a `Gio.DBusProxy.call_sync`, which — per `GLib`'s implementation — pushes a *different*, private `GMainContext` as thread-default while waiting, so a real nested-`call_sync` hang would have stalled the heartbeat too; it never did). This rules out a second instance of ticket 19's `SwitchProfile` reentrancy class — that fix is not implicated here.

**Finding 2 — the freeze is a permanent, per-surface Wayland protocol wedge.** Capturing `WAYLAND_DEBUG=1` across three live freezes shows the exact same shape each time: normal traffic (pointer motion, `xdg_wm_base` ping/pong, frame commits, `xdg_toplevel.configure` activation toggles) runs right up to some moment, then **every** message in both directions — including compositor-*initiated* ones like `ping` — simply stops forever. The client's `wl_display` fd stays connected (no error, no disconnect); Mutter just stops addressing that one surface at all. Confirmed scoped to that one window/process: other application windows keep working throughout (user-confirmed), and killing + relaunching the frozen GUI process against the same live Daemon immediately produces a fully responsive fresh window — nothing is corrupted at the Daemon, session, or compositor level generally, only that one client's surface.

**Finding 3 — ruled out: `xdg_popup` grab race on `Gtk.MenuButton`, on its own.** The first live capture showed a suspicious double `xdg_popup.grab()` → immediate `popup_done()` (rejected) → retry with a stale/reused input serial → rejected again, right after a "Quick switch" click on a not-yet-focused window — a plausible-looking race between window activation and popover grab validity, independent of the Toggle. Implemented a fix (`Gtk.GestureClick` in the capture phase on every `Gtk.MenuButton`, claiming the press instead of letting it open the popover whenever `window.is_active()` was `False`) and live-tested it: **did not stop the freeze.** The fix was reverted (see repo history — not present in the working tree) since it doesn't address the real mechanism and would misrepresent this ticket as resolved.

**Correction (this same session) — the Toggle *is* required.** An earlier draft of this comment claimed the freeze "reproduced with no Toggle running at all." That was wrong — a tracking error, not a re-tested finding: `GetState()` was only checked at a couple of checkpoints, and the Toggle had in fact been re-started (real grid-key-2 press) before both of the later freezes that seemed to contradict the Toggle's involvement. Directly confirmed with the person driving the physical hardware: **every freeze actually observed happened with the Toggle actively running.** The one clean test with the Toggle confirmed *off* (`GetState()` showed `active_toggles: []` immediately beforehand) did not freeze. So Finding 3's popover-grab race is not sufficient on its own — the Toggle's continuous OS-level autorepeat stream (`wl_keyboard.key` arriving every ~30ms while the Daemon holds a key logically down, per `executor.rs`'s `run_toggle_loop`) is a necessary ingredient, restoring the plausibility of this session's original hypothesis (the Daemon's synthetic key-repeat output interacting with the GUI window at/around a focus transition).

**Finding 4 — the correlate, now better explained: `xdg_toplevel.configure` activation transitions while the autorepeat stream is live.** In every trace, the last thing the client ever sends/receives before going permanently silent is at or immediately after an activation-state `configure` (the `ACTIVATED` bit flipping). Combined with the correction above, the more precise characterization is: the freeze is a low-probability race between the compositor's activation-configure/ack/commit handshake for this surface and the continuous stream of synthetic key-repeat events the Toggle is generating at the same time — not a plain "any popover click" trigger, and not deterministic (plenty of activate/deactivate cycles elsewhere in the same sessions resolve fine even mid-Toggle).

**Where this leaves the ticket:** not yet root-caused to a specific line of GDK-Wayland/Mutter, but narrowed to a real, reproducible, three-part precondition: (1) a Toggle actively running (so the Daemon is continuously re-affirming a key as logically held, arming the OS's own key-repeat), (2) a keyboard-focus transition onto the Acheron window, (3) landing at an unlucky moment relative to that window's activation-configure handshake. No in-repo code change is confirmed to fix the underlying race — it lives below the level Acheron's Python/Rust code can reach — but unlike the ruled-out popover theory, this one has a concrete Acheron-side lever: the Daemon is what keeps re-affirming the held key and thus keeps the OS's autorepeat armed for the Toggle's whole duration. **Confirmed with a controlled A/B test (same session, same window, same click sequence — empty-area click to focus, ~2s wait, click a grid button):**
- Toggle off (`GetState()` checked immediately beforehand, `active_toggles: []`): no freeze.
- Toggle on (same sequence, nothing else changed): froze immediately.

So the Toggle's continuous autorepeat stream is a confirmed-necessary precondition, not just a correlation. Two directions from here, needing a product call rather than another blind code attempt:
- **(a) File upstream** against `gnome-shell`/`mutter` (GNOME Shell 50.1, GTK 4.22.4) with the evidence gathered here (the "heartbeat-alive-but-surface-dead" signature, the A/B result, a trimmed `WAYLAND_DEBUG` capture) and treat this ticket as blocked on that.
- **(b) Daemon-side mitigation**: stop relying on the OS's own key-repeat for a running Toggle's "keep sending the key" effect — have `run_toggle_loop` explicitly cycle (release, then re-press) rather than leave a key raw-held indefinitely, which denies the OS's autorepeat mechanism the sustained-down state it needs, so the precondition for the race is never created. This is a real behavior change for a Keypress bound to Toggle, though: CONTEXT.md documents that case as "held down" (e.g. holding a movement key continuously) — cycling it would turn that into a periodic flicker instead of a true continuous hold, unless the cycle rate is tuned finely enough not to matter for that use case. Needs a decision on whether that tradeoff is acceptable before implementing.

Practical workaround in the meantime, regardless of which direction: restarting the GUI process reliably recovers it (confirmed twice), with nothing corrupted at the Daemon/session/compositor level generally.

**Decision (2026-08-15):** leaving this unresolved rather than picking (a) or (b) yet. Before either, worth answering a prior question: is this Acheron-GUI-specific, or would *any* Python+GTK4+Wayland app that leaves a key logically held (arming OS autorepeat) hit the same freeze on a focus-regain? So far every live test in this session used the real Acheron GUI — this hasn't actually been isolated from Acheron's own code yet.

**Next step for a future session:** build a minimal test GUI to answer that, and use it to decide whether this is worth an Acheron-side mitigation at all versus purely an upstream report. Important methodological note: this session's *first* attempt (before the live repros above) was already a from-scratch minimal harness — two bare `Gtk.ApplicationWindow`s, an external `python-evdev` `UInput` device holding a key down, no Toggle/Daemon involved — and it did **not** reproduce the freeze (heartbeat + stack dumps stayed healthy through repeated focus swaps). So whatever ingredient actually matters was lost by building up from nothing. A more promising approach: start from the real `app.py`/`device_overview.py` as they exist and strip pieces out one at a time (the `subscribe_layer_changed`/`subscribe_profile_changed` signal wiring and its `idle_add` rebuild, the CSS provider, the `Gtk.MenuButton`/`Gtk.Popover` tree, the sidebar) rather than starting from a blank two-window script — narrowing down *from* a known-reproducing case is much more likely to preserve whatever the real trigger is than reconstructing it from assumptions about what "should" matter. Re-run the same controlled A/B (Toggle on vs. off, same click sequence) at each reduction step; the last version that still freezes is the minimal repro.

**2026-08-15 (follow-up session) — minimal repro found; bug is confirmed NOT Acheron-GUI-specific.** Live A/B reduction against the real Daemon + real Tartarus Pro, following the plan above exactly: start from real `app.py`, strip one piece at a time, re-test with the same physical grid-key-2 A/B sequence at each step, using the `faulthandler`/`SIGUSR1` + heartbeat + `WAYLAND_DEBUG=1` harness from the prior session (recreated fresh; nothing from the prior session's job persisted).

Reduction sequence, each still freezing:
- **v1** — real `app.py` minus `subscribe_layer_changed`/`subscribe_profile_changed` + `idle_add` rebuild. Froze (confirmed Toggle was still actively repeating at the moment of freeze, checked explicitly this time per the prior session's tracking-mistake warning). Stack dump: idling normally in `Gio.Application.run()`, heartbeat uninterrupted — same signature as Findings 1–2.
- **v2** — v1 minus the CSS provider. Froze on the 2nd of 2 attempts (non-deterministic, consistent with Finding 4's "not deterministic" note); user confirmed the Toggle was actively running at the moment of both attempts.
- **v3** — v2 minus the entire `Gtk.MenuButton`/`Gtk.Popover` tree (monkeypatched `Gtk.MenuButton` to a plain `Gtk.Button` with a no-op `set_popover` before importing `device_overview`, so every grid button/sidebar button/tray button is inert — same layout, zero popover machinery). Froze on 3/3 attempts.
- **v4 (final, minimal repro)** — a **bare `Gtk.ApplicationWindow` with a single plain `Gtk.Button`**. No `device_overview.py`, no sidebar, no D-Bus/`DaemonClient` at all — this variant makes zero calls into Acheron's own Python code beyond the debug wrapper. Only the real Daemon (driven by an actual physical grid-key-2 press, exactly as every other variant) supplies the synthetic key-repeat stream. **Froze**, with the identical signature (heartbeat alive, `SIGUSR1` stack idling in `Gio.Application.run()`, `WAYLAND_DEBUG` showing the same kind of protocol wedge).

**This settles the open question from the prior decision: the bug is not in Acheron's GUI code at all.** Any Python+GTK4 window on this machine (GNOME Shell 50.1, GTK 4.22.4, Wayland/Mutter) that has keyboard focus while the Daemon's Toggle is actively running will hit this freeze. It is a general Python+GTK4+Wayland issue on this machine/compositor version, triggered by the Daemon's continuous synthetic key-repeat stream — nothing about Acheron's widget tree, CSS, popovers, signal subscriptions, or sidebar is load-bearing.

**Two more preconditions from Finding 4 turned out to be wrong, discovered incidentally while running v3/v4:**
- **A focus transition is *not* required.** Every earlier repro happened to involve clicking away and back, which Finding 4 treated as part of the necessary precondition (the activation-configure handshake theory). Directly tested: click into the window first so it already has keyboard focus, *then* press grid key 2 to start the Toggle without ever changing focus — **froze anyway**, confirmed on v4 (the bare-window minimal repro) after first observing it on v3. So the precondition simplifies to just: (1) window has keyboard focus, (2) Daemon Toggle actively running. The activation-configure-handshake timing theory in Finding 4 is not the mechanism (or at least not a necessary one) — most likely a coincidence of every earlier test also including a focus change.
- **The freeze self-heals without restarting the GUI process.** Turning the Toggle off (second grid-key-2 press) made the same still-running window (same PID throughout, never killed/relaunched) clickable and responsive again immediately — confirmed live on v4. This refines Finding 2's "permanent, per-surface Wayland protocol wedge" framing: it's not permanent in the sense of requiring a process restart, only for as long as the Toggle's synthetic key-repeat stream keeps flowing. This also gives a much cheaper practical workaround than restarting the GUI: just stop the Toggle.

**Where this leaves the ticket now:** root-caused to a general Python+GTK4+Wayland (this compositor/version) freeze triggered by *any* focused window receiving the Daemon's continuous synthetic key-repeat stream for a held Toggle key, self-healing once that stream stops, independent of focus transitions and independent of anything in Acheron's own GUI code. The two directions from the prior decision still apply, but now with a much simpler, Acheron-independent minimal repro to hand off if going the upstream route:
- **(a) File upstream** against `gnome-shell`/`mutter` (GNOME Shell 50.1, GTK 4.22.4) — the bare-window minimal repro (v4) is a clean, self-contained upstream bug report on its own, needing no Acheron code at all beyond something that holds a key logically down via `UInput`/synthetic input at a similar cadence to `executor.rs`'s `run_toggle_loop`.
- **(b) Daemon-side mitigation** — same option as before: have `run_toggle_loop` cycle (release, then re-press) rather than leave a key raw-held, denying the OS/compositor the sustained-key-repeat-source state the race needs. The self-healing finding above makes this more clearly correct as a *complete* fix rather than just a probability-reducer: since the freeze requires the stream to keep flowing and clears the instant it stops, removing the sustained raw-hold removes the trigger outright, not just its likelihood. Still needs the same product decision on the "held key becomes a fast periodic re-press instead of a true continuous hold" tradeoff documented in the original comment before implementing.

**2026-08-15 (same follow-up session) — self-heal verified on the real, unmodified GUI, with one important caveat.** Re-tested directly against `acheron_gui.app` (not a stripped variant) to confirm the self-healing finding above wasn't an artifact of the reduced variants:

- Plain repro (no popover interaction at all before/during/after the freeze): confirmed self-heals live on the real app too — stop the Toggle, the same still-running window becomes clickable again, no restart needed.
- **Caveat found incidentally:** if a grid button's popover is opened (or attempted to be opened) *while the window is already frozen*, the window does **not** recover after the Toggle is stopped — it stays permanently wedged (same idling-heartbeat/`Gio.Application.run()` signature, so still not a Python-level deadlock, but no longer self-clearing) and needs a real process restart, matching the original workaround. By contrast, a popover opened and closed *before* the freeze sequence starts doesn't block recovery at all — confirmed with a clean isolated test (open popover, close it normally, then freeze, then stop Toggle: recovered fine). So the self-heal workaround is reliable **as long as no popover/dropdown is opened while the window is unresponsive** — this plausibly reconnects to Finding 3's original (independently insufficient) `xdg_popup` grab-race theory: attempting a popover grab against an already-wedged surface likely compounds into its own, separate, non-self-clearing wedge, on top of the base Toggle-driven one.

**Decision (2026-08-15, same session):** leaving this unresolved/parked rather than pursuing (a) or (b). Rationale (user call): the Daemon holding a Toggle key raw-down is correct, intended behavior — it's what a Toggle is supposed to do — and this freeze is a narrow edge case that only a user deliberately running an autorepeat-macro Toggle at all would hit, at which point unexpected interaction with other focused windows is already an accepted risk of that feature. Not worth the "held key becomes a periodic re-press" behavior change from (b), or the yet-unfiled upstream report from (a), for this narrow a case.

Practical guidance to carry forward given this decision: if the GUI freezes while a Toggle is running, stopping the Toggle alone recovers it **unless** a popover/dropdown was opened while it was already frozen, in which case a full GUI restart is required (same as before this session's findings). No further Acheron-side code changes planned; this comment records the fully-diagnosed state in case someone revisits (a)/(b) later.
