# 16 — GUI MVP wired to the real Daemon

**What to build:** A running GTK4 GUI that lets the user see and edit Base-layer Fire-once Keypress bindings against the real Daemon over D-Bus — the first end-to-end "click a key in the GUI, see it take effect on hardware" slice. Build from `prototype/09-gui-information-architecture/prototype.py` directly: it already implements Device Overview, the Action Table sidebar, and the shared Binding editor against an in-memory `DaemonStub` — this ticket's job is adapting that structure to a real D-Bus client backend, not redesigning the layout. See `.scratch/tartarus-keybinder/spec.md` ("GUI information architecture (GTK4)") for the full design; at this ticket's scope, only Keypress/Fire-once editing needs to actually work end-to-end (Macro/other-Trigger-mode UI can exist inert, matching ticket 15's D-Bus scope).

**Blocked by:** 15

**Status:** resolved

- [x] Device Overview (the main view) mirrors the physical device layout exactly as built in `prototype/09-gui-information-architecture/prototype.py` — grid, wheel-as-column-5-continuation, rotated thumbstick diamond, circular Mode key, key-20 paddle.
- [x] The GUI's D-Bus client layer replaces the prototype's `DaemonStub` with a real connection to `com.acheron.Daemon` (PyGObject's `Gio.DBusProxy`, or `dbus-fast`/`dbus-next` — not `dbus-python`), while preserving a swappable-fake-backend seam for tests (same shape as `DaemonStub`).
- [x] Clicking any device control opens the shared Binding editor in a popover; setting a Keypress binding calls `SetBinding` on the real Daemon and the popover reflects `GetConfig()`'s current state on open.
- [x] The Action Table sidebar (collapsible, closed by default, no independent Profile/Layer pickers, "Show all inputs" checkbox, sidebar-open state surviving re-renders) is wired to the same real backend and the same shared Binding editor.
- [x] On launch, the GUI opens straight to Device Overview reflecting `GetConfig()`/`GetState()` from the real Daemon — no separate onboarding wizard, even on a fresh seed `Default` Profile with everything passthrough.
- [x] Live demo: with the real Daemon running, click a grid key in the GUI, set it to a Keypress remap, and immediately (no restart) see the remapped output when physically pressing that key.
- [x] Automated GUI tests use a fake Daemon object implementing `com.acheron.Daemon`'s interface (the `DaemonStub` pattern from the prototype) to exercise Device Overview rendering, click-to-edit, and the Action Table's filter/show-all/open-state behavior without a real Daemon process.

## Comments

Implemented as a new top-level `gui/` Python package (`acheron_gui`), adapting `prototype/09-gui-information-architecture/prototype.py`'s Device Overview / Action Table / shared Binding editor structure directly, per the ticket's instruction not to redesign the layout.

- `acheron_gui/wire.py` — hand-written `GLib.Variant` encoders (`binding_to_variant`/`action_to_variant`/`macro_step_to_variant`) mirroring `daemon/src/dbus/wire.rs`'s conventions exactly (flat `Binding` dict, `"type"`-tagged `Action`/`MacroStep`, empty `modifiers` omitted). Decoding needs no hand-written counterpart — `GLib.Variant.unpack()` already recursively turns a `GetConfig()`/`GetState()` reply into plain Python dicts/lists/strings.
- `acheron_gui/daemon_client.py` — `DaemonClient` (a `typing.Protocol`, the structural "swappable fake backend" seam the ticket asks for) and the real `DBusDaemonClient`: a synchronous `Gio.DBusProxy` against `com.acheron.Daemon` (spec.md's explicit choice over `dbus-python`/`dbus-fast`/`dbus-next`), with `com.acheron.Daemon.Error.*` translated into typed `NotFoundError`/`AlreadyExistsError`/`InvalidBindingError`/`DaemonIoError` exceptions via `Gio.DBusError.get_remote_error`.
- `acheron_gui/daemon_stub.py` — the ticket 09/12 `DaemonStub` pattern reshaped to the real `DaemonClient` interface (`get_config`/`get_state`/`set_binding`/`clear_binding`, flat Binding dicts) rather than the prototype's old nested shape; deep-copies on both read and write so it matches `DBusDaemonClient`'s object-independence semantics (`GLib.Variant.unpack()` always returns fresh objects) — caught in `/code-review`.
- `acheron_gui/inputs.py`, `binding_editor.py`, `device_overview.py`, `action_table.py` — the prototype's widget-building functions, split into a few modules and adapted to the real *flat* Binding shape (`{"trigger": ..., "type": ..., ...}`, matching what `GetConfig()` actually returns) instead of the prototype's nested `{"trigger": ..., "action": {...}}`. Trigger-mode/Macro editing UI is kept fully working (the wire format already round-trips it per ticket 15) even though only Keypress/Fire-once fires in the Daemon yet, per the ticket's "can exist inert" allowance.
- **Scope decision**: the real D-Bus surface has no `SwitchProfile` and no Layer parameter on `SetBinding`/`ClearBinding` (tickets 19/18) — both always act on the Daemon's current active Profile's Base Layer implicitly. Rather than let the Profile sidebar or the Held-Layer tab look interactive while silently mis-targeting edits, both are rendered (matching the prototype's structure) but disabled with a tooltip pointing at the relevant later ticket.
- `acheron_gui/gtk_utils.py` — `clear_children()`, factored out of four near-identical "remove every child" loops during `/code-review`.
- `acheron_gui/app.py` / `gui/main.py` — the runnable `Gtk.Application`; `ui_state` (GUI-only view state surviving a full rebuild, ticket 09's pattern) now also tracks the Action Table's per-row expanded state (`expanded_rows`), not just `table_open` — `/code-review` caught that a Save-triggered rebuild was re-collapsing any row the user had open.
- Tests (`gui/tests/`, run via a `gui/.venv` with `--system-site-packages` so PyGObject/GTK4 stay the system install): 19 tests against real Gtk4 widgets (per spec.md's testing decision — real widgets, `DaemonStub`, no mocks), covering wire round-trips, `DaemonStub` behavior, click-to-edit save/clear (including the already-passthrough no-op-clear case), Action Table show-all filtering, and both `table_open`/`expanded_rows` surviving a rebuild.
- Live-hardware demo done 2026-08-15: built and ran the real `acheron-daemon` release binary (Tartarus Pro connected), drove the real `DBusDaemonClient` directly (`SetBinding`/`ClearBinding`/`NotFoundError` all round-tripped through `config.toml` correctly), then launched the actual GTK4 app (`gui/main.py`) against the running Daemon. With both running, the user clicked grid key `r1c1` in the GUI, set it to Keypress `KEY_9` via the popover editor and Saved, then physically pressed the corresponding key on the real Tartarus Pro — `9` appeared instead of the stock `1`, confirming the full click-to-hardware path with no Daemon restart. Binding cleared via `ClearBinding` and both processes stopped afterward; `config.toml` back to the clean seed.
- `/code-review` (medium, re-run once properly scoped to the staged `gui/` diff — the first pass accidentally reviewed already-committed Rust files since the new files were still untracked) caught three real issues, all fixed: the `DaemonStub` shallow-copy divergence from `DBusDaemonClient`'s decoupled-object semantics, the duplicated child-clearing loop (now `gtk_utils.clear_children`), and the Action Table's expanded-row state not surviving a rebuild.
