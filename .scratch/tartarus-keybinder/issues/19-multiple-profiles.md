# 19 — Multiple Profiles

**What to build:** Named, manually-switched Profiles — each a complete, independent Base+Held Binding set — with switching that cleanly kills any in-progress Toggle. See `.scratch/tartarus-keybinder/spec.md` ("Toggle behavior across Layer/Profile switches", D-Bus method list) for the full design.

**Blocked by:** 18

**Status:** resolved

- [x] `CreateProfile`, `DeleteProfile`, `RenameProfile`, and `SwitchProfile` D-Bus methods exist, each atomic/immediately-applied/immediately-persisted to `config.toml`, per the conventions already established by `SetBinding`/`ClearBinding` (ticket 15) and `SetModeKeyRole` (ticket 18).
- [x] Profiles are keyed by name (`HashMap<String, Profile>`); each independently carries its own Base/Held Binding maps and `mode_key_role`.
- [x] `SwitchProfile` force-stops every currently-active Toggle immediately as part of the switch — force-releasing each one's tracked held keys via the injector, using the mechanism from ticket 17 — before the new Profile's state becomes active.
- [x] `ActiveProfileChanged(name: s)` fires correctly on every switch.
- [x] The GUI's left-hand Profile sidebar (from the prototype) is wired to real `CreateProfile`/`DeleteProfile`/`RenameProfile`/`SwitchProfile` and `ActiveProfileChanged`.
- [x] The tray mock's "Quick switch" popover lists real Profiles and calls `SwitchProfile`.
- [x] Live demo — **partially verified, with a known issue handed off to ticket 22**: creating a second Profile, binding a different set of keys in it, and switching via the GUI sidebar were all verified live against the real Tartarus Pro, including confirming a Toggle left running in the first Profile is force-stopped (no stuck key, no continued looping) the instant the switch lands. The tray-quick-switch half of this demo hit a GUI hang unrelated to whether the Daemon-side behavior is correct (the Daemon stayed fully responsive throughout) — see ticket 22, filed to track that separately rather than block this ticket's otherwise-complete and tested implementation.
- [x] Automated tests cover: independent Binding sets per Profile, `SwitchProfile` killing all active Toggles with exact-key release, and Profile CRUD persisting correctly to `config.toml`.

## Comments

Implemented by agent: `daemon/src/command.rs` (`CreateProfile`/`DeleteProfile`/`RenameProfile`/`SwitchProfile` `Command` variants, `CommandError::AlreadyExists`/`InvalidRequest`), `daemon/src/dispatch.rs` (their handlers — atomic mutate/persist/rollback matching `SetBinding`'s existing pattern, `SwitchProfile` draining and force-stopping every `ActiveToggle`, active/last-Profile deletion guard, empty-name validation on `CreateProfile`/`RenameProfile`), `daemon/src/dbus/mod.rs` (the four D-Bus methods + `DaemonError` mapping). GUI: `device_overview.py` (real Profile sidebar with Create/Rename/Delete/Switch, tray mock's Quick-switch wired to `SwitchProfile`, inline error surfacing matching `build_binding_editor`'s existing convention), `daemon_client.py`/`daemon_stub.py` (the four methods + `subscribe_profile_changed`), `app.py` (subscribes to `ActiveProfileChanged`, rebuilds). 95 daemon tests + 50 GUI tests passing, `cargo clippy` clean. `/code-review` run once and both findings fixed: silently-swallowed Switch/Delete/tray-pick errors (now shown inline, matching the existing `show_error` convention) and missing server-side empty-name validation on `CreateProfile`/`RenameProfile` (previously only the GUI's own popover blocked it).

Live demo against the real, connected Tartarus Pro: created a `Gaming` Profile via the GUI's "+ New Profile", bound `grid_r1c1` differently per-Profile (`KEY_B` fire-once in Gaming, left passthrough in Default) confirming independent Binding sets, bound `grid_r1c2` in Gaming to a Toggle Macro (`KeyDown(KEY_A)` + `Delay(1000)`), started it with a real physical key press (confirmed via `GetState()`), and switched back to Default via the GUI sidebar — the Toggle stopped immediately (`active_toggles` empty, no stuck key), fully exercising the ticket's core "Toggle force-stopped on Profile switch" requirement against real hardware.

Attempting the same test via the tray mock's "Quick switch" popover surfaced a real, reproducible GUI hang (window stops responding after a physical Toggle-starting key press, even before touching the tray popover). Investigating it found and fixed a genuine related bug — `SwitchProfile` used to emit `ActiveProfileChanged` before sending its own method reply, a reentrant-blocking-call hazard for any synchronous D-Bus client — and added `GLib.idle_add` deferral in the GUI's signal callbacks as defense in depth. Neither fix resolved the specific hang reproduced above, which reproduces without ever calling `SwitchProfile` at all; `gdb` couldn't attach in this session (`ptrace_scope`) to get a stack trace. Rather than block this otherwise-complete, fully-tested ticket on an apparently-unrelated GUI freeze, filed ticket 22 to track and root-cause it separately.
