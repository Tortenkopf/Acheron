# 15 — D-Bus surface v1 (live mutation, no restart)

**What to build:** The Daemon exposes its Base-layer Fire-once Keypress bindings over D-Bus, so a client can read and mutate config live without restarting the Daemon or hand-editing TOML. See `.scratch/tartarus-keybinder/spec.md` ("D-Bus surface (ADR-0004)") for the full design — this ticket implements the subset needed for ticket 14's scope (Base layer, Keypress, Fire-once); the remaining methods/fields (Macro, other Trigger modes, Layers, Profiles, `device_connected`) are added by later tickets reusing the same object/interface/encoding conventions rather than redesigning them.

**Blocked by:** 14

**Status:** resolved

- [x] One flat D-Bus object `/com/acheron/Daemon` on bus name `com.acheron.Daemon`, one combined interface (also `com.acheron.Daemon`) — no ObjectManager hierarchy.
- [x] `GetConfig() -> a{sv}` returns the entire config document (the `Default` Profile's Base-layer bindings, at this ticket's scope).
- [x] `GetState() -> (profile: s, layer: s, active_toggles: as, device_connected: b)` returns the live runtime snapshot — `layer` and `active_toggles` can be fixed/stub values at this ticket's scope (`"base"`, empty list) since Layers/Toggles don't exist yet; `device_connected` can be hardcoded `true` (real detection is ticket 20's scope).
- [x] `SetBinding` and `ClearBinding` are atomic, per-entity methods: each call validates, applies in-memory, and rewrites `config.toml` immediately — no draft/save step, no buffered state.
- [x] `Input` marshals as a plain string reusing its `Display`/`FromStr` form (ticket 14). `Action`/`MacroStep`/`Binding` marshal as `a{sv}` dicts with a `"type"` tag key (hand-written `Serialize`/`Deserialize`, not a JSON-string fallback) — build this encoding to already accommodate the `Macro`/other-Trigger-mode shapes described in spec.md even though only `Keypress`/`FireOnce` are exercised yet.
- [x] A small set of named errors under `com.acheron.Daemon.Error.*` exists: `NotFound`, `AlreadyExists`, `InvalidBinding`, `IoError`.
- [x] `ActiveProfileChanged`, `ActiveLayerChanged`, and `ActiveTogglesChanged` signals are wired (even though nothing yet changes Profile/Layer/Toggles at this ticket's scope — they should fire correctly once later tickets add the triggering behavior).
- [x] Live demo: a small script/CLI (e.g. `dbus-send` or a throwaway Python snippet) calls `SetBinding` for a grid key, the Daemon's live remap changes with no restart, and `config.toml` on disk reflects the change; `GetConfig()` reflects it too.
- [x] Automated tests exercise the D-Bus methods directly (real `zbus` server, in-process) combined with ticket 13's fake `CaptureSource` to assert the full path: D-Bus mutation → dispatch state → injected output.

## Comments

Implemented on top of ticket 14's config/dispatch code, entirely within `daemon/`.

- `src/command.rs` (new) — `Command` (`GetConfig`/`GetState`/`SetBinding`/`ClearBinding`, each carrying a `oneshot` reply channel) and `State` (the `GetState()` snapshot), the message shape D-Bus method calls push into the dispatch task's channel. `CommandError` is deliberately narrower than the D-Bus surface's error set (`NotFound`/`IoError` only) — `AlreadyExists`/`InvalidBinding` never originate in the dispatch task at this ticket's scope.
- `src/dispatch.rs` — restructured per spec.md's "D-Bus interleaving": `run()` now takes a second channel (`Command`s) alongside the capture channel, and owns the full `Config` (not just a bindings map) so it stays the sole state-owning consumer. A `tokio::select!` loop serves both; the command channel closing (D-Bus side gone) isn't fatal, only the event channel closing is (issue 07). `SetBinding`/`ClearBinding` mutate in-memory first, then persist via `config::write` — on a write failure the in-memory edit is rolled back so `config.toml` on disk and `GetConfig()` never diverge. `persist()` runs the actual `std::fs::write` via `spawn_blocking` (caught by `/code-review`: an inline blocking write would have stalled every queued `PhysicalEvent` behind it).
- `src/dbus/mod.rs` (new) — the `Daemon` D-Bus-facing type: holds only a `Command` sender, forwards every method call and awaits the dispatch task's reply, so it never touches `Config` directly. `DaemonError` (`#[derive(zbus::DBusError)]`, prefix `com.acheron.Daemon.Error`) covers `NotFound`/`AlreadyExists`/`InvalidBinding`/`IoError`; `AlreadyExists` isn't reachable yet (no `CreateProfile` until a later ticket) but the variant exists per the ticket's named-error-set decision. The three signals (`ActiveProfileChanged`/`ActiveLayerChanged`/`ActiveTogglesChanged`) are declared and proven deliverable end-to-end in a test, but nothing calls them yet — no later ticket has to redesign the signal surface, just add call sites.
- `src/dbus/wire.rs` (new) — the hand-written `a{sv}` encoding: `Action`/`MacroStep` tagged dicts, `Binding` bundling `trigger` flat alongside the `Action` fields (not nested), `Modifiers` as a list of held-modifier names. Full round-trip support for `Action::Macro` and all three `TriggerMode`s exists and is unit-tested even though only `Keypress`/`FireOnce` fire in dispatch yet, per the ticket's forward-compatibility requirement.
- `src/main.rs` — builds the `com.acheron.Daemon` session-bus connection (`zbus::connection::Builder`) alongside the existing capture/dispatch/injector pipeline; the `Connection` is held in `_connection` for the process's lifetime.
- `Cargo.toml` — added `zbus` (default features off, `tokio` + `p2p`; `p2p` only needed for the in-process test harness's peer-to-peer connection). Dev-only `futures-util` for the signal-subscription test.
- Tests: 20 new tests (45 total via `cargo test`) — `dbus::wire::tests` unit-tests the encoding round-trips; `dispatch::tests` covers `Command` handling (persistence, rollback-on-error, `NotFound`) directly against the dispatch task; `dbus::tests` spins up a real in-process `zbus` peer-to-peer connection (`tokio::net::UnixStream::pair`, no session bus needed) serving a real `Daemon` backed by a real dispatch task and ticket 13's fake `CaptureSource`, exercising the full path D-Bus mutation → dispatch state → injected output, plus the `NotFound`/`InvalidBinding` error paths and a real signal delivery. `cargo clippy --all-targets -- -D warnings` and `cargo fmt --check` both clean.
- Live-hardware demo done 2026-08-14: ran the release binary against the real, connected Tartarus Pro. `busctl --user introspect` matched the spec'd method/signal signatures exactly. `SetBinding` on `grid_r1c1` (via `busctl --user call`) changed the live remap with no restart — the user confirmed the physical top-left grid key (stock output `1`) now types `9` — and both `config.toml` on disk and a follow-up `GetConfig()` call reflected the change immediately. `ClearBinding` restored passthrough and correctly errored `NotFound` on a second call against the same (now-unbound) Input. Config was reset back to the clean empty seed afterward.
- `/code-review` (medium) caught two real issues, both fixed: (1) `config::write` ran synchronously inline on the dispatch task for every `SetBinding`/`ClearBinding`, which would stall queued `PhysicalEvent`s behind a slow disk write — moved behind `tokio::task::spawn_blocking`; (2) the `active_profile_mut().expect(...)` pattern was duplicated four times across apply/rollback paths — extracted into one `active_profile_mut()` helper.
