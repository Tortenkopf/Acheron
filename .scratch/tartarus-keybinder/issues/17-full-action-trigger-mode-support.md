# 17 — Full Action/Trigger-mode support

**What to build:** Macro actions and the Hold-to-repeat/Toggle trigger modes, end to end — the Daemon can run a looping or held-down Action and cleanly stop it, and the GUI can author one. See `.scratch/tartarus-keybinder/spec.md` ("Domain model (Daemon, Rust)", "Daemon event loop and concurrency", "Toggle behavior across Layer/Profile switches") for the full design.

**Blocked by:** 16

**Status:** resolved

- [x] `Action::Macro { steps: Vec<MacroStepDTO> }` exists, `MacroStepDTO` = `{ KeyDown(Key), KeyUp(Key), Delay(ms) }`.
- [x] Both `Action` kinds compile at config-load time into one `steps: Vec<MacroStep>` on the runtime `Binding`, run by one shared executor (a Keypress becomes a canned modifier-down/key-down/key-up/modifier-up sequence).
- [x] `TriggerMode::HoldToRepeat` fires on `Down` and every subsequent `Repeat` (driven by the device's native evdev autorepeat, no separate repeat-interval config).
- [x] `TriggerMode::Toggle` starts on `Down`, loops the compiled step sequence indefinitely (`tokio::time::sleep` between `Delay` steps) in its own spawned task, and ignores `Repeat`/`Up` entirely.
- [x] Firing any Action spawns its own task; all `uinput` writes still funnel through the one injector task from ticket 13 (write-commands over a channel), so concurrently-running Toggles never interleave raw writes.
- [x] Active Toggles are tracked in a `HashMap<Input, ActiveToggle>`, each holding a live `HashSet<Key>` of currently-down keys (updated as the executor processes `KeyDown`/`KeyUp`) plus a `CancellationToken`.
- [x] Pressing the physical key that has an active Toggle stops that Toggle first — force-releasing exactly its tracked held keys via the injector — regardless of what Binding the key's current Layer/context nominally assigns; only then does the key resume normal evaluation.
- [x] `SetBinding`'s existing `a{sv}` encoding (from ticket 15) is exercised for real now with `Macro`/`HoldToRepeat`/`Toggle` payloads — no wire-format changes needed.
- [x] The GUI's shared Binding editor gains a Trigger-mode dropdown (Fire-once/Hold-to-repeat/Toggle) and a Macro step add/remove list (Keypress steps + per-step delay), per the prototype's editor component.
- [x] Live demo: bind a grid key to a Toggle Macro with visible delays between steps, watch it loop continuously after one press, press the same key again and see it stop cleanly (no stuck keys); bind another key to Hold-to-repeat and confirm continuous refire only while physically held.
- [x] Automated tests (fake `CaptureSource` + real dispatch/executor) cover: Toggle start/loop/stop-releases-exact-keys, Hold-to-repeat firing on Repeat events, and that an unbalanced Macro (e.g. odd KeyDown without matching KeyUp) still gets force-released cleanly on stop.

## Comments

- `daemon/src/executor.rs` (new) — the one shared executor spec.md calls for. `compile(&Action) -> Vec<MacroStep>` turns a Keypress into a canned modifier-down/key-down/key-up/modifier-up sequence (the `modifier_codes`/`keypress_steps` logic moved here from `injector.rs`, since a compiled Keypress now runs through the exact same step-walker as a Macro) and maps a Macro's `MacroStepDto`s straight across, `Delay(ms)` becoming a `Duration` once at compile time. `run_once` walks a step sequence once (`spawn_fire_once` for Fire-once/Hold-to-repeat); `ActiveToggle::spawn` runs the same walk in an unbounded loop until cancelled.
- **Design choice — no Mutex, ever**: an `ActiveToggle`'s loop task owns its live `HashSet<KeyCode>` of currently-held keys entirely locally, rather than mirroring it into a shared/locked structure. Nothing outside that one task ever needs to read the held-set mid-flight; `ActiveToggle::stop()` cancels the loop and `.await`s its `JoinHandle`, so by the time `stop()` returns the force-release (`force_release`, sending `KeyUp` for every still-held key — this is what makes an unbalanced Macro's stray `KeyDown` safe) has unconditionally already run. This satisfies the ticket's `HashMap<Input, ActiveToggle>` + held-set + `CancellationToken` shape without introducing the lock spec.md's architecture otherwise avoids everywhere else.
- `daemon/src/injector.rs` — `InjectorMessage::Keypress{modifiers,key}` (a canned batch) replaced with `InjectorMessage::KeyState{key,down}` (one transition, one `SYN_REPORT` frame), since the executor now walks steps itself and only needs the injector to do raw down/up transitions — matches how a Macro's individual `KeyDown`/`KeyUp` steps need to be emitted anyway.
- `daemon/src/dispatch.rs` — `fire()` branches on `(TriggerMode, EventState)`: Fire-once only on `Down`; Hold-to-repeat on `Down` and every `Repeat` (the device's own evdev autorepeat — no separate interval config, per the ticket); Toggle starts a loop on `Down` and otherwise ignores `Repeat`/`Up` entirely. Stopping is handled a level up in `handle_event`, *before* any Binding lookup: a `Down` on an `Input` with an entry in `toggles` always stops it first and consumes that press outright, regardless of what the Input's current Binding nominally says — this is what makes "same physical key stops its own Toggle" hold even if the Binding changed underneath it mid-Toggle.
- **Code review (medium)** on the initial `dispatch.rs`/`executor.rs` diff found two issues, both addressed:
  - *Same-Input firings could overlap and interleave raw writes*: `fire()`'s Fire-once/Hold-to-repeat branch spawned a fire-and-forget task on every `Down`/`Repeat` with nothing stopping two firings for the same `Input` from running concurrently — a slow Macro outlasting a fast `HoldToRepeat` autorepeat could let two firings' `KeyDown`/`KeyUp` steps land on the shared `Injector` channel out of order. Fixed by adding `in_flight: HashMap<Input, JoinHandle<()>>` to the dispatch task's state: before spawning a new firing for an `Input`, `fire()` checks whether a previous firing's `JoinHandle` is still unfinished and, if so, drops the new firing instead of spawning a second one. Covered by the new `dispatch::tests::overlapping_same_input_firings_are_dropped_not_queued` test (a Hold-to-repeat Macro with a `Delay`, a `Repeat` sent mid-Delay is dropped, a `Repeat` sent after the first firing completes starts a genuine second firing). This also required rewriting `hold_to_repeat_fires_on_down_and_every_repeat_but_not_up` to send its scripted `Down`/`Repeat`/`Repeat`/`Up` sequence with `yield_now()` gaps instead of back-to-back with none, matching how real evdev autorepeat events (tens of milliseconds apart) never actually land faster than a same-Input firing can finish.
  - *`executor::compile` re-runs on every single firing* instead of being cached once per Binding: **accepted as-is, not fixed**. `compile` is a small, allocation-only, side-effect-free walk over a Binding's `Action` (a few steps in the common case) — its cost is negligible next to the `uinput` writes and `tokio::time::sleep`s the firing itself performs, and caching it would mean either re-deriving the compiled form on every `SetBinding`/`ClearBinding` (a second synced copy of `Config` to keep consistent, which spec.md's "no Mutex, mutation serialized by construction" architecture deliberately avoids elsewhere) or compiling lazily into some cache keyed by `Input`/Binding identity, complexity this MVP ticket doesn't need. Revisit only if profiling ever shows `compile` as a measurable cost.
- `daemon/src/dbus/mod.rs` — `GetState`'s `active_toggles` is real now (`toggles.keys().copied().collect()`), covered by a new `set_binding_over_real_dbus_with_a_macro_toggle_payload_starts_and_stops_it` test exercising `SetBinding` with a real Macro+Toggle payload over a real D-Bus socket, then a start-press and a stop-press, asserting exactly one Macro lap plus a force-release. The `ActiveTogglesChanged` D-Bus signal itself stays unwired (deliberate scope decision, same as `active_profile_changed`'s already-existing gap) — nothing in this ticket's checklist calls for GUI-side live Toggle-state push.
- **Scope exclusions, deliberate**: no Profile-switch-clears-toggles behavior, since `SwitchProfile` doesn't exist yet (ticket 19); no Held Layer interaction (ticket 18) — a Toggle's stop-on-same-key-Down logic works purely off `Input` identity, independent of Layer.
- GUI: **zero code changes needed**. `gui/acheron_gui/inputs.py`'s `TRIGGER_OPTIONS` (Fire-once/Hold-to-repeat/Toggle) and `ACTION_TYPES` (Keypress/Macro) dropdowns, and the Macro step add/remove editor, were already built out in ticket 16 ("Trigger-mode/Macro editing UI kept fully working... even though only Keypress/Fire-once fires in the Daemon yet") — this ticket's Daemon-side work is exactly what makes that already-existing UI functional end-to-end.
- Verification: `cargo test` (54 tests, all daemon unit/integration tests including the D-Bus-socket ones), `cargo clippy --all-targets -- -D warnings`, `cargo fmt --check` all clean.
- Live-hardware demo done 2026-08-15: built the real `acheron-daemon` release binary, hand-wrote `config.toml` with grid key `r1c1` bound to a Toggle Macro (`KeyDown A`, 700ms delay, `KeyUp A`, 700ms delay) and grid key `r1c2` bound to Hold-to-repeat Keypress `KEY_B`, ran it against the real, connected Tartarus Pro. User confirmed: pressing `r1c1` once started a visibly looping `A` in a text editor that kept going until a second press stopped it cleanly with no stuck/repeating key; holding `r1c2` repeated `B` only while held and stopped immediately on release. `config.toml` restored to the clean empty seed afterward.
