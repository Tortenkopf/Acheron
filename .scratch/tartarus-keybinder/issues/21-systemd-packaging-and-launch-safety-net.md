# 21 — systemd packaging + launch safety net

**What to build:** The Daemon runs continuously without the user having to launch it by hand — it starts at login via `systemd --user`, and the GUI double-checks it's up (and clears any stuck failure) every time the GUI itself launches. See `.scratch/tartarus-keybinder/spec.md` ("Packaging and lifecycle") for the full design.

**Blocked by:** 20

**Status:** resolved

- [x] A `systemd --user` unit at `~/.config/systemd/user/acheron-daemon.service`: `Type=simple`, `ExecStart=%h/.local/bin/acheron-daemon`, `After=graphical-session.target`, `WantedBy=default.target`, `Restart=on-failure`, `RestartSec=1`, `StartLimitIntervalSec=60`, `StartLimitBurst=5`. Stdout/stderr go to the default journal.
- [x] A small idempotent `install.sh`: builds the release binary, copies it to `~/.local/bin/acheron-daemon`, copies the unit file into place, runs `systemctl --user daemon-reload`, then `systemctl --user enable --now acheron-daemon`. Safe to re-run on every rebuild.
- [x] On its own launch, the GUI calls `org.freedesktop.systemd1.Manager.ResetFailedUnit("acheron-daemon.service")` then `StartUnit("acheron-daemon.service", "replace")` over the same session D-Bus connection it already holds — no `systemctl` shell-out, no subprocess. `StartUnit` is a no-op if the Daemon is already running.
- [x] Live demo: run `install.sh`, log out and back in, and confirm (`systemctl --user status acheron-daemon` or the GUI's status chip from ticket 20) the Daemon is already running with no manual start. Separately, `kill -9` the Daemon process to force it into `systemd`'s `failed` state, then launch the GUI, and confirm the Daemon comes back automatically (visible via ticket 20's status chip flipping from not-running to running) with no terminal interaction. **Both performed live — see Comments.**
- [x] Automated coverage is limited to what doesn't require a real systemd user session (e.g. `install.sh`'s idempotency, unit-file content) — the login-autostart and crash-recovery demos above are manual/live-hardware verification, not unit tests.

## Comments

**Packaging:**
- `packaging/acheron-daemon.service`: the exact unit from the ticket/spec — `StartLimitIntervalSec`/`StartLimitBurst` placed in `[Unit]` (systemd's canonical location for unit-level start-rate-limiting, not `[Service]`), `Restart=on-failure`/`RestartSec=1`/`Type=simple`/`ExecStart=%h/.local/bin/acheron-daemon` in `[Service]`, `WantedBy=default.target` in `[Install]`.
- `install.sh` (repo root): builds `daemon/` in release mode, copies the binary to `~/.local/bin/acheron-daemon` and the unit to `~/.config/systemd/user/acheron-daemon.service`, then `daemon-reload` + `enable --now`. Every step is a plain overwrite or an already-idempotent `systemctl` call, so re-running is safe.
- `packaging/test_install.sh`: automated coverage per the ticket's own scope limit — asserts the unit file's required directives via exact-line `grep`, and runs `install.sh` twice against a fake `$HOME` with `cargo`/`systemctl` stubbed out (recording invocations to a log), asserting the binary/unit land in the right place, the installed unit matches the source file byte-for-byte, and both `daemon-reload`/`enable --now` fire exactly once per run with no error on the second run. No real systemd session or Rust build needed.

**GUI safety net (ticket 21's other half):**
- `gui/acheron_gui/systemd_client.py` (new): `SystemdClient` Protocol + real `DBusSystemdClient`, mirroring `daemon_client.py`'s shape. `ensure_daemon_started()` calls `ResetFailedUnit` then `StartUnit("replace")` against `org.freedesktop.systemd1`'s `Manager` interface over the session bus via `Gio.DBusProxy` — no `systemctl` shell-out, no subprocess.
- `gui/acheron_gui/app.py`: `AcheronApplication.__init__` gains an optional `systemd_client` param (defaults to a real `DBusSystemdClient()`, mirroring the existing `client`/`DBusDaemonClient` pattern); new `_ensure_daemon_started_on_launch` is called once, first thing in `do_activate`, wrapped in `try/except GLib.Error` — best-effort (never blocks the GUI opening), but prints the error to stderr rather than swallowing it outright (see live-testing finding below).
- Tests: `gui/tests/test_app.py` gains `_FakeSystemdClient` plus tests for the call happening and the error being reported without raising.

`/code-review` (medium) on the diff caught one real issue, fixed: `DBusSystemdClient`'s `Gio.DBusProxy` was constructed eagerly in `__init__`, which itself runs unconditionally and un-guarded in `AcheronApplication.__init__` — well before `do_activate`'s try/except exists to catch anything — so a proxy-construction failure (e.g. session bus unreachable) would have crashed the whole GUI at startup, directly contradicting the "must never block the GUI from opening" promise. Fixed by making the proxy lazy, built on the first `ensure_daemon_started()` call instead, so construction failures surface from the same call site the try/except already guards. A second finding (the `Gio.DBusProxy.new_for_bus_sync` boilerplate duplicating `DBusDaemonClient`'s) was accepted as a minor, non-fatal duplication not worth abstracting for two call sites.

**Live demo, performed on the user's real machine/hardware:**

1. **`install.sh` + reboot**: `install.sh` run for real (built, installed, `enable --now`). A full reboot (not just log-out/log-in — a prior log-out/log-in cycle turned out not to actually restart the user's `systemd --user` manager, so it didn't exercise this path at all) confirmed genuine login-autostart: `journalctl --user -u acheron-daemon -b` showed the unit starting on its own via `WantedBy=default.target`, no manual start needed. One incidental finding along the way: the daemon crashed once on its very first start attempt each boot (exit code 1, no diagnostic output captured — root cause not identified, no root access available to strace it), self-recovered within ~4s via `Restart=on-failure`/`RestartSec=1`, and never recurred across several subsequent clean starts. Logged as a follow-up rather than chased further, since ticket 21's own job (the unit's resilience config) worked exactly as designed. The Tartarus Pro itself also needed a physical unplug/replug before the daemon recognized it post-reboot — plausibly a device-enumeration-at-boot timing question, but ticket 07/10/20 (`CaptureSource`) territory, not this ticket's.
2. **`kill -9` + GUI relaunch, crash-recovery safety net**: this is where the demo caught a real bug. Deliberately tripping `StartLimitBurst` (5 kills within `StartLimitIntervalSec=60`) put the unit into genuine `failed` state ("Start request repeated too quickly"). Quitting and relaunching the user's GUI did **not** bring it back — because `Manager.ResetFailed()` (the call ticket 10/spec.md/this ticket's own checklist all specified) takes **no arguments** and clears every failed unit on the bus, not one; calling it with a unit-name string is a `GLib.Error` (`InvalidArgs`), which `_ensure_daemon_started_on_launch`'s original fully-silent `except: pass` swallowed with zero trace anywhere. Confirmed live via `busctl --user introspect` against the running `org.freedesktop.systemd1.Manager`: the real per-unit method is `ResetFailedUnit(s unit_name)`. Fixed in `systemd_client.py`, verified directly (`DBusSystemdClient().ensure_daemon_started()` against a live, deliberately-`failed` unit — unlatched and restarted it), then re-verified through the actual GUI: unit tripped into `failed` again, user quit/relaunched the GUI, daemon came back with no terminal interaction, confirmed by both the user and independently via `systemctl`/`busctl` on this end. `spec.md`, ticket 10, and ticket 11 corrected to say `ResetFailedUnit` (they all had the wrong no-argument form). The error-swallowing itself was also loosened — failures are now printed to stderr — specifically because full silence is what let this bug hide until a live crash-recovery demo.
