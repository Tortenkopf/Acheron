# 21 — systemd packaging + launch safety net

**What to build:** The Daemon runs continuously without the user having to launch it by hand — it starts at login via `systemd --user`, and the GUI double-checks it's up (and clears any stuck failure) every time the GUI itself launches. See `.scratch/tartarus-keybinder/spec.md` ("Packaging and lifecycle") for the full design.

**Blocked by:** 20

**Status:** resolved

- [x] A `systemd --user` unit at `~/.config/systemd/user/acheron-daemon.service`: `Type=simple`, `ExecStart=%h/.local/bin/acheron-daemon`, `After=graphical-session.target`, `WantedBy=default.target`, `Restart=on-failure`, `RestartSec=1`, `StartLimitIntervalSec=60`, `StartLimitBurst=5`. Stdout/stderr go to the default journal.
- [x] A small idempotent `install.sh`: builds the release binary, copies it to `~/.local/bin/acheron-daemon`, copies the unit file into place, runs `systemctl --user daemon-reload`, then `systemctl --user enable --now acheron-daemon`. Safe to re-run on every rebuild.
- [x] On its own launch, the GUI calls `org.freedesktop.systemd1.Manager.ResetFailed("acheron-daemon.service")` then `StartUnit("acheron-daemon.service", "replace")` over the same session D-Bus connection it already holds — no `systemctl` shell-out, no subprocess. `StartUnit` is a no-op if the Daemon is already running.
- [ ] Live demo: run `install.sh`, log out and back in, and confirm (`systemctl --user status acheron-daemon` or the GUI's status chip from ticket 20) the Daemon is already running with no manual start. Separately, `kill -9` the Daemon process to force it into `systemd`'s `failed` state, then launch the GUI, and confirm the Daemon comes back automatically (visible via ticket 20's status chip flipping from not-running to running) with no terminal interaction. **Not yet performed — needs the user to log out/in on their own session; see Comments.**
- [x] Automated coverage is limited to what doesn't require a real systemd user session (e.g. `install.sh`'s idempotency, unit-file content) — the login-autostart and crash-recovery demos above are manual/live-hardware verification, not unit tests.

## Comments

**Packaging:**
- `packaging/acheron-daemon.service`: the exact unit from the ticket/spec — `StartLimitIntervalSec`/`StartLimitBurst` placed in `[Unit]` (systemd's canonical location for unit-level start-rate-limiting, not `[Service]`), `Restart=on-failure`/`RestartSec=1`/`Type=simple`/`ExecStart=%h/.local/bin/acheron-daemon` in `[Service]`, `WantedBy=default.target` in `[Install]`.
- `install.sh` (repo root): builds `daemon/` in release mode, copies the binary to `~/.local/bin/acheron-daemon` and the unit to `~/.config/systemd/user/acheron-daemon.service`, then `daemon-reload` + `enable --now`. Every step is a plain overwrite or an already-idempotent `systemctl` call, so re-running is safe.
- `packaging/test_install.sh`: automated coverage per the ticket's own scope limit — asserts the unit file's required directives via exact-line `grep`, and runs `install.sh` twice against a fake `$HOME` with `cargo`/`systemctl` stubbed out (recording invocations to a log), asserting the binary/unit land in the right place, the installed unit matches the source file byte-for-byte, and both `daemon-reload`/`enable --now` fire exactly once per run with no error on the second run. No real systemd session or Rust build needed.

**GUI safety net (ticket 21's other half):**
- `gui/acheron_gui/systemd_client.py` (new): `SystemdClient` Protocol + real `DBusSystemdClient`, mirroring `daemon_client.py`'s shape. `ensure_daemon_started()` calls `ResetFailed` then `StartUnit("replace")` against `org.freedesktop.systemd1`'s `Manager` interface over the session bus via `Gio.DBusProxy` — no `systemctl` shell-out, no subprocess.
- `gui/acheron_gui/app.py`: `AcheronApplication.__init__` gains an optional `systemd_client` param (defaults to a real `DBusSystemdClient()`, mirroring the existing `client`/`DBusDaemonClient` pattern); new `_ensure_daemon_started_on_launch` is called once, first thing in `do_activate`, wrapped in `try/except GLib.Error` — best-effort, since this is a safety net, not a requirement for the GUI to open (the status chip from ticket 20 already gives an honest live answer if the Daemon still isn't up afterward).
- Tests: `gui/tests/test_app.py` gains `_FakeSystemdClient` plus tests for the call happening and the error being swallowed.

`/code-review` (medium) on the diff caught one real issue, fixed: `DBusSystemdClient`'s `Gio.DBusProxy` was constructed eagerly in `__init__`, which itself runs unconditionally and un-guarded in `AcheronApplication.__init__` — well before `do_activate`'s try/except exists to catch anything — so a proxy-construction failure (e.g. session bus unreachable) would have crashed the whole GUI at startup, directly contradicting the "must never block the GUI from opening" promise. Fixed by making the proxy lazy, built on the first `ensure_daemon_started()` call instead, so construction failures surface from the same call site the try/except already guards. A second finding (the `Gio.DBusProxy.new_for_bus_sync` boilerplate duplicating `DBusDaemonClient`'s) was accepted as a minor, non-fatal duplication not worth abstracting for two call sites. Regression test added: `test_dbus_systemd_client_does_not_connect_at_construction_time`. 106 daemon tests + 70 GUI tests passing; `packaging/test_install.sh` passing.

**Live demo not yet performed** — the two demo steps (`install.sh` + log out/in; `kill -9` + GUI relaunch) require the user's own session (a real log-out/log-in cycle, and killing the actual running Daemon process) and were left for the user to run rather than performed autonomously. Everything reachable without those — the unit file, `install.sh`'s idempotency, and the GUI-side `ResetFailed`/`StartUnit` wiring and its failure handling — is implemented and covered by automated tests above.
