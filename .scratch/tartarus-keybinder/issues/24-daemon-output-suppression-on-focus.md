# 24 — Daemon: output-suppression flag + D-Bus surface + disconnect safety

**What to build:** The Daemon gains a way for a connected D-Bus client to suppress all of its synthetic `uinput` output — Fire-once, Hold-to-repeat, and Toggle firings alike — for as long as that client says so, without altering any Trigger-mode firing logic, Macro looping, or Toggle's `active_toggles` state internally. Only the actual write to the virtual input device is withheld while suppression is on; everything resumes exactly where it logically was the instant suppression is cleared. If the client that turned suppression on disappears (crash, `kill -9`, any ungraceful disconnect) without explicitly clearing it, the Daemon must notice and auto-clear it itself — suppression must never be able to get stuck on and silently mute the entire physical device.

This ticket delivers a complete, independently testable Daemon-side capability against the existing `CaptureSource` fake-event seam; it does not require a real GUI to be driving it yet (that's ticket 25).

**Blocked by:** None — can start immediately.

**Status:** resolved

- [x] Injector task (`injector.rs`, the single task that already serializes every `uinput` write — the ticket text said `executor.rs`, but that module only compiles/walks `MacroStep` sequences; the actual `sink.emit` call lives in `injector.rs`'s `injector_loop`) gates each write behind a suppression flag; when set, Fire-once/Hold-to-repeat/Toggle firing logic and internal Macro looping (including `run_toggle_loop`'s sleeps/iteration) continue completely unaffected — only the write to the virtual device is skipped.
- [x] New `com.acheron.Daemon` D-Bus method (`SetOutputSuppressed(suppressed: b)`) for a client to push its current focus/suppression-desired state (level-set — reflects "should output be suppressed right now," not an edge-triggered toggle — so a client can call it redundantly with the same value with no ill effect).
- [x] Suppression auto-clears if the connection that set it drops before it's explicitly cleared, via peer/name-disconnect detection on the Daemon's `zbus` connection — `NameOwnerChanged` (subscribed before checking current ownership, to close the TOCTOU where the client vanishes between the reply and the watcher's subscription completing) on a real bus, `Connection::closed()` over a private peer-to-peer connection (no bus daemon, no unique name to watch).
- [x] A running Toggle's state (`active_toggles`, its internal loop) is unaffected by suppression turning on or off — only whether its output reaches `uinput` changes. Confirmed via `GetState()` showing the Toggle still active throughout a suppress/resume cycle.
- [x] If suppression is requested by one client while another client (or no client) previously held it, behavior is well-defined: last-write-wins on the flag (an epoch counter, bumped and read atomically under one lock acquisition per call, since zbus spawns a task per method call and `SetOutputSuppressed` calls can run concurrently), with disconnect-clear tied to whichever connection most recently set it.
- [x] Test coverage at the existing `CaptureSource`/`TestServer` fake-event seam (`daemon/src/dbus/mod.rs`):
  - [x] Output is withheld while the flag is set, and resumes when explicitly cleared.
  - [x] Output resumes automatically when the client that set the flag disconnects, without an explicit clear call.
  - [x] A Toggle started before suppression continues looping/reporting as active throughout, and its buffered/next output reaches `uinput` again once suppression clears.
- [x] `spec.md` and `CONTEXT.md` gain a new section documenting Daemon-output suppression, explicitly noted as separate from — and not an amendment to — the existing Toggle-stop-conditions list (ticket 04): a Toggle is never stopped by this mechanism, only its output delivery is gated.

## Comments

Implemented in `daemon/src/dbus/mod.rs` (`SetOutputSuppressed`, `watch_disconnect`, `SuppressionState`) and `daemon/src/injector.rs` (`InjectorMessage::SetSuppressed`). `Daemon` now also holds an `Injector` handle alongside its `Command` sender, used only by this method — deliberately bypassing the dispatch task since suppression never touches `Config`.

`/code-review` caught two real races in the first pass, both fixed before commit: (1) the epoch bump/read was split across two separate lock acquisitions with an `.await` in between, so two concurrent `SetOutputSuppressed` calls (zbus spawns a task per method call) could misattribute each other's epoch and clobber each other's stored watcher handle — fixed by capturing the bumped epoch atomically in the same critical section that takes/aborts the previous watcher. (2) `watch_disconnect` subscribed to `NameOwnerChanged` with no check for whether the name had already vanished before the subscription completed, which could permanently miss a disconnect that raced the watcher's own setup — fixed by checking `name_has_owner` immediately after subscribing (subscribe-then-check ordering, so nothing in the gap is missed).

Next: ticket 25 (GUI-side wiring of window focus to this method).

**2026-08-15 (cross-reference, follow-up) — ticket 25's live-hardware verification found a real bug in this ticket's own injector gating and fixed it here.** `ActiveToggle::stop()`'s force-release (`executor::force_release`) was going through the same `InjectorMessage::KeyState` write this ticket gates behind the suppression flag — so a Toggle stopped while suppression was on had its release silently withheld, leaving a real physical key stuck down at the OS level even though `active_toggles` correctly reported it stopped. Fixed by adding `InjectorMessage::ForceRelease`/`Injector::force_release_key`, a write this task never gates, and pointing `force_release` at it instead. This ticket's own core design (suppression as a pure future-write gate, level-set, resumes instantly) is unchanged — this was a gap in what got gated, not a change to the flag's semantics. See ticket 25's comments for how live testing found this.
