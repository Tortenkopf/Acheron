# 25 — GUI: focus-scoped output suppression wiring

**What to build:** The real Acheron GUI actually drives ticket 24's Daemon-side suppression capability from its own window's live focus state, so the ticket 22 freeze and the stray-macro-output-in-a-text-field risk (ticket 23) are closed end-to-end — not just reachable via a manual D-Bus call. Whenever the GUI's main window has keyboard focus, it tells the Daemon to suppress output; whenever it doesn't, it tells the Daemon output is fine to resume. This includes the moment the GUI first connects, in case it starts out already focused.

**Blocked by:** 24

**Status:** resolved

- [x] `app.py` wires GTK focus tracking (e.g. `notify::is-active` on the main `Gtk.ApplicationWindow`) to call ticket 24's new Daemon method on every focus change, passing the window's current focus state.
- [x] Initial focus state is pushed once on GUI startup/connect, not just on subsequent transitions — covers the GUI launching while already the focused window.
- [x] `gui/acheron_gui/daemon_client.py`'s `DaemonClient`/`DBusDaemonClient` gains the corresponding client method, following the existing call shape (e.g. `switch_profile`'s pattern).
- [x] Test coverage at the existing `DaemonStub` D-Bus client seam: simulated focus-state changes call the new method with the correct value, including the one-shot initial-state call on startup.
- [x] Live/manual verification against the real Daemon + real GUI + real hardware (per ticket 22/23's repro) — **required two amendments beyond the original scope before it actually passed; see comments below.** Final state: starting a Toggle while the GUI window is already focused no longer freezes it, and focusing the GUI while a Toggle is already running no longer freezes it either (the Toggle is force-stopped instead of merely suppressed — a deliberate scope change from the ticket's original "suppress, don't stop" framing, decided live; see below). Confirmed via `GetState()`/`active_toggles`.
- [x] **(Added during live verification)** `StopAllToggles()` D-Bus method + `Command::StopAllToggles`, called by the GUI (`gui/acheron_gui/app.py`) alongside `SetOutputSuppressed(true)` on every focus-*gain* only — force-stops every active Toggle. No corresponding action on focus-loss (deliberately one-directional).
- [x] **(Added during live verification)** `Injector::force_release_key`/`InjectorMessage::ForceRelease` — a Toggle-stop's force-release now bypasses suppression unconditionally, fixing a real stuck-key bug the live test surfaced in ticket 24's original gating.

## Comments

Implemented in `gui/acheron_gui/app.py` (`_wire_focus_tracking`), `gui/acheron_gui/daemon_client.py` (`set_output_suppressed` on both `DaemonClient` and `DBusDaemonClient`, calling `SetOutputSuppressed(b)`), and `gui/acheron_gui/daemon_stub.py` (`DaemonStub.set_output_suppressed`, recorded to `.calls` for test assertions).

`notify::is-active` carries no value of its own and `is-active` is a read-only, WM-computed property (`Gtk.Window.set_property("is-active", ...)` raises) — nothing can force it in a headless test. `_wire_focus_tracking` is duck-typed against `is_active()` + `connect()` rather than annotated to a real `Gtk.Window`, so `gui/tests/test_app.py` drives it with a small fake window exposing a `simulate_focus_change()` seam, the same shape as `DaemonStub`'s own `simulate_*` methods. The same handler is both connected to the signal and called once immediately for the initial push, so there's one code path instead of two that could drift.

`/code-review` (medium) caught a real reentrancy hazard before commit: the first pass called `client.set_output_suppressed` straight through from the `notify::is-active` handler, which can fire while some other blocking `call_sync` (e.g. `switch_profile`) is still in flight on the same `GMainContext` — nesting a second blocking D-Bus round-trip inside the first one's still-unfinished wait, the same class of hang `app.py`'s own module docstring documents for `SwitchProfile`/`ActiveProfileChanged` (tickets 18/19). Fixed by deferring the call via `GLib.idle_add`, matching `on_layer_changed`/`on_profile_changed`'s existing guard. `test_app.py` pumps the default `GMainContext` after each simulated focus change to observe the deferred call, plus a regression test asserting the signal handler never calls through synchronously.

**2026-08-15 (same day, follow-up session) — live-verified against the real Daemon + real GUI + real Tartarus Pro, with two real bugs found and fixed along the way.**

Built and ran the real `acheron-daemon` binary and `gui/main.py` against each other and the physical device (config already had `Gaming.grid_r1c2` bound to a Toggle Macro `[KeyDown(KEY_A), Delay(1000)]` left over from ticket 22's own testing).

**Round 1 — both of ticket 22's freeze scenarios reproduced, contradicting the ticket's own "closes the freeze end-to-end" framing:**
- *Scenario A*: focus the GUI, press the physical key once (starts the Toggle, no freeze — suppression correctly withheld the output), press it again (stops the Toggle) — **froze**, even though focus never knowingly left the window.
- *Scenario B*: start the Toggle while the GUI is unfocused, then click into the GUI to focus it — **froze**.

Captured live D-Bus traffic with `busctl --user monitor com.acheron.Daemon` (`dbus-monitor`'s eavesdrop match failed silently on this session's bus policy — acquired then immediately lost the match rule; `busctl monitor` doesn't need eavesdrop and worked directly). An idle 30s capture (GUI focused, nothing touched) showed exactly one `SetOutputSuppressed` call — rock stable. A capture across the live repro showed 14 flips of `SetOutputSuppressed` true/false within about a minute, correlated with device activity, not with any window-switching the person driving the hardware reported doing.

**Root-caused scenario A to a real code defect** (not the flapping, though that's also real — see below): `ActiveToggle::stop()`'s force-release (`executor::force_release`) called `injector.set_key_state(key, false)`, gated by the suppression flag exactly like every other write (`daemon/src/injector.rs`'s `InjectorMessage::KeyState` handling). So a Toggle stopped while the GUI is suppressing output had its release silently dropped — the key was never actually released at the OS level even though `active_toggles` correctly showed it stopped. First fix (this round): added `Injector::force_release_key`/`InjectorMessage::ForceRelease`, a write the injector never gates, and pointed `executor::force_release` at it instead. Regression tests: `executor::tests::toggle_stop_force_releases_a_held_key_even_while_output_is_suppressed`, `dbus::tests::stop_all_toggles_over_real_dbus_releases_a_key_even_while_suppressed`.

Re-tested after that fix: scenario A's specific stuck-key mechanism was real and worth fixing, but **did not fully explain the freeze** — restarting the daemon and repeating scenario B (focus arriving while a Toggle is already running, no stop involved) still froze. The force-release fix only ever helps the *stop* path; it does nothing when the freeze happens purely from focus arriving mid-Toggle.

**Root cause for scenario B (and the deeper reason A also reproduced): suppression only gates *future* writes — it cannot undo a key that already went down for real before suppression engaged.** A Toggle started while the GUI is unfocused sends a real `KeyDown` to `uinput`; the OS itself arms autorepeat for that key, independent of anything the Daemon does afterward. When focus then moves to the GUI, suppression turning on doesn't touch that already-armed key — the window gains keyboard focus while a real key is mid-autorepeat, which is exactly ticket 22's original, already-diagnosed Wayland/Mutter freeze precondition. (Scenario A's 14-flip trace likely reflects the same mechanism via a route the person driving the hardware didn't consciously trigger — GDK's `is-active` demonstrably isn't perfectly stable on this compositor even without deliberate window-switching, per the idle-vs-active capture contrast above, though this wasn't chased to full root cause since the fix below closes the observable freeze regardless of why `is-active` flickered.)

**Decision (2026-08-15, live, user call):** fix this by having the GUI force-stop every running Toggle outright on focus-gain, not just suppress its output — deliberately narrower than a full "suppress → resume" story: *"I do not think the GUI ever needs to re-engage a toggle it has stopped ... We just need to guard the GUI against people leaving the toggle on by accident."* This revises ticket 23's original "suppress, not stop" decision for this one case (GUI regaining focus specifically), based on live evidence ticket 23 didn't have: pure suppression cannot prevent the freeze when a Toggle is already running before focus arrives, because the precondition (a real, already-armed key) is set before suppression ever gets a chance to act. `SetOutputSuppressed` itself is unchanged and still never stops anything — the new `StopAllToggles()` is a separate call the GUI makes alongside it, one-directional (focus-gain only, never resumed on focus-loss).

Second fix: `Command::StopAllToggles` + dispatch-task handling (drains `toggles` exactly like `SwitchProfile`'s existing force-stop loop, minus the Profile change) + `com.acheron.Daemon.StopAllToggles()` D-Bus method + GUI client method (`daemon_client.py`, `daemon_stub.py`) + `app.py`'s `_wire_focus_tracking` calling it right after `set_output_suppressed(True)` on every focus-*gain*. Regression tests: `dispatch::tests::stop_all_toggles_force_stops_every_active_toggle_without_switching_profile`, `dbus::tests::stop_all_toggles_over_real_dbus_releases_a_key_even_while_suppressed`, plus `gui/tests/test_app.py`'s focus-gain/focus-loss call-sequence tests. `spec.md`'s "Toggle behavior across Layer/Profile switches" gained a third, explicit stop condition; `CONTEXT.md`'s "Output suppression" glossary entry now cross-references it as a separate mechanism, not a suppression side effect.

**Re-verified live after both fixes, all three checks passing:**
- Scenario A (continuous focus, start then stop via the same physical key): no freeze either time.
- Scenario B (start unfocused, then focus the GUI): no freeze; `GetState()` confirmed `active_toggles: []` immediately after.
- Normal use (GUI never focused at all): Toggle output reaches whatever window *is* focused and keeps running normally — unaffected by any of the above.

Full test suites green throughout: 101 daemon tests (`cargo test`), 55 GUI tests (`pytest`).

**2026-08-15 (same day) — a second `/code-review` (medium) pass on the amended diff caught one more real bug and one duplication, both fixed:**

1. **Real bug**: a Toggle's own *normal* loop step (not the stop path) could also race suppression. `executor::execute_step`'s `KeyUp` arm removed `key` from `held` unconditionally, even when the matching write was silently withheld by suppression — so if suppression turned on and the loop's own scheduled `KeyUp` step ran (its write dropped) shortly before `StopAllToggles`'s cancellation actually reached the loop, `held` would forget a key that was still genuinely down, and the eventual `force_release` would never re-release it. Root cause: `held` was updated based on the loop's *intent*, not on whether the write actually reached `uinput`. Fixed by having `Injector::set_key_state` report back (`Result<bool, InjectorClosed>`, via a `oneshot` reply on `InjectorMessage::KeyState`) whether the write was actually applied or suppressed, and `execute_step` now only mutates `held` when `applied` is true. Regression test: `executor::tests::a_suppressed_keyup_step_keeps_the_key_in_held_for_a_later_force_release`.
2. **Duplication**: `Command::SwitchProfile` and `Command::StopAllToggles` each had their own copy of the `for (_, toggle) in toggles.drain() { toggle.stop().await; }` loop. Extracted into a shared `dispatch::stop_all_toggles(&mut HashMap<Input, ActiveToggle>)`, called by both.

Full test suites re-verified green after both fixes: 102 daemon tests, 55 GUI tests. Live re-verification against real hardware was not repeated for this round (the terminal that had been driving the daemon crashed mid-session while the reviewer's first pass was running — unrelated to these fixes, not yet diagnosed) — the fixes address a race the live session's specific timing never happened to hit, confirmed instead by the new deterministic `tokio::time::advance`-based unit test above, which reproduces the exact interleaving directly.
