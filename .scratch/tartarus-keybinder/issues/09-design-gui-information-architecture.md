## Question

Prototype how the GTK4 GUI presents and edits Profiles, Layers, Bindings, and Macros over the D-Bus surface decided in [Decide D-Bus interface surface](./08-decide-dbus-interface-surface.md) — navigation structure (e.g. Profile picker + Binding grid vs list), how a Binding's Input/Action/Trigger-mode are edited, how Macro sequences (Keypress + delay steps) are authored, and what the tray icon shows/exposes (active Profile/Layer, quick switch) per CONTEXT.md's GUI definition.

## Answer

Prototype session, 2026-08-13, via `/prototype` (UI branch). Started as three structurally different, radically-different variants compared live in a running GTK4 app (real widgets, in-memory `DaemonStub` standing in for the ticket 08 D-Bus surface); iterated against user feedback (including two live screenshots and a device photo) down to one real information architecture. Asset: [prototype/09-gui-information-architecture/prototype.py](../../../prototype/09-gui-information-architecture/prototype.py) — the full set of explored variants is preserved in that file's git history in spirit, but this repo has no git yet, so unlike the skill's usual "throwaway branch" step, the file itself (with the exploration narrated in its docstring) is the primary source, left in place rather than split across branches.

**One main view, one collapsible sidebar, one dropped variant:**
- **Device Overview** (main and only top-level view) — the window mirrors the physical Tartarus Pro directly: a `Gtk.Grid` for the 20-key pad (rows 1-3 five wide, row 4 four wide for keys 16-19), with the wheel (scroll up / middle click / scroll down) occupying the same grid as a continuation of column 5 starting at row 4 — physically where a 20th inline key would sit, next to key 19. The thumbstick and Mode key sit further right: a diamond of four buttons drawn **rotated 90° clockwise** from a naive N/S/E/W layout (top lobe fires Left, left lobe fires Down, right lobe fires Up, bottom lobe fires Right) matching how the device actually looks to the user viewing it from the side on the desk, each lobe showing an arrow glyph (←↓↑→) matching its own default/passthrough evdev output rather than its screen position; the Mode key is a circular button directly above the diamond's top (Left) lobe; key 20 is a separate paddle-shaped button below the diamond, not inline with the grid — the physical layout doesn't put it there (confirmed against Device Picture.jpg and the user's corrected layout.md). Profiles are a left-hand sidebar of buttons (not a dropdown); Base/Held is a two-button tab row. Clicking any device control opens its binding editor (trigger mode, Keypress-vs-Macro, key+modifiers or a macro step builder) in a popover.
- **Action Table** — demoted from a standalone page to a collapsible sidebar off Device Overview, toggled via a button next to the Base/Held tabs, **closed by default**. It has no Profile/Layer pickers of its own — it reflects whatever's already selected in Device Overview rather than duplicating those controls — just one expandable row per Input (only bound ones shown by default; a "Show all inputs" checkbox reveals passthrough rows too). It stays open across edits/profile switches: sidebar-open is GUI-only view state, kept in a small `ui_state` dict threaded through re-renders separately from the Daemon-mirroring state, specifically because the naive version (state implicit in the widget tree) reset to closed on every rebuild.
- **"Focused wizard"** (a compact dot-overview strip + one-binding-at-a-time editor with Prev/Next) was built and compared live, then explicitly rejected and deleted — Device Overview plus the Action Table sidebar covers both the spatial and the dense-list use cases well enough that a third navigation mode added no value.

**Binding editor is one shared component** (trigger dropdown, Keypress/Macro toggle, key+modifier fields, macro step add/remove list) used identically from Device Overview's popovers and the Action Table's expandable rows — the two views differ only in navigation, not in how a Binding is actually edited.

**Tray icon** — represented in the prototype as an in-window mock panel (icon + "Profile · Layer" status text, a "Quick switch" popover listing Profiles) since `AppIndicator3`/`AyatanaAppIndicator3` isn't installed in this dev sandbox (confirmed unavailable via `gi.require_version` probe). This settles *what* the tray shows and exposes (active Profile, active Layer, a quick Profile-switch menu) but not the real `AppIndicator3` wiring itself, which is an implementation detail for whoever builds the real GUI, not a fresh decision.

No new tickets surfaced. [Decide systemd service packaging](./10-decide-systemd-service-packaging.md) and [Decide first-run experience](./11-decide-first-run-experience.md) remain the frontier.
