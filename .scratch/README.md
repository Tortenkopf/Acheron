- [Tartarus status-LED indicator](tartarus-status-leds/map.md) — **spec ready** (wayfinder, all tickets resolved 2026-09-02). Charted the way to a gated [`spec.md`](tartarus-status-leds/spec.md) for a feature that lets each Profile define an on/off state for the three side Status LEDs (orange/green/blue), asserted on Profile switch, on Daemon startup, and on every device (re)connect. **Kill-gate PASSED** (ticket 01, fw v1.2): all three LEDs independently host-controllable via the `0x0F/0x02` LED-ID-`0x0B` static-effect frame, all-off reachable, no adverse device behaviour, every byte of ticket 02's source-derived wire spec verified on hardware. Tickets 01–05 resolved; [`spec.md`](tartarus-status-leds/spec.md) + [ADR-0006](../docs/adr/0006-status-leds-driven-from-dispatch-over-short-lived-hidraw-fds.md) + the `Status LED` / `Status LED assignment` `CONTEXT.md` entries are written. **Implementation is a fresh effort** — this map is done and can be archived. Key decisions in the spec: stateless `assert_status_leds()` / `clear_status_leds()` in `analog.rs` (short-lived Interface-2 hidraw fd, no driver mode), driven by a dedicated non-fatal `led` task fed a `watch<Option<StatusLeds>>` from dispatch (the sole `Config` owner); `Effect::AssertStatusLeds` on Profile switch + set-edit, assert on every connect edge, all-off on clean exit; `StatusLeds { orange, green, blue }` struct + `#[serde(default)]` `Profile.status_leds` (no `schema_version` bump — all-off serde default is the migration); `Edit::SetStatusLeds` / `SetStatusLeds(bbb)` whole-triple; no `GetState()` addition, no new signal; GUI "Status LEDs" group (three colour lozenges, lit/unlit) in `device_row` between thumbstick and Chords per the user's mockup; nothing in `rules.py`. Research files `tartarus-pro-status-leds.md` (grounding) + `status-led-wire-protocol.md` (ticket 02); prototype `prototype/01-status-leds/`.
- [Tartarus status-LED indicator — implementation](tartarus-status-leds-impl/issues/) — **active**, non-wayfinder (ticket files only, no map).
