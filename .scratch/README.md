Charted the course from the shipped MVP to a feature-complete v1.0 (Chord/Stepper/Profile-Switch/Controller-button/Axis Actions, the Macro & Stepper libraries, grid-key analog capture + Analog-repeat, the full output picker, tray icon, About dialog, release docs) and executed it ticket by ticket. Post-1.0 refinements (Analog-repeat/axis rate curves, joystick hat direction) go to a new effort.
- [Tartarus status-LED indicator](tartarus-status-leds/map.md) — **active**, wayfinder (charting done 2026-09-02). Finding the way to a gated `spec.md` for a feature that lets each Profile define an on/off state for the three side Status LEDs (orange/green/blue), asserted on Profile switch. **Kill-gate PASSED** (ticket 01, 2026-09-02): on the real Tartarus Pro (fw v1.2) all three LEDs are independently host-controllable via the `0x0F/0x02` LED-ID-`0x0B` static-effect frame, all-off is reachable, no adverse device behaviour — and every byte of ticket 02's source-derived wire spec verified on hardware. Key findings: no on-device keymap switch exists (no re-assert hook needed); neither NOSTORE nor VARSTORE persists across re-enumeration (daemon must assert on startup *and* every reconnect); use NOSTORE. Tickets 01 + 02 resolved; frontier: ticket 03 (daemon architecture, HITL grilling). Research files `tartarus-pro-status-leds.md` (grounding) + `status-led-wire-protocol.md` (ticket 02); prototype `prototype/01-status-leds/`.
- [Post-release development](post-release-development/issues/) — **active**, non-wayfinder (ticket files only, no map). A second architecture review (2026-09) opened a fresh set: the parallel Macro and Stepper library views in the GUI collapsed into one `LibraryKind`-parameterised module (13, `ready-for-agent`).
