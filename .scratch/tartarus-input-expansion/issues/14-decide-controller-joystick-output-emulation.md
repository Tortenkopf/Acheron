Type: grilling
Status: resolved

## Question

Design **Controller/Joystick output emulation** as a new Acheron capability, surfaced by the Synapse catalog ([Catalog Synapse's remap/macro feature set](./07-task-catalog-synapse-feature-set.md)) and locked in scope (non-blocking for v1.0) by [Lock the v1.0 feature list](./08-decide-v1-feature-list.md). Synapse emulates a full kernel-level virtual controller partly to circumvent anti-cheat tooling on Windows — that rationale doesn't transfer to Linux, and it's explicitly not wanted here. A **userspace-emulated** virtual gamepad (a second `uinput` device advertising `EV_ABS`/`BTN_*` gamepad codes, analogous to how the existing keyboard `uinput` device already advertises the full `EV_KEY` range) is fine and is the intended shape.

This is the first ticket of an open-ended strand — expect research and prototype tickets to graduate from it once the design questions below narrow the shape; don't try to spec the whole implementation in this session.

Settle at least:

- **Minimal viable mapping**: which physical Inputs map to which virtual controller elements? Synapse's Joystick mode offers 24 bindable buttons plus X/Y/Z analog axis output (with single-step increment/decrement, not just full-deflection) and four digital diagonal directions. Acheron doesn't need to match this 1:1 — decide what subset is worth building given the Tartarus Pro's actual physical control count (20 grid keys, Mode key, thumbstick, wheel).
- **Axis output, digital now and analog later**: this bullet originally asked whether axis output should be *gated* on real analog input existing. That framing is obsolete — [the prototype](./13-task-standalone-analog-capture-prototype.md) settled that analog capture works, at a full 8-bit range per grid key. But the analog charting pass then split the strand: only the *data model* ([ticket 17](./17-decide-analog-data-model.md)) is in the v1.0 required floor, while the capture rework ([ticket 18](./18-rework-capture-path-for-analog.md)) stays non-blocking. So a v1.0 joystick would still derive its axes from digital presses. **Don't pick one — design an axis model that works from digital press/release now and accepts real depth without a rewrite when ticket 18 lands.** Ticket 17 is the ticket that decides how depth reaches `dispatch.rs`, so this session's axis design is an input to it: if an analog axis needs something from the event stream that ticket 17 isn't already planning to carry, say so.
- **New Action target, not a new Binding shape**: decide whether "fire a controller button/axis" is a new `Action` kind (alongside Keypress/Macro/Profile-Switch), reusing the existing Binding/Trigger-mode machinery, or something structurally different.
- **Macros firing controller/joystick buttons**: already settled during charting — **yes**, Macros should be allowed to include controller/joystick button steps (not axis — axis was explicitly ruled too complex for a Macro step). Build this in rather than re-litigating it.
- **Device advertising**: does the virtual gamepad need to be a distinct `uinput` device from the existing keyboard one, and if so, does it need `js0`/`event*` joystick-API compatibility (older `/dev/input/jsX` interface) for older game engines, or is a modern `evdev`-only gamepad sufficient for Linux gaming today? This is likely a `research` question to graduate.
- **GUI surface**: how a user assigns "controller button N" or "axis step +1" as an Action — likely its own picker, related to but distinct from the key/mouse-button picker in [Finalize mouse-button + key output and picker](./02-decide-mouse-button-output-and-picker.md).

## Answer

**Scope of this pass: buttons only, every Input eligible.** All 20 grid keys, the Mode key (already works for free today via the existing `ModeKeyRole::Bound` — no new Daemon capability needed), the thumbstick's 4 directions, and the wheel's 2 directions can all carry a controller-button Action. Axes are explicitly deferred to a future ticket — not built here, and not sharp enough yet to ticket (see the map's Not yet specified).

**Axis guidance for that future ticket**, so it doesn't repeat this ticket's now-stale premise: the "digital press/release now, real depth later" framing this ticket opened with is itself obsolete — real per-key depth (`u8`, 0-255) has been live in the Daemon since tickets 22/26/27 (`depth_tx`/`PhysicalEvent.depth`), independent of this strand ever consuming it. Whenever axis design happens, it should target real depth directly from the start, falling back to press/release step-increment only when `capture_mode` is Digital — not build a throwaway digital-only placeholder.

**New `Action::ControllerButton { button: KeyCode }`** — an ordinary Action variant, not a special-cased one. It reuses the existing Binding/Trigger-mode/dispatch pipeline exactly as Keypress does (Fire-once/Hold-to-repeat/Toggle all apply unchanged) — unlike `ProfileSwitch` (ticket 05), which needed dispatch-level interception because it mutates Daemon state rather than injecting keys. A controller-button press is the same shape as a Keypress: compile a down/up pair, inject it — only the target `uinput` device differs, an `executor`/`injector`-level distinction. This also means it composes for free: a Chord's Action can be `Action::ControllerButton` (ticket 01's Chord already fires any Action unchanged), and a Macro step's `KeyDown`/`KeyUp` can carry a `BTN_*` gamepad code the same way it already carries mouse-button codes today — no new work either place. Macros firing controller *axis* steps stays ruled out (already settled pre-session, axis is a Macro-step shape mismatch regardless of whether it's built).

**Device advertising**: a second, distinct `uinput` device from the existing keyboard one, advertising the *entire* standard Linux Gamepad Spec capability set — the named `BTN_GAMEPAD` range (`BTN_SOUTH/EAST/NORTH/WEST/TL/TR/TL2/TR2/SELECT/START/MODE/THUMBL/THUMBR`), the full `BTN_TRIGGER_HAPPY1`–`BTN_TRIGGER_HAPPY40` extra-button range, and `BTN_DPAD_UP/DOWN/LEFT/RIGHT` (axes deferred, so dpad is 4 discrete buttons for now) — mirroring the existing Keypress precedent (`injector::build_device` already advertises the entire `EV_KEY` range and leaves all curation to the GUI). No hardcoded physical-Input-to-button-code correspondence: any Input can be assigned any button code via its Binding; users design their own layout. `button: KeyCode` reuses the bare `KeyCode` type Keypress already uses (evdev's `BTN_*` codes already share `KeyCode`'s numeric space, the same precedent ticket 02 used for mouse buttons), validated against a curated gamepad-button allowlist at `SetBinding` time.

**Legacy `/dev/input/jsX` joystick API: closed, zero work needed.** Spawned and resolved [research the legacy joystick API](./37-research-legacy-joystick-api-compatibility.md) mid-session: `jsX` exposure isn't a feature Acheron implements — the kernel's `joydev` module auto-attaches a `jsX` node to any `uinput`-created device that already advertises the `BTN_GAMEPAD`/`ABS_X`-class bits the `evdev` path needs anyway, on any desktop kernel with `CONFIG_INPUT_JOYDEV` loaded (the near-universal default). SDL2/SDL3 (which nearly all native-Linux and Proton/Steam-Play gamepad detection ultimately runs through) defaults to `evdev`-only scanning; Godot's own pre-SDL driver actively excluded `jsX`; Steamworks/Valve's udev rules show no `jsX` dependency. Build the standard `evdev`/Gamepad-Spec device and get `jsX` for free.

**Naming**: `Action::ControllerButton`, "Controller" as the CONTEXT.md glossary term — matches the map's own established "Controller/Joystick output emulation" strand name and how players actually talk about the thing, not the kernel's internal `gamepad` vocabulary (which stays as an implementation comment near `build_device`, not the domain term).

**GUI**: out of scope for this ticket. Spawned [Prototype the controller-button picker UX](./38-prototype-controller-button-picker-ux.md), matching the decide → prototype → build pattern used elsewhere on this map.

**Drive-by fix**: CONTEXT.md's `Action` glossary entry still said "either a Keypress or a Macro" — never updated when Stepper's `Action::Step` (ticket 03) or Profile Switch's `Action::ProfileSwitch` (ticket 05) were decided. Folded the full current enumeration (Keypress, Macro, Step, ProfileSwitch, ControllerButton) into that line while adding the Controller entry.
