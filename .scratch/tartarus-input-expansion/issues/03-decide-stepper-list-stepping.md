## Question

Design the **Stepper** construct — a generic pairing of two physical Inputs ("forward"/"backward") that steps a cursor through a user-defined ordered list of items, firing the newly-selected item on every step, in one motion (confirmed reading during charting — each physical activation both moves the cursor *and* fires, not a separate select-then-confirm). Primary intended use is the scroll wheel's `ScrollUp`/`ScrollDown`, but the construct itself should stay generic — bindable to any two Inputs, per the domain model's existing treatment of wheel up/down as two independent Inputs. Settle at least:

- **Item type**: items are restricted to fire-once Keypress or mouse-button actions (settled by the user directly — no Macro items, no per-item Hold-to-repeat/Toggle). Confirm this constraint is actually enforceable/enforced in whatever shape you land on, don't re-litigate it.
- **Data model**: is a Stepper a distinct top-level entity (e.g. a named list referenced by two Bindings) or an inline structure attached to a Binding pair? How does it interact with the existing sparse `HashMap<Input, Binding>` per Layer — does binding an Input to "Stepper forward" preclude that Input also carrying an ordinary Binding?
- **Scoping**: is a Stepper (and its current cursor position) Profile-scoped, Layer-scoped, or independent of both?
- **Boundary behavior**: does stepping past either end of the list wrap around or clamp?
- **Cursor persistence**: does the current position survive a Layer switch, a Profile switch, and a Daemon restart, or reset in some/all of those cases?
- **GUI**: building/reordering a Stepper's item list is likely its own "how should it look/behave" question — consider `/prototype`.

Once resolved, add the full **Stepper** entry to CONTEXT.md (currently just a reserved name — see the map's Notes). The map's "Not yet specified" section flags unresolved composition questions between Stepper, Chord, and mouse-button output — revisit whether any of that fog is now specifiable once this ticket lands.

## Answer

Opened by testing the user's own reframing: is Stepper actually just an optional "wait for keypress" step inside a Macro? Close, but it breaks on two structural axes — a Binding is one Input→one Action, but Stepper needs *two* Bindings (forward/backward) sharing one persistent cursor, and Macro has no state that outlives a single firing (Fire-once replays from the top, Toggle loops the whole thing). The part of the instinct that *is* right — one motion moves the cursor and fires, no separate select-then-confirm — carries through as the firing semantics, just hung off a new construct rather than Macro.

- **Data model**: Stepper is a distinct top-level entity — a named, ordered list of items — living in one **global** library (not per-Profile), shared the way the in-flight [reusable Macro entities](./15-decide-reusable-macro-entities.md) design is heading. A Binding references it via a new `Action` variant, `Action::Step { stepper: StepperId, direction: Forward | Backward }` (one variant with a direction field, not two separate variants) — so it occupies an Input's ordinary Binding slot exactly like Keypress/Macro/Chord do, precluding an ordinary Binding on that Input the same way any Action choice does.
- **Reuse across pairs**: exactly one forward/backward pair may reference a given list at a time (no real use case for simultaneous multi-pair use), but a list can be **reassigned** to a different pair at any time — the whole point of the library. Assigning it to a new pair **silently moves** it off its old one; unlike Chord's overlap rejection, there's no ambiguity to prevent here, so no reject-at-save step.
- **Item type**: a dedicated type distinct from `Action` — restricted to a single fire-once keyboard key or mouse-button, never a Macro or another Stepper — enforced structurally (the type can't hold the excluded cases) rather than by a save-time check. Deliberately designed to extend to joystick/controller buttons later rather than hardcoded to today's two kinds, anticipating [Controller/Joystick output emulation](./14-decide-controller-joystick-output-emulation.md).
- **Boundary behavior**: wraps around (weapon-wheel-style UX, matches the primary scroll-wheel use case).
- **Scoping & persistence**: the cursor is **per-list** runtime state, independent of Profile/Layer (one position regardless of which Profile's Bindings currently reference the list). It is **never persisted** — Daemon-side only, always resets to the list's first item on restart. This mirrors `capture_mode`'s live-`GetState()` precedent (ticket 25) over adding a `Config` field, and avoids rewriting `config.toml` on every wheel notch.
- **Trigger mode**: governs the step itself — Fire-once (one step per press) and Hold-to-repeat (fast-advance while held, via the existing repeat machinery) both apply; **Toggle is disallowed**, the first documented exception to Trigger mode's "applies to every Binding" rule, since a cursor advance has no coherent continuously-running state.
- **GUI**: spawned [Prototype the Stepper library and list-editing UX](./31-prototype-stepper-library-ux.md), deliberately **blocked on** [Design reusable Macro entities](./15-decide-reusable-macro-entities.md) — both are "named entity, defined once, reassignable to a Binding" library patterns and may share UX or even end up the same prototype; left a forward-pointing note on ticket 15 flagging this.
- **Composition fog, partially graduated**: a Chord's Action can be `Action::Step`, and a Stepper's forward/backward Input can itself be a Chord — both fall out for free, since Chord already fires any `Action` unchanged. No new mechanism, no new ticket. The mouse-button↔Stepper half was already covered by the Item-type decision above. The Profile-Switch↔Stepper half of the map's composition fog stays open until [Design Profile Switch](./05-decide-profile-switch-action.md) settles its own shape.

CONTEXT.md gained the full **Stepper** entry and a Toggle-exception note on **Trigger mode**.
