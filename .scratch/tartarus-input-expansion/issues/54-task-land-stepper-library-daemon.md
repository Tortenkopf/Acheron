## Question

Land [Design the Stepper list-stepping construct](./03-decide-stepper-list-stepping.md)'s settled shape into the real Daemon/config, Daemon-side only — split off [ticket 41](./41-task-build-stepper-macro-library-ux.md), mirroring [ticket 51](./51-task-land-macro-library-daemon.md)'s split of the Macro half. This ticket is Daemon/config/D-Bus only — no GUI widgets. [Build the Stepper library GUI](./55-task-build-stepper-library-gui.md) is the paired follow-up that consumes this shape. Independent of ticket 51/Macro's schema (a different `Action` variant, a different `Config` field, and — unlike Macro's cutover — purely additive, since `Action::Step`/a Stepper library don't exist at all yet), so it carries no blocking edge on the Macro-side tickets and can be built in either order relative to them.

Scope:

- **Config**: a Stepper-list global library equivalent to `Config.macros` — a named, ordered list of items, each item a type distinct from `Action` and structurally restricted to a single fire-once keyboard key or mouse-button (never a Macro or another Stepper), per ticket 03's Answer. Identity follows the same frozen-slug `StepperId`-from-`name` pattern as `MacroId` (ticket 15), for consistency across the two libraries.
- **Action**: new `Action::Step { stepper: StepperId, direction: Forward | Backward }` — one variant with a direction field, occupying an Input's ordinary Binding slot like Keypress/Macro/Chord do. Net-new addition, no existing shape to cut over.
- **D-Bus**: `CreateStepper`, `RenameStepper`, `DeleteStepper`, and the forward/backward pair-assignment call — assigning a list to a new Input pair silently moves it off its old pair (no reject-at-save step, unlike Chord's overlap rejection; ticket 03 confirmed no ambiguity to prevent here). At most one pair may reference a given list at a time.
- **Runtime cursor**: per-list cursor is Daemon-side-only runtime state, independent of Profile/Layer, never persisted to `config.toml` — always resets to the list's first item on Daemon restart (mirrors `capture_mode`'s live-`GetState()` precedent, ticket 03). Wraps around at either end. Threaded into `GetState()` for the GUI's benefit, the same way `capture_mode` is.
- **Trigger mode**: Fire-once and Hold-to-repeat both apply to a Stepper's forward/backward Bindings via the existing repeat machinery; Toggle must be rejected for `Action::Step` — the first documented Trigger-mode exception (ticket 03's Answer, already reflected in CONTEXT.md's Trigger mode entry).
- **Cross-module plumbing, not GUI widgets**: thread the new wire shape (`steppers`/cursor state in `GetConfig()`/`GetState()`, the new D-Bus methods) through `daemon_client.py`/`daemon_stub.py` so the Rust+Python test suites stay green, per the same precedent [ticket 51](./51-task-land-macro-library-daemon.md) follows from ticket 21. Since `Action::Step` is net-new (no existing GUI code path references it), there is no equivalent stub/disable step needed here — `binding_editor.py`'s Action dropdown simply doesn't offer "Stepper" yet until ticket 55 adds it.

Verified via the Rust + Python test suites — no live hardware needed for a Daemon/config-only ticket.

## Answer

Landed exactly as scoped, no hardware involved. Daemon test count went from 221 to 258 (37 new tests); GUI test count went from 187 to 207 (20 new tests). `cargo build`/`cargo test`/`cargo clippy --all-targets -- -D warnings`/`cargo fmt --check` all clean; `.venv/bin/python -m pytest tests` all green.

### `daemon/src/config.rs`

`StepperId(String)` (`#[serde(transparent)]`, `Display`, `From<String>`/`From<&str>`, no validation — mirrors `MacroId` exactly) and `StepperDef { name, items: Vec<StepperItem> }` added. `StepperItem` is a `"type"`-tagged enum with today's sole `Key { key: KeyCode }` variant — a dedicated type distinct from `Action` (never a Macro or another Stepper, per ticket 03's Answer) built as an enum specifically so a later joystick/controller-button variant can be added without reshaping every existing list. `Config.steppers: HashMap<StepperId, StepperDef>` added as `#[serde(default, skip_serializing_if = "HashMap::is_empty")]`, alongside `macros` — purely additive, since `Action::Step` is net-new. `Action::Step { stepper: StepperId, direction: StepDirection }` added (`StepDirection::Forward`/`Backward`), occupying an Input's ordinary Binding slot exactly like Keypress/Macro/ControllerButton do. `slug_base` was refactored to take a `fallback: &str` parameter (`"macro"`/`"stepper"`) so `unique_stepper_id` shares the exact slug algorithm with `unique_macro_id` rather than duplicating it. `parse()` gained two more validation passes: `ConfigError::UnknownStepper` (a dangling `stepper` reference, mirroring `UnknownMacro`) and `ConfigError::InvalidStepTrigger` (an `Action::Step` Binding whose trigger is `Toggle`, mirroring `InvalidProfileSwitchTrigger`'s shape) — both refuse to start rather than silently accepting an invalid config.

### `daemon/src/executor.rs`

`compile`'s `Action` match gained an `Action::Step { .. } => unreachable!(...)` arm, mirroring `Action::ProfileSwitch`'s existing precedent — a Step's steps depend on Daemon-owned runtime cursor state `executor::compile` has no access to, so it's never reached for real; `dispatch::compile_action` intercepts it first.

### `daemon/src/command.rs`

`State` gained `stepper_cursors: HashMap<StepperId, usize>` — every Stepper library entry's current position, threaded into `GetState()` "for the GUI's benefit, the same way `capture_mode` is" per the ticket's own text. Four new `Command` variants mirroring Macro's exactly: `CreateStepper { name, items }` (returns the derived `StepperId`), `RenameStepper`, `DeleteStepper` (refuses while referenced), `SetStepperItems` (a pure field-write overwrite, added beyond the ticket's literal D-Bus bullet list for the same reason ticket 51 added `SetMacroSteps`-equivalent plumbing — ticket 55's list-editing UX needs a way to persist edits to an *existing* entry, and the narrowest addition that unblocks it without touching any GUI widget is in scope for this ticket's own "cross-module plumbing" bullet).

### `daemon/src/dispatch.rs`

This is where the actual firing semantics live, since they're the one part of Stepper that isn't a mechanical Macro mirror:

- `stepper_cursors: HashMap<StepperId, usize>` is new task-local state in `run()`, alongside `toggles`/`in_flight` — Daemon-side-only, reset to empty (meaning "every list at its first item") on every Daemon start, never touching `config.toml`.
- `compile_action` is a new dispatch step ahead of `executor::compile`: for `Action::Step` it calls `resolve_step` (advances/retreats the cursor with wraparound, defaults a never-touched cursor to index 0, then compiles the newly-selected item into a bare `KeyDown`/`KeyUp` pair — "one motion moves the cursor and fires," ticket 03's Answer's firing semantics, not a separate select-then-confirm); every other Action still goes straight to `executor::compile` unchanged. `fire()`'s existing same-Input overlap guard (a still-in-flight previous firing drops the new event) now also protects the cursor: a dropped firing never calls `compile_action`, so a Stepper never advances without actually firing.
- `SetBinding`'s handler gained an `Action::Step` validation block (unknown `stepper` → `InvalidRequest`, `Toggle` trigger → `InvalidRequest`) mirroring the `Action::Macro`/`Action::ControllerButton` blocks already there, plus `take_stepper_direction_elsewhere` — ticket 03's Answer's "assigning it to a new pair silently moves it off its old one, no reject-at-save step": before the target insert, every *other* Binding anywhere (any Profile/Layer) carrying the same `(stepper, direction)` is removed and folded into the same rollback-on-persist-failure path the target insert already uses. Reassignment is per-direction (matching how the GUI will call plain `SetBinding` once per Input) — no dedicated "pair-assignment" D-Bus method exists, since `Action::Step` occupies an Input's ordinary Binding slot "exactly like Keypress/Macro/Chord do" (ticket 03's Answer) and needs no special call to get there.
- `Command::GetState`'s handler computes `stepper_cursors` from `config.steppers.keys()` (defaulting each to `0`), not from the raw cursor map directly, so a never-yet-stepped library entry still reports a defined position rather than being absent.
- `stepper_references`/`CreateStepper`/`RenameStepper`/`DeleteStepper`/`SetStepperItems` handlers mirror their Macro counterparts exactly.

### `daemon/src/dbus/wire.rs` / `daemon/src/dbus/mod.rs`

`wire.rs` gained `direction_str`/`direction_from_str`, a `"step"` arm on `action_to_dict`/`action_from_dict` (`stepper_id`/`direction` fields), `stepper_item_to_dict`/`stepper_item_from_dict`, `stepper_def_to_dict`/`steppers_to_dict` (folded into `config_to_dict` as a `"steppers"` entry, mirroring `macros_to_dict`), and `stepper_cursors_to_dict` (folded into `state_to_dict`, keyed by `stepper_id` string to a `u64` index). `mod.rs` gained `create_stepper`/`rename_stepper`/`delete_stepper`/`set_stepper_items` `#[interface]` methods mirroring the Macro four, plus matching `#[proxy]` entries and a `TestServer::create_stepper` round-trip helper.

### GUI (`gui/`)

`wire.py` gained `stepper_item_to_variant` and a `"step"` arm on `action_to_variant`. `daemon_client.py`'s `DaemonClient` protocol and `DBusDaemonClient` gained `create_stepper`/`rename_stepper`/`delete_stepper`/`set_stepper_items`. `daemon_stub.py` mirrors the real Daemon precisely: `get_config()`/`get_state()` grew `"steppers"`/`"stepper_cursors"` (the latter defaulting every library entry to `0`); `set_binding` validates an unknown `stepper_id`/a `Toggle` trigger and implements the same silent-move-off-old-pair behavior as the real `SetBinding`; `_slug_base` took the same `fallback` parameter as the Rust refactor. `binding_editor.py` is untouched — `Action::Step` is net-new with no existing GUI code path to stub/disable, exactly as the ticket's own text anticipated; its Action dropdown (`inputs.py`'s `ACTION_TYPES`) simply doesn't offer "Stepper" yet, left for [ticket 55](./55-task-build-stepper-library-gui.md).

### Code review findings, fixed

- **`stepper_cursors` leaked across a delete/recreate cycle**: `Command::DeleteStepper`'s handler only received `stepper_cursors` immutably (needed just for `GetState`), so deleting a Stepper never cleared its runtime cursor. Since `unique_stepper_id` reassigns a freed slug to a brand-new `CreateStepper` call sharing the same derived name, a stale nonzero cursor could leak into that unrelated new entry's very first `GetState()`, violating "always resets to the list's first item." Fixed by widening `stepper_cursors` to `&mut` through `handle_command`/`run()` and clearing the entry on a successful delete. Same widening also let `SetStepperItems` clamp (or drop, if shrunk to zero) a cursor a shrink left stranded past the new end — previously only `resolve_step` clamped it, so `GetState` could report an out-of-range index until the Stepper was next fired. Three new regression tests.
- **`binding_editor.py` would crash opening a key already bound to `Action::Step`**: `build_binding_editor`'s initial `action_dd` selection did `[k for k, _ in ACTION_TYPES].index(starting["type"])` unconditionally — since `ACTION_TYPES` doesn't (deliberately, per this ticket's own scope) list `"step"` yet, this raised `ValueError` the moment any Grid key's Binding was a Step, which this ticket's own Daemon-side change now makes possible (a hand-edited `config.toml`, or any other `com.acheron.Daemon` caller). The ticket text's "no existing GUI code path references it" reasoning held for the Action dropdown's *options* but missed this lookup and `action_summary`'s silent Macro-fallback mislabeling. Fixed narrowly, mirroring ticket 51's own "gate/stub, don't build the real editor" precedent for exactly this situation: `action_summary` gained a `"step"` branch (raw `stepper_id`, no name resolution — same "raw id until the real picker lands" stance ticket 51 took for Macro pre-ticket-52); `build_binding_editor` now falls back to a safe dropdown index and force-disables Save with an explanatory banner whenever the Binding being opened isn't one of `ACTION_TYPES`'s known kinds, so opening (or reflexively saving) the popover can never silently clobber an existing Stepper Binding — Clear still works as an escape hatch, and picking a real Action re-enables Save normally. Three new regression tests, including the crash reproduction.

### Deliberately out of scope

- The real Stepper-library picker/manager UI and item-list editor — ticket 55's job, per this ticket's own Daemon/config/D-Bus-only scope.
- A dedicated "assign pair" D-Bus method — considered and rejected in favor of reusing plain `SetBinding` twice (once per direction), since `Action::Step` needs no special call to occupy an ordinary Binding slot.
