## Question

Design **reusable, named Macro entities**, replacing today's inline-only model where a Macro is a hand-specified Keypress sequence defined directly inside one Binding (`CONTEXT.md:37-38`). Surfaced by the Synapse catalog ([Catalog Synapse's remap/macro feature set](./07-task-catalog-synapse-feature-set.md)): Synapse maintains a separate macro library — a Macro is defined once, then assigned/reassigned to any physical key without rebuilding it — and [Lock the v1.0 feature list](./08-decide-v1-feature-list.md) locked this in scope for v1.0 as a genuine usability gap worth closing.

Settle at least:

- **Storage shape**: does a Macro become a named top-level entity in `config.toml` (e.g. a `[macros.<name>]` table), referenced by id/name from a Binding, alongside (not replacing) the option to still define one inline? Or does every Macro become a library entry, even single-use ones?
- **Identity and editing**: renaming a named Macro, and what happens to Bindings referencing it; deleting a Macro that's still referenced by one or more Bindings.
- **Scoping**: is a Macro library global (shared across all Profiles/Layers) or per-Profile? The Synapse behavior being copied is "swap a macro from one key to another" — decide whether that swap is meant to work across Profile boundaries too.
- **GUI**: a macro-library picker/manager (list existing macros, create/edit/delete, assign to a Binding) — likely a "how should it look/behave" question, consider `/prototype`.
- **Interaction with in-flight tickets**: confirm this doesn't collide with [Design Chord Bindings](./01-decide-chord-bindings.md) or [Design Profile Switch](./05-decide-profile-switch-action.md) — a named Macro should compose as a drop-in replacement for today's inline Macro wherever `Action::Macro` is used, without needing changes to either.

Once resolved, update CONTEXT.md's **Macro** entry to describe the named/reusable shape (currently describes only the inline form).

## Answer

Settled via a `/grilling` session, seven questions total (six + one follow-up), all resolved as recommended, no pushback:

- **Storage shape — every Macro becomes a named library entry, replacing inline entirely.** `Config` gains `macros: HashMap<MacroId, MacroDef>` (new top-level field, alongside `profiles`). `MacroDef { name: String, steps: Vec<MacroStepDto> }` — the step-sequence content moves here unchanged from today's `Action::Macro { steps }`. `Action::Macro { steps: Vec<MacroStepDto> }` becomes `Action::Macro { macro_id: MacroId }` — a Binding no longer carries step content directly, only a reference. No inline/unnamed Macro survives as a second representation: one Action shape, one GUI editing path. Mirrors Stepper's still-unbuilt `Action::Step { stepper: StepperId, .. }` precedent exactly.
- **Scoping — one global library**, shared across every Profile, matching Stepper and matching the actual Synapse behavior being copied (one macro library, reassignable to any key regardless of Profile). No per-Profile macro namespacing.
- **Identity — opaque `MacroId`, decoupled from the editable `name` field.** Concretely: `MacroId` is a slug derived from `name` at creation time (lowercase, hyphenated, numeric suffix appended on collision — e.g. `screenshot-combo`, `screenshot-combo-2`), then **frozen** — it is the `HashMap` key and never changes again, even when `name` is later edited. This is a deliberate departure from `Profile`'s name-is-the-key model (and the rename-cascade `ProfileSwitch { target: String }` needed as a result): a macro library invites much more casual renaming than a Profile does, and freezing the slug at creation means `RenameMacro` is a pure `MacroDef.name` field write — no scan, no cascade, nothing else in `config.toml` changes. Chosen over a random UUID specifically to stay consistent with the codebase's existing plain-`String`-key style (`Profile`'s map, `Input`'s config keys) and because the daemon has no direct `uuid` dependency today (confirmed against `daemon/Cargo.toml` — only a transitive one via `zbus`); a slug also stays legible if a user hand-edits `config.toml`, which the project's release-documentation goal treats as a first-class use case.
- **Reuse cardinality — many-to-one, unlike Stepper.** Any number of Bindings, across any number of Profiles, may reference the same `MacroId` simultaneously — ordinary shared-library reuse, no exclusivity, no "assigning it elsewhere silently moves it" behavior. Stepper's exclusive-single-owner model exists specifically because of its persistent per-list runtime cursor (ticket 03); a Macro is stateless content with nothing to contend over, and many-to-one reuse ("ten keys across three Profiles all fire the same combo") is the actual usability win a shared macro library is for.
- **Deletion while referenced — refuse, like `DeleteProfile`.** `DeleteMacro` returns `CommandError::InvalidRequest` if any Binding anywhere (`base`/`held`/`chords_base`/`chords_held`, any Profile — chords don't exist in code yet, scan whatever Binding maps actually exist at build time, per ticket 34's identical caveat) still references its `MacroId`. Makes a dangling `macro_id` structurally impossible, avoiding any "what does firing a dangling reference do" runtime question — same reasoning [Design Profile Switch](./05-decide-profile-switch-action.md) already landed on for `DeleteProfile`.
- **Composition with in-flight tickets — settled by construction, no changes needed anywhere else.** `Binding = {trigger, action}` is reused unchanged by Chord (ticket 01: "a Chord is just a Binding keyed by a Set<Input>, not a new Action variant"), so a Chord's Action can be the new `Action::Macro { macro_id }` for free — no Chord-side change. Profile Switch is a fully separate `Action` variant (`Action::ProfileSwitch { target }`) untouched by any of the above. A Stepper list item's type already structurally excludes `Action`/Macro entirely (ticket 03) — no interaction to design.
- **GUI — no separate decide-ticket; folds into a shared `/prototype` session with Stepper's library-picker UX.** [Prototype the Stepper library and list-editing UX](./31-prototype-stepper-library-ux.md) — deliberately blocked on this ticket for exactly this reason — is now unblocked and updated to cover both: the shared "library picker: list/create/rename/delete/assign-to-Binding" chrome is the actual object of the UX question, while each construct's item-editing surface (Macro's step sequence vs. Stepper's reorderable list) lives as its own sub-screen within that one session rather than forcing a single shared widget.

Once ticket 31 resolves, spawn the real build ticket (matching the decide → prototype → build pattern used for Chord and Profile Switch) — not spawned here since the GUI shape isn't settled yet.

CONTEXT.md's **Macro** entry updated to describe the named/reusable shape.
