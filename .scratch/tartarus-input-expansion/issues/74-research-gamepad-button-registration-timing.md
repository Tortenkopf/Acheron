Type: research
Status: resolved

## Question

Hardware testing surfaced a real bug: games don't register `Action::ControllerButton` presses bound with Fire-once or Hold-to-repeat Trigger mode — only Analog-repeat reliably registers. The user's own working theory is timing: Analog-repeat's lower-frequency window works, but the same Binding under full-auto-repeat (or a single Fire-once tap) doesn't.

Grounding facts from reading the real code (`daemon/src/executor.rs`, `daemon/src/dispatch.rs`, `daemon/src/injector.rs`), not yet confirmed against actual games:

- `executor::compile()` compiles `Action::ControllerButton { button }` to a **bare `[MacroStep::KeyDown(button), MacroStep::KeyUp(button)]`** — no `MacroStep::Delay` between them, identical treatment to a plain unmodified Keypress (ticket 14's explicit design intent).
- `run_once` (executor.rs) walks that step list with nothing but an `await` on each `injector.set_key_state()` call between Down and Up — no artificial dwell time. Each call round-trips through the injector task's `mpsc`/`oneshot` channel and writes its own immediate `SYN_REPORT` frame (`injector.rs`'s `set_key_state` doc comment: "Each step is its own `SYN_REPORT` frame, same as a real physical key press").
- `dispatch.rs` (~line 1032-1040) handles `(TriggerMode::HoldToRepeat, EventState::Down | EventState::Repeat)` by calling `spawn_fire_once` **again on every kernel autorepeat `Repeat` event** — so a held Hold-to-repeat Controller-button Binding is a train of independent, separately-compiled zero-dwell pulses at kernel autorepeat cadence, not a single continuous Down held for the physical press's duration.
- By contrast, **Analog-repeat already has a deliberate, working, non-zero dwell time**: `dispatch.rs`'s `ANALOG_REPEAT_PULSE_HOLD` constant, tuned and live-verified at **15ms** ([ticket 73](./73-task-verify-and-tune-analog-repeat-on-hardware.md)'s Answer — `evtest`-confirmed ~15ms-wide pulses). This is the one Trigger mode confirmed to register reliably in games, and it's also the one Trigger mode whose pulse isn't zero-width by construction.

This is a strong circumstantial case that the zero-dwell pulse is the actual cause, but per this map's own standing discipline ("confirm empirically rather than assuming — untested claims from reading code have been wrong before on this project"), research it before designing a fix:

- How do real Linux games typically consume gamepad button state from a `uinput`/`evdev` gamepad device — via SDL2/SDL3's event queue (`SDL_JOYBUTTONDOWN`/`UP`, or `SDL_EVENT_GAMEPAD_BUTTON_DOWN`/`UP`), via SDL's per-frame `SDL_GameControllerGetButton()`/`SDL_GetGamepadButton()` polled-state call, or via the legacy `/dev/input/jsX` interface's own `read()` semantics? Which of these could, in principle, ever miss a real but extremely short (sub-millisecond) Down→Up transition, and which couldn't (the kernel's evdev event queue is FIFO and non-lossy under normal operation, so a pure event-consumer shouldn't lose it — pointing at per-frame *state polling* as the likely actual failure mode, not event loss)?
- What's a safe minimum dwell duration to target so a synthesized press reliably survives at least one game-loop poll, across realistic frame rates (16.6ms@60fps, 8.3ms@120fps+, uncapped/variable-rate engines, Proton/Wine-mediated titles if that layer adds its own polling latency)? Does 15ms (Analog-repeat's already-proven value) look adequate, or does the research suggest games commonly need more headroom?
- Does Hold-to-repeat's *train* of independent, separately-fired pulses (one fresh pulse per kernel autorepeat `Repeat` event, not one continuous held Down for the physical press's duration) read to a typical game as "repeated taps" (plausibly the actually-desired behavior for a mashable action button) or does it need to look like one sustained hold instead (e.g. for a "run"/"aim" button a game expects held, not tapped)? This affects whether the eventual fix is "give every pulse a minimum dwell" or "hold the button down continuously for the Input's whole physical press, no repeat pulses at all, for Controller output specifically."

Report findings with enough specificity that [Decide the fix for Fire-once/Hold-to-repeat Controller-button registration](./75-decide-controller-button-pulse-fix.md) can design a concrete fix without re-deriving this.

## Answer

Root cause confirmed mechanically, from primary sources, not just correlated: the culprit is **per-frame polled-state reads**, not evdev/`jsX` event loss. Both kernel queues (`drivers/input/evdev.c`, `drivers/input/joydev.c`) are genuine 64-entry FIFO ring buffers that never drop a same-tick Down/Up pair — loss happens strictly inside userspace *polled-state* accessors. Read straight from SDL3's own source: `HandleInputEvents()` (`SDL_sysjoystick.c`) drains all pending evdev events into a cached `joystick->buttons[]` array once per call (typically once per frame); `SDL_SendJoystickButton` (`SDL_joystick.c`) updates that cache **and separately** pushes a discrete event. A game consuming the **event queue** (`SDL_JOYBUTTONDOWN`/`UP`) gets both transitions no matter how close together they are — structurally immune. A game instead calling `SDL_GetGamepadButton`/`SDL_GetJoystickButton` once per frame reads only the cache's value *after* the drain — a same-drain Down-then-Up is invisible to it even though it genuinely happened. Whether a given game uses one path or the other is invisible from Acheron's side, so the fix must defend against the polled-state case unconditionally.

Proton/Wine doesn't meaningfully change this: XInput has no event-queue alternative at all (`XInputGetState` is a pure snapshot read, by Microsoft's own docs), and DirectInput defaults to polled "immediate" data (buffered mode needs explicit opt-in, default buffer size 0). Windows-side gamepad APIs are polled-state by design, with or without Wine in the chain.

No spec anywhere documents a rigorously-derived minimum dwell — every prior-art figure found is empirically tuned per-project: AntiMicroX's "Press Time" (Linux gamepad remapper, same exact failure mode named in its own docs — "prevent rapid key presses and releases that might be missed by the event loop in a game") defaults to **100ms**; sc-controller's general `Macro.HOLD_TIME` is **10ms** (deliberately lowered to 1ms only for keyboard-text macros, corroborating that gamepad-button dwell needs materially more margin than keyboard dwell). Acheron's own Analog-repeat `ANALOG_REPEAT_PULSE_HOLD` (15ms, live-tuned in ticket 73) sits in the same neighborhood as these — but that 15ms was only ever confirmed at the device/`evtest` level, not against real game polling, and the research flags it as **thin margin at 60fps** (16.6ms/frame): true phase-independent single-poll coverage needs dwell exceeding one full inter-poll period, not merely approximating it. AntiMicroX's 100ms is the closest thing found to a figure deliberately chosen to be safe against *unknown* game engines rather than tuned against specific tested titles.

Left open for [ticket 75](./75-decide-controller-button-pulse-fix.md) to settle: the concrete dwell value (research suggests treating 15ms as unproven-in-the-relevant-sense rather than a safe floor, and weighing headroom toward AntiMicroX's 100ms), and the Hold-to-repeat taps-vs.-sustained-hold question (not resolved by primary sources — game-specific, not discoverable from SDL/kernel/API docs in the abstract).
