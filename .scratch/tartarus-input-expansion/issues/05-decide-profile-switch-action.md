Type: grilling

## Question

Design **Profile Switch** as a third `Action` kind (alongside Keypress and Macro): a Binding whose firing switches the active Profile to a specific target, instead of emitting any keys. The binding popup's Trigger-mode field is disabled/greyed out for it, and the Key/Macro editor is replaced with a Profile selector. Settle at least:

- **Architecture**: does `Action::ProfileSwitch { target: String }` compile into the shared `steps: Vec<MacroStep>` executor at all (it emits no keys, so this seems like a poor fit — see the Daemon data model in `spec.md`'s "Runtime `Binding`"), or does `dispatch.rs` special-case it directly, calling the same internal function the existing `SwitchProfile` D-Bus method already uses? This is the same "does it ride the shared MacroStep pipeline or bypass it" fork the map's Notes already flagged for Chord/Stepper.
- **Trigger-mode semantics**: the GUI greys the field out, but does the persisted `Binding` still carry a `trigger` value (fixed to something like `fire_once` under the hood for schema uniformity), or does the config schema drop the field entirely for this Action kind? Either way, decide what the Daemon does defensively if a hand-edited `config.toml`/a raw `SetBinding` D-Bus call sets `trigger = "toggle"` or `"hold_to_repeat"` on a Profile Switch Binding — reject at validation, or silently only ever fire on `Down` regardless of what's stored?
- **Target reference and staleness**: Profiles are `HashMap<String, Profile>` keyed by name today (no stable id concept exists). A Profile Switch Binding storing `target: String` by name will go stale if that Profile is later renamed or deleted — nothing in the Daemon currently updates by-name references on `RenameProfile`/`DeleteProfile`, because nothing has referenced a Profile by name from inside a Binding before now. Decide: does `RenameProfile` cascade-update any Binding pointing at it, does `DeleteProfile` refuse if a Binding still targets it, or is a dangling reference tolerated (and if so, what does firing a dangling Profile Switch actually do — no-op, D-Bus error, fall back to passthrough)?
- **Self-reference**: binding a control to switch to the Profile that's *already* active — allow as a harmless no-op, or block it (e.g. exclude the current Profile from the GUI's selector)?
- **Layer scope**: bindable from both Base and Held layers, or restricted? (No obvious reason to restrict, given the existing model treats every Binding uniformly across Layers — confirm rather than assume.)
- **Interaction with existing Profile-switch behavior**: switching Profile already force-stops every active Toggle (see `spec.md`'s "Toggle behavior across Layer/Profile switches") — confirm a Profile Switch Binding firing goes through that exact same path with no special-casing needed.
- **GUI**: `binding_editor.py`'s `render_action_editor()`/`on_save()` currently hard-assume exactly two Action kinds (`if kind == "keypress": ... else: ...` covers Macro as the fallback) — this ticket's build work generalizes that to a real N-way branch, adds Profile Switch to `inputs.py`'s `ACTION_TYPES`, and updates `action_summary()`'s two-way assumption too. The profile selector itself is a `Gtk.DropDown` populated from `config["profiles"].keys()`.

## Blocking

Not blocked by, and doesn't block, any other open ticket on this map. Checked directly against `binding_editor.py`: **Decide mouse-button output + GUI picker** only touches the *inside* of the existing `"keypress"` branch (the key/mouse-button picker widget), never the branch structure this ticket generalizes; **Decide key-textfield context-menu items** concerns the `key_entry` widget specifically, which a Profile Switch Binding never has (a dropdown replaces it entirely, not a text entry); Chord and Stepper are both different Binding shapes (multi-Input and two-Input-pair respectively) and are expected to get their own editor surfaces rather than a fourth branch inside this same function. Frontier stays unordered, matching the rest of this map.
