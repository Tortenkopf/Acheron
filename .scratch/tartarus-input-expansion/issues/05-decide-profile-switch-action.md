Status: resolved

## Question

Design **Profile Switch** as a third `Action` kind (alongside Keypress and Macro): a Binding whose firing switches the active Profile to a specific target, instead of emitting any keys. The binding popup's Trigger-mode field is disabled/greyed out for it, and the Key/Macro editor is replaced with a Profile selector. Settle at least:

- **Architecture**: does `Action::ProfileSwitch { target: String }` compile into the shared `steps: Vec<MacroStep>` executor at all (it emits no keys, so this seems like a poor fit — see the Daemon data model in `spec.md`'s "Runtime `Binding`"), or does `dispatch.rs` special-case it directly, calling the same internal function the existing `SwitchProfile` D-Bus method already uses? This is the same "does it ride the shared MacroStep pipeline or bypass it" fork the map's Notes already flagged for Chord/Stepper.
- **Trigger-mode semantics**: the GUI greys the field out, but does the persisted `Binding` still carry a `trigger` value (fixed to something like `fire_once` under the hood for schema uniformity), or does the config schema drop the field entirely for this Action kind? Either way, decide what the Daemon does defensively if a hand-edited `config.toml`/a raw `SetBinding` D-Bus call sets `trigger = "toggle"` or `"hold_to_repeat"` on a Profile Switch Binding — reject at validation, or silently only ever fire on `Down` regardless of what's stored?
- **Target reference and staleness**: Profiles are `HashMap<String, Profile>` keyed by name today (no stable id concept exists). A Profile Switch Binding storing `target: String` by name will go stale if that Profile is later renamed or deleted — nothing in the Daemon currently updates by-name references on `RenameProfile`/`DeleteProfile`, because nothing has referenced a Profile by name from inside a Binding before now. Decide: does `RenameProfile` cascade-update any Binding pointing at it, does `DeleteProfile` refuse if a Binding still targets it, or is a dangling reference tolerated (and if so, what does firing a dangling Profile Switch actually do — no-op, D-Bus error, fall back to passthrough)?
- **Self-reference**: binding a control to switch to the Profile that's *already* active — allow as a harmless no-op, or block it (e.g. exclude the current Profile from the GUI's selector)?
- **Layer scope**: bindable from both Base and Held layers, or restricted? (No obvious reason to restrict, given the existing model treats every Binding uniformly across Layers — confirm rather than assume.)
- **Interaction with existing Profile-switch behavior**: switching Profile already force-stops every active Toggle (see `spec.md`'s "Toggle behavior across Layer/Profile switches") — confirm a Profile Switch Binding firing goes through that exact same path with no special-casing needed.
- **GUI**: `binding_editor.py`'s `render_action_editor()`/`on_save()` currently hard-assume exactly two Action kinds (`if kind == "keypress": ... else: ...` covers Macro as the fallback) — this ticket's build work generalizes that to a real N-way branch, adds Profile Switch to `inputs.py`'s `ACTION_TYPES`, and updates `action_summary()`'s two-way assumption too. The profile selector itself is a `Gtk.DropDown` populated from `config["profiles"].keys()`.

## Answer

Settled via a `/grilling` session, five questions, all resolved as recommended, no pushback:

- **Architecture — dispatch special-cases it, doesn't ride the shared `MacroStep` pipeline.** `executor::compile()`/the injector/the toggle loop stay purely about synthesizing keypresses; they never see `Action::ProfileSwitch`. `Command::SwitchProfile`'s handler body (`dispatch.rs`: `contains_key` check, `mem::replace` on `active_profile`, persist, `stop_all_toggles`, `publish_actuation_snapshot`, reply-before-signal `ActiveProfileChanged` ordering) gets extracted into one shared function. `handle_event` checks `binding.action` for `Action::ProfileSwitch` *before* calling `fire()`/`compile()` and calls that shared function directly instead — which requires widening `handle_event`'s `config: &Config` param to `&mut Config` and threading `config_path`/`actuation_tx` into it (both already available in `run()`'s scope). Reusing the exact same shared function as `Command::SwitchProfile` means the force-stop-every-Toggle path, the actuation-snapshot republish, and the signal ordering all apply automatically — settles "interaction with existing Profile-switch behavior" as a direct consequence, no special-casing needed there.
- **Trigger-mode — reject at validation, not silent runtime coercion.** `Binding` stays one shared struct (`trigger` isn't made `Option`), but `SetBinding` returns `CommandError::InvalidRequest` unless `trigger == TriggerMode::FireOnce` when `action` is `ProfileSwitch`. `load_or_seed` applies the same check to a hand-edited `config.toml` and refuses to start on a violation, consistent with its existing validation of `active_profile`. Mirrors the precedent Stepper already set (Toggle disallowed, "the first exception to Trigger mode's 'applies to every Binding' rule") and avoids a Hold-to-repeat Profile-Switch Binding re-persisting `config.toml` on every autorepeat tick.
- **Target reference — cascade-update on rename, refuse delete if referenced.** `Action::ProfileSwitch { target: String }`, name-keyed like `Profile` itself. `RenameProfile` rewrites every `ProfileSwitch { target }` that pointed at the old name, across *every* Profile's `base`/`held`/`chords_base`/`chords_held` Bindings (not just the renamed Profile's own) — mirrors how it already rewrites `active_profile` when the renamed Profile is active. `DeleteProfile` refuses (reusing `CommandError::InvalidRequest`, same pattern as its existing "cannot delete the active Profile" refusal — no new `CommandError` variant) if any Binding anywhere still targets it. This makes a dangling `ProfileSwitch` reference structurally impossible, so there's no "what happens when a dangling switch fires" runtime branch to design at all.
- **Self-reference — allowed, as a harmless no-op with real incidental utility.** A Binding inside Profile "gaming" targeting `"gaming"` itself just `mem::replace`s the same value, but still runs through the same shared function as every other Profile Switch, so it still force-stops every active Toggle — a "stop all toggles" hotkey via self-targeting, not just a tolerated edge case. The GUI's Profile dropdown does not exclude the Profile currently being edited.
- **Layer scope — unrestricted.** Bindable from both Base and Held, same as every other Action kind; no precedent anywhere in the model for a Layer-restricted Action.

**Fog resolved for free, not spawning a ticket:** the map's "Composition between Stepper and Profile-Switch" fog note is now answered by construction rather than needing its own decision. (a) A Stepper list item is already "restricted to a single fire-once keyboard key or mouse-button, structurally excluding Macro/[Stepper]" (ticket 03) — that exclusion covers Profile-Switch too, so a Stepper item can never be one. (b) A Stepper's forward/backward Binding's Action is fixed to `Action::Step{...}` by definition of being a Stepper Binding — a single Binding has exactly one Action, so "can a Stepper Binding also be a Profile-Switch" isn't a coherent question. (c) Stepper cursor position is explicitly Profile-independent runtime state (ticket 03: "independent of Profile and Layer") and Profile Switch (per the architecture decision above) never touches anything but `active_profile`/Toggles/actuation — so a Profile Switch firing has zero special interaction with any Stepper cursor, by construction, needing no code to enforce.

**GUI implications** (mechanical, following directly from the above, not separately decided): `inputs.py`'s `ACTION_TYPES` gains a `("profile_switch", "Profile Switch")` entry; `binding_editor.py`'s `render_action_editor()`/`on_save()` generalize from `if kind == "keypress": ... else: ...` to a real three-way branch; the Profile Switch branch renders a `Gtk.DropDown` populated from `config["profiles"].keys()` (no exclusion, per self-reference above) in place of the Key/Macro editor slot; `trigger_dd` is set insensitive and `on_save` always submits `fire_once` for this kind, matching the Daemon's validation; `action_summary()`'s two-way assumption gains a third branch (e.g. `"→ gaming"`, no Trigger-mode suffix since it's always Fire-once).
