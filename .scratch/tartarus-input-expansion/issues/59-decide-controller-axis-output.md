## Question

Design **Controller/Joystick axis output** — the fog left after [Design Controller/Joystick output emulation](./14-decide-controller-joystick-output-emulation.md) deliberately scoped its first pass to buttons only. Buttons are now fully built and live-hardware-verified ([ticket 43](./43-task-build-controller-button-picker-ux.md), [ticket 45](./45-task-verify-controller-button-picker-ux-on-hardware.md)), and the legacy `/dev/input/jsX` question is closed (ticket 14 spawned and resolved [research the legacy joystick API](./37-research-legacy-joystick-api-compatibility.md) mid-session — free kernel side effect, zero work needed). This whole strand stays non-blocking for v1.0 per [Lock the v1.0 feature list](./08-decide-v1-feature-list.md).

Guidance already banked by ticket 14's Answer, carry it in rather than re-deriving: **target real depth directly from the start** — `depth_tx` (per-key 0-255 depth, live since tickets 22/26/27) is already flowing through a running Daemon, so an axis model built against real depth rather than a digital press/release placeholder won't need a later rewrite. Fall back to press/release step-increment only when `capture_mode` is Digital.

Settle at least:

- **Which axes**: what physical Inputs map to virtual axis output? Candidates raised on the map: the thumbstick as an analog stick (it's currently 4 discrete evdev directions, not itself a depth-bearing Input — decide whether/how it becomes an analog `ABS_X`/`ABS_Y` pair, or whether it stays digital-only and only grid-key depth feeds axes), and a grid key's depth as a trigger axis (`ABS_Z`/`ABS_RZ`-style, mirroring `BTN_TL2`/`BTN_TR2`'s analog-trigger convention on real gamepads).
- **Deadzone/curve model**: does axis output need its own deadzone and response curve (linear vs. curved), analogous to Analog-repeat's fixed deadzone and linear rate curve ([ticket 20](./20-decide-analog-repeat-trigger-mode.md))? Decide whether to reuse that precedent directly or diverge, and why.
- **`ABS_*` code choices**: which standard Linux Gamepad Spec `ABS_*` codes the second `uinput` device (already advertising the `BTN_GAMEPAD`/Trigger-Happy/`BTN_DPAD_*` range per ticket 14) should add, and whether the dpad's existing 4-discrete-button shape should become a real `ABS_HAT0X`/`ABS_HAT0Y` instead now that axes are in scope.
- **New Action shape**: does axis output need a new `Action` kind (alongside the existing `Action::ControllerButton`), and if so what does assigning "this Input drives this axis" look like at the Binding level — an Input firing a Binding is normally a discrete event, while an axis is a continuous value, so decide whether this fits the existing Binding/Trigger-mode shape at all or needs something structurally different.
- **GUI surface**: whether axis assignment needs its own picker/editor surface distinct from the existing controller-button picker ([ticket 43](./43-task-build-controller-button-picker-ux.md)), even at a design-only level — the concrete UX can spawn its own prototype ticket rather than being decided here.

This is the first ticket of what may be its own open-ended strand — expect prototype/task tickets to graduate from it once the shape narrows, per the button strand's own decide → prototype → build pattern (tickets 14 → 38 → 43 → 45). Don't try to spec the whole implementation in this session.

## Answer

Settled over a full grilling session, against ticket 14/17/19/20/26's existing precedents. Full shape:

1. **Scope**: only grid keys get axis output — they're the only Input with real Depth. The thumbstick stays fully digital/button-only (already fully covered by `Action::ControllerButton`, ticket 43); its 4 discrete evdev directions carry no depth to drive an axis with, and a "fake" analog stick synthesized from digital on/off input would only ever produce fixed full-deflection values, no functional gain over 4 buttons.

2. **Structural shape — not a new `Action`, a new parallel per-Layer map**: axis assignment is a first-order fork, decided independently per (Layer, Input) — the same physical grid key may be Axis-assigned on Base and carry an ordinary Binding (or Chord membership) on Held. Modeled as `Profile.axis_base` / `Profile.axis_held: HashMap<Input, AxisTarget>`, mirroring `chords_base`/`chords_held`'s existing precedent of a parallel per-Layer map alongside `Binding`, not a new `Action` variant — Trigger-mode has no coherent meaning for a continuous value, which is the tell it doesn't belong in the `Action` enum. An Input present in a Layer's axis map is structurally excluded from that Layer's `bindings_*` map *and* from Chord membership on that Layer (a Chord needs a discrete Down/Up transition to fire on, which an Axis-assigned key no longer produces).

3. **Axis catalog — 17 targets per grid key**, all on the existing single gamepad-identity `uinput` device (no second device, no `BTN_JOYSTICK`-range buttons — confirmed via research that a single device may freely mix `BTN_GAMEPAD` buttons with HOTAS-style `ABS_*` axes with no OS/SDL classification conflict; the extra axes are simply invisible to SDL's Gamepad-specific mapping step but fully available via the raw Joystick API, which flight/racing titles use directly):
   - **5 unsigned** (single key, 0→max Depth, no polar opposite): Left Trigger (`ABS_Z`), Right Trigger (`ABS_RZ`), Throttle (`ABS_THROTTLE`), Gas (`ABS_GAS`), Brake (`ABS_BRAKE`).
   - **6 signed axes × 2 independently-assignable halves = 12 targets**: Left Stick X/Y, Right Stick X/Y (`ABS_X`/`Y`/`RX`/`RY`), Rudder (`ABS_RUDDER`), Wheel (`ABS_WHEEL`) — each split into a +/- pick so two independent keys can cover both halves.
   - `ABS_HAT0X`/`Y` dropped from scope entirely: a joystick hat is conventionally a 3-state digital signal (kernel models it as `EV_ABS` for historical reasons only), not a continuous value — it belongs on the digital/Binding branch as a future bindable target, not here. Moved to the map's fog.
   - Deliberately **not** pursuing a distinct flight-stick/HOTAS device identity (separate `BTN_JOYSTICK`-range buttons or a third `uinput` device): the existing `BTN_TRIGGER_HAPPY1-40` allowlist already covers "extra unlabeled buttons" as well as a curated `BTN_JOYSTICK` set would, Steam Input's own docs explicitly place flight sticks/racing wheels outside its remapping scope, and a second device identity is a second uinput lifecycle in the supervisor for no real functional gain — same "functional coverage over faithful device mimicry" reasoning ticket 37 used for legacy `jsX`.

4. **Deadzone/curve — diverges from Analog-repeat (ticket 20) deliberately**: no separate axis-specific deadzone or curve setting. Reuses the key's own already-tunable Actuation/Release points (tickets 17/19/26) as the axis's start/end thresholds: 0 output below the Release point, linear ramp to raw Depth above the Actuation point. Ticket 20's Analog-repeat needed a *fixed* deadzone specifically to preserve the key's whole travel range for its rate curve; axis output has no such constraint, and reusing the user's own configured trigger point avoids a second, redundant per-key threshold. The Tartarus Pro's keys also have no mechanical "wobble" (unlike heavy Hall-effect sticks) that would otherwise motivate a real deadzone. Curved (non-linear) response deferred to post-1.0 fog.

5. **Runtime conflict resolution**: two keys assigned to opposite halves of one signed axis (e.g. Right Stick X+ and X-) — whichever key is already actively outputting suppresses the other; a real stick can't move two directions at once. Two keys assigned to the *same* half of one axis (allowed freely, no reject-at-save, mirrors `ControllerButton`'s existing no-restriction precedent) — resolved by taking the greater of the two Depths when both are pressed, since neither is physically contradictory the way opposite polarity is.

6. **Digital Capture mode fallback**: press/release step-increment (guidance already banked forward from ticket 14's Answer) — exact step size left as a build-time-tuned constant, same precedent as Analog-repeat's four TBD constants.

7. **Forward-looking architecture note, banked but not built now**: implement axis resolution internally as its own seam — `(Depth, edge_event) → axis_value` — even though "Live/linear" (this ticket's only designed variant) is the only resolver in the first build. This is what makes a future **Sticky/latching mode** (the axis value latches to the highest Depth reached since the key's last discrete press, resetting to 0 only on the next press — a user-raised idea, e.g. for simulating a throttle detent) a small second-resolver addition later rather than a rewrite. Sticky mode itself is deferred to the map's fog, not designed here.

8. **GUI**: deliberately not designed in this session, per the ticket's own scope. Structurally, the per-key Binding editor needs an Axis/Digital fork ahead of today's Action-kind/Chord-membership options. The concrete look/interaction spawns its own prototype ticket, mirroring the button strand's decide → prototype → build → verify pattern (14 → 38 → 43 → 45).

9. **CONTEXT.md**: gained a new **Axis assignment** glossary entry, and the **Controller** entry's stale "not-yet-designed" axis note was corrected to point to it.

No code changes this session (design only). Spawned [Prototype the axis-assignment GUI](./60-prototype-axis-assignment-ux.md). Fog added to the map: Sticky/latching axis mode; `ABS_HAT0X`/`Y` hat-direction support on the digital/Binding branch.
