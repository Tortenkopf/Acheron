## Question

Given [Research gamepad button registration timing](./74-research-gamepad-button-registration-timing.md)'s findings and the confirmed root-cause hypothesis (`Action::ControllerButton`'s Fire-once/Hold-to-repeat pulse is a zero-artificial-dwell `KeyDown`→`KeyUp` pair, unlike Analog-repeat's already-working, deliberately-timed `ANALOG_REPEAT_PULSE_HOLD` (15ms)), decide the actual fix:

- Should a minimum pulse-hold duration be enforced generically wherever a bare Down/Up pair is compiled (`executor::compile`/`executor::keypress_steps`), or scoped only to `Action::ControllerButton` — Keypress/mouse-button output hasn't been reported broken, and keyboard/mouse input paths on the receiving end (kernel input subsystem read by a desktop app) aren't necessarily bound by the same per-frame-poll failure mode a game's gamepad handling might be?
- Where does the fix live structurally: a `MacroStep::Delay` auto-inserted between the Down and Up steps `compile()` emits for `Action::ControllerButton` (reusing the existing Macro-step machinery, simplest change), or a lower-level change in `run_once`/`injector.rs`? Does it need to be a genuinely enforced dwell (blocking the Up write until the duration elapses) or is queuing a delayed Up sufficient?
- What happens to Hold-to-repeat specifically: does each per-repeat pulse just gain the same minimum dwell (independent taps, cadence otherwise unchanged), or does research's finding about "taps vs. sustained hold" call for a structural change — e.g. holding the Controller-button's `KeyDown` continuously for the physical Input's whole press (suppressing the intermediate `KeyUp`/`KeyDown` pairs kernel autorepeat currently drives) rather than pulsing at all? A structural change here is a bigger build than a dwell constant and needs to be sized as such.
- Should this reuse `ANALOG_REPEAT_PULSE_HOLD` as a shared named constant/primitive (avoiding a second hardcoded "15ms" living in two unrelated places), or does research suggest Fire-once/Hold-to-repeat actually need a different value than Analog-repeat's tuned figure?
- Confirm the fix's blast radius: `Action::ControllerButton` fires through the same shared `executor::compile`/`run_once` path regardless of whether it's a direct Binding, a Chord's Action, or (per ticket 03's Stepper scope) never reachable from Stepper — so a fix at the `compile()` level covers Chord for free; call out explicitly if that's not desired.
- Pick the concrete dwell value and any other numeric constants the design needs, informed by research rather than guessed blind (mirroring this map's own standing discipline, and unlike ticket 39's admitted "shipped blind, tuned later" precedent for Analog-repeat — tune this one with research backing before it ships, since verifying the fix needs an actual game running, not just `evtest`/`jstest`).

Record the settled design as this ticket's Answer; spawn a build task (and its own hardware-verify follow-up, tested against a real game this time, not just `evtest`/`jstest` — [ticket 45](./45-task-verify-controller-button-picker-ux-on-hardware.md)'s device-level-only verification is what let this gap ship unnoticed) per this map's standing build→verify precedent.

## Answer

Settled via `/grilling`, against ticket 74's research. Two structurally different fixes, both scoped to `Action::ControllerButton` only (Keypress/mouse-button/Macro output — mouse buttons are `Action::Keypress` with a `BTN_*` `KeyCode`, not a separate Action — are completely untouched by either):

- **Fire-once**: gains a genuine dwell. Fire-once's whole point is a canned pulse decoupled from the physical hold duration, so there is no real duration to mirror — a minimum has to be invented, exactly like AntiMicroX/sc-controller's own tap-dwell constants (research §4). Fix lives as a `MacroStep::Delay` auto-inserted between the `KeyDown`/`KeyUp` steps `compile()` emits for `Action::ControllerButton` — reuses existing Macro-step machinery, no new primitive. The dwell is a **blocking** `await tokio::time::sleep(...)` before the `KeyUp` write (mirrors `ANALOG_REPEAT_PULSE_HOLD`'s existing pattern in `dispatch.rs`), not a detached/queued Up — a detached Up would need its own task outliving the firing handle, complicating ticket 33's force-release-on-physical-Up semantics for no benefit here. **Value: 35ms**, a new named constant (e.g. `CONTROLLER_BUTTON_FIRE_ONCE_PULSE_HOLD`), deliberately *not* shared with `ANALOG_REPEAT_PULSE_HOLD` — the two dwells are tuned for unrelated jobs (15ms was tuned against Analog-repeat's own rate-curve/cadence on real hardware in ticket 73; 35ms is chosen fresh against the polling-survival problem, a bit over double a 60fps frame interval since research §6 established that true phase-independent single-poll coverage needs dwell exceeding one full inter-poll period, not merely approximating it). Sharing the constant would silently couple two unrelated tuning knobs. Not final-tuned against a real game yet — see the verify task below.

- **Hold-to-repeat**: no dwell at all, and a different mechanism entirely. A real gamepad button doesn't autorepeat in hardware — held down, it just stays down — so "look like what a real gamepad sends" (the standard this session settled on for `Action::ControllerButton` output) means Hold-to-repeat needs to mirror the *actual* physical press duration, which is already available and always many multiples of a frame interval — no invented number needed. Fix is dispatch-level, not compile()-level: on `TriggerMode::HoldToRepeat` with `Action::ControllerButton`, fire `KeyDown` once on the physical Down, **ignore** the intervening kernel-autorepeat `Repeat` events entirely (no re-fire), and fire `KeyUp` once on the physical Up — reusing the existing `ActiveToggle`-style "hold a key down across two separate trigger events" mechanism (today used for Toggle) rather than inventing new architecture. This is a net simplification versus a dwell-per-pulse fix: no timer, no constant to tune, and it's immune to the polling problem by construction rather than by tuning margin.

- **Blast radius**: both fixes apply uniformly whether `Action::ControllerButton` fires via a direct Binding or a Chord's Action (same shared `executor::compile`/`run_once`/dispatch path). Stepper is unaffected — it can never reach `Action::ControllerButton` (ticket 03's settled scope).

- **Explicitly deferred, not decided here** (no release yet, no users to protect, so no urgency): whether Fire-once/Analog-repeat should even remain *allowed* for `Action::ControllerButton` at all going forward, and whether a new Auto-fire/Turbo mode (the discrete-tap-train behavior Hold-to-repeat is losing above) is worth building as its own mode — spawned as [ticket 78](./78-decide-controller-button-trigger-mode-applicability.md). Also spawned, per the user's own follow-up: whether mouse-button output should get the same sustained-hold Hold-to-repeat treatment (enabling drag) — [ticket 79](./79-decide-mouse-button-sustained-hold-drag.md).

Spawned [Build the Controller-button pulse fix](./76-task-build-controller-button-pulse-fix.md) and [Verify the Controller-button pulse fix on hardware, against a real game](./77-task-verify-controller-button-pulse-fix-on-hardware.md).
