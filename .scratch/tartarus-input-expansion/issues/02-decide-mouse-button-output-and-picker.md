Type: grilling

## Question

Finalize mouse-button output support **and** full keyboard-key output support, then design the GUI's key/action picker covering both. (Scope broadened during charting — a separate idea about binding modifier/function/navigation/lock keys turned out to be the exact same underlying question this ticket already owned: what the picker exposes and how. Folded in here rather than split into a sibling ticket, so "which keys/buttons does the picker expose" has one answer, not two.) Settle at least:

- **Verify, don't assume — mouse buttons**: the map's Notes record that the Daemon likely already supports targeting a mouse button (`BTN_LEFT`/`BTN_RIGHT`/`BTN_MIDDLE`/etc.) from `Action::Keypress`/Macro steps with zero code changes, based on reading `injector.rs`/`input.rs` and the `evdev` crate's `FromStr`. Confirm this empirically against the real, connected Tartarus Pro/Daemon before treating it as settled — hand-edit a `config.toml` Binding to `key = "BTN_LEFT"` (or via `busctl SetBinding`) and confirm a real left-click actually lands.
- **Verify, don't assume — non-alphanumeric keys**: today's GUI key field is a bare `Gtk.Entry` defaulting to `"KEY_A"`, with nothing hinting what else is valid, which reads as "can't be bound" even though `Action::Keypress.key`/`MacroStepDto::KeyDown`/`KeyUp` are plain `evdev::KeyCode` with no allow-list, and evdev's `FromStr`/`Display` (the `evdev_enum!` macro backing `KeyCode`) parses every variant name uniformly — not just letters/digits. Confirm live that each of these already round-trips end-to-end through `config.toml`/D-Bus/real output: modifier keys used as a *main* key (`KEY_LEFTCTRL`/`RIGHTCTRL`, `KEY_LEFTSHIFT`/`RIGHTSHIFT`, `KEY_LEFTALT`/`RIGHTALT`, `KEY_LEFTMETA`/`RIGHTMETA`), lock keys (`KEY_CAPSLOCK`, `KEY_SCROLLLOCK`, `KEY_NUMLOCK`), function keys (`KEY_F1`…`KEY_F24`), the navigation cluster (`KEY_UP`/`DOWN`/`LEFT`/`RIGHT`, `KEY_HOME`, `KEY_END`, `KEY_PAGEUP`, `KEY_PAGEDOWN`, `KEY_INSERT`, `KEY_DELETE`), and misc (`KEY_TAB`, `KEY_ESC`, `KEY_PRINT`, `KEY_PAUSE`, …).
- **Edge case — modifier used as both the main key and an active modifier flag**: a Binding with `key = KEY_LEFTCTRL` *and* `modifiers.ctrl = true` presses `KEY_LEFTCTRL` twice before releasing it twice (`executor.rs`'s `keypress_steps` treats them as unrelated). Decide whether this needs guarding (e.g. the picker disables/clears a modifier checkbox that matches the selected main key) or is harmless enough to leave as-is (a second `KeyDown` on an already-down key is normally a no-op at the evdev/uinput level) — confirm which, don't just assume harmless.
- **Modifier-combination interaction (mouse buttons)**: does holding a modifier while a mouse-button Action fires make sense (e.g. Ctrl+Click), and if so does it reuse the exact same `Modifiers` mechanism as a keyboard Keypress?
- **Macro steps**: do `MacroStepDto::KeyDown`/`KeyUp` already work identically for mouse buttons and non-alphanumeric keys (they should, per the same `evdev::KeyCode` typing), or is there a wrinkle worth surfacing?
- **Scope button/key set**: which mouse buttons does the GUI actually expose — Left/Right/Middle plus Side/Extra (`BTN_SIDE`/`BTN_EXTRA`), or a narrower set? Is any keyboard key excluded from being a bindable *target* for desktop/compositor-reserved reasons, or is the full range fair game (as it already implicitly is for letters/digits today)?
- **GUI picker design**: replace (or augment) the free-text `Gtk.Entry` key field in `binding_editor.py` with a graphical picker covering the *entire* keyboard (not just letters/digits — group modifiers, function keys, navigation cluster, lock keys, misc, sensibly) plus mouse buttons. This is very likely a "how should it look/behave" question — use `/prototype`.

Out of scope for this ticket (per the map): cursor movement, synthetic scroll output, capturing from a real external mouse.
