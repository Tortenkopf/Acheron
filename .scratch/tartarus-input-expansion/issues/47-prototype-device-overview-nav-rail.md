## Answer

Prototyped on `prototype/47-device-overview-nav-rail` (real production widgets — `build_profile_sidebar`, `make_input_button`, `build_action_table` — driven by the real `daemon_stub.DaemonStub`, seeded with real Bindings; ticket 31's actual winning Library screen reused verbatim; the Chords list mocked fresh since only its placement, not its internal shape, was ever the open question). Four structurally different variants, round 1: **all three rejected outright** — informative, not inconclusive: the user's reaction named exactly what was wrong (rail-as-a-separate-column, icons, and an Action Table getting more real estate all felt off), sharp enough to skip a second 3-way spread and go straight to a round-2 refinement.

**Round 2 (variant D) won**, refined again over a second round of live reaction into the final design:

- **No rail column at all.** The left Profile sidebar stays exactly as it is in the live GUI today (`build_profile_sidebar`, unchanged, permanent) — none of round 1's instinct to fold Profile switching into a new rail survived contact with the user's own daily use.
- **Action Table is cut outright**, not relocated — the user's own real-world verdict, from actually using the software: they never needed it once the real key/mouse-button picker (ticket 42) landed inline in the per-key Binding editor, and an expanded row now just reads as crowded, not useful.
- **"Grid" / "Library" — plain text, no icons** — become a two-button switcher sitting where Action Table's toggle/`table_sidebar` used to be, fully replacing the content area on selection. A `Gtk.Separator` (a plain light-grey hairline) sits between this switcher and whatever it's switching, so the destination-level chrome reads as visually distinct from the per-destination content below it.
- **The Chords list is always visible beside the grid, no toggle** — round 1's Action-Table-toggle-shaped "Chords ▸/◂" slot was cut in round 2 once the user pointed out there's room to just show it permanently, avoiding a rescale on every open/close. It only exists at all while the Grid destination is selected (never while Library is), per the ticket's own "Chords isn't a clean peer of Library" framing — Chord *recording* is grid-native (ticket 30) and has nothing to point at once the grid isn't showing.
- **The real `build_layer_bar`** (Base/Held tabs + Mode-key-role toggle) sits above the grid inside the Grid destination, with real spacing added specifically between it and the grid — round 1's version crowded the two together.
- **A real GTK4 bug, caught and fixed live**: the Profile sidebar visibly widened while the Library destination was showing. Root cause — `Gtk.Box`'s expand-propagation: a profile row's `switch_btn` sets `hexpand=True` three container levels down, and GTK infers the sidebar itself wants to expand from that, so it competed for whatever horizontal slack the *other* destination's content left unclaimed — different amounts for Grid (whose big grid+thumbstick natural width claims most of it) versus Library (which claims less). Fixed with an explicit `sidebar.set_hexpand(False)`, which overrides the inferred propagation; measured directly (walking the real allocated widget tree) at 197px in both destinations after the fix, versus visibly drifting before it.

Prototype: `prototype/47-device-overview-nav-rail` (`gui/acheron_gui/prototype_47_device_overview_nav_rail.py`, `gui/prototype_47_device_overview_nav_rail.py`; also carries a copy of ticket 31's `prototype_31_stepper_macro_library_ux.py`, reused as an import rather than reprototyped). Variants A/B/C are kept on the branch as rejected reference points; the switcher defaults to D.

None of this is wired into the real `device_overview.py` yet.
