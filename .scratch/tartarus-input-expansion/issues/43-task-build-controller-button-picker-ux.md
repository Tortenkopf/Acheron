## Answer

Landed both halves for real, no open design questions left to resolve — everything built matches ticket 14's and ticket 38's settled shapes exactly, with two robustness additions beyond their literal scope (both consistent with existing precedent, not new decisions):

**Daemon** (`config.rs`, `input.rs`, `injector.rs`, `executor.rs`, `dispatch.rs`, `dbus/wire.rs`):
- `Action::ControllerButton { button: KeyCode }` added to the `Action` enum; `executor::compile` gives it the same bare down/up pair as a plain Keypress (no modifiers), exactly ticket 14's "same shape as a Keypress, only the target device differs."
- `input::is_gamepad_button`/`gamepad_button_codes()` (`daemon/src/input.rs`) are the one source of truth for the curated 57-entry allowlist (13 named `BTN_GAMEPAD` buttons + 4 `BTN_DPAD_*` + `BTN_TRIGGER_HAPPY1`-`40`) — both the second `uinput` device's advertised capability set (`injector::build_gamepad_device`, wired into `main.rs` alongside the existing device, sharing the same ticket-28 startup-race retry) and the injector's own keyboard-vs-gamepad write routing (`sink_for`, checked per `KeyState`/`ForceRelease` write) read from this single function, so the two can never drift apart. `injector::spawn` now takes both sinks; every test call site updated (`sink.clone(), sink.clone()` where gamepad routing isn't under test — the same shared `RecordingSink` catches both, since `Clone` shares the underlying `Arc`).
- Allowlist validation added in **two** places, mirroring `ProfileSwitch`'s exact precedent (`SetBinding` in `dispatch.rs` *and* `load_or_seed`/`parse` in `config.rs`, both via `ConfigError`/`CommandError::InvalidRequest`) rather than the one place ticket 43's own text named. Reason found while implementing, not speculative: the gamepad `uinput` device only advertises the curated 57 codes (unlike the keyboard device's "advertise everything" precedent — ticket 14 deliberately scoped it narrower), so a hand-edited `config.toml` naming an out-of-allowlist code would hit an `EINVAL` on `emit()` at fire time, which is fatal to the *entire* injector task (both devices, per `main.rs`'s "any of the three top-level tasks finishing is fatal" design) — not a graceful per-Binding failure. Guarding `parse()` too closes that off at startup instead, the same protection `InvalidProfileSwitchTrigger` already gives the hand-edit path.
- `dbus/wire.rs` gained the `"controller_button"`/`"button"` wire tag pair, mirroring every other Action variant.
- 12 new Rust tests (199 total, was ~188 pre-session): allowlist coverage (`gamepad_button_codes` count, named+range acceptance, keyboard/mouse rejection), `compile` shape, injector routing (two `RecordingSink`s, asserting a gamepad code never reaches the keyboard sink and vice versa), `SetBinding` accept/reject, `parse()` accept/reject, and a wire round-trip. Clippy clean, `cargo fmt --check` clean on every line this session touched (three pre-existing unrelated `executor.rs` formatting diffs confirmed present on `main` before this session, left alone).

**GUI** (`controller_picker.py` new, `binding_editor.py`, `inputs.py`, `wire.py`, `app.py`):
- `controller_picker.build_inline_controller_picker` ports ticket 38's winning variant A (Gamepad Diagram) geometry unchanged (`_PAD_LAYOUT`/`_OFFSET_Y`, already live-reaction-refined over the prototype's three rounds) against the real 57-entry catalog (asserted equal to the Daemon's count at import time) instead of the prototype's hand-listed one, plus the separate collapsed "Extra buttons (Trigger-Happy 1-40)" grid.
- **One deliberate deviation from ticket 38's literal prototype shape**: the *outer* summary is always shown inline, with no "▸ Change" collapse/expand toggle — the prototype had one. Reason: this exact picker mounts inside the identical per-key modal `Gtk.Window` container ticket 44 already found, live, on real hardware, silently breaks that shape for the sibling key/mouse-button picker (a Popover's positioner has nowhere to grow into for most grid buttons; a nested Popover off a MenuButton mispositions instead). `key_picker.build_inline_key_picker` already carries that fix; this picker applies it from the start rather than reproducing a known bug and needing its own ticket-44-style hardware session to rediscover it. The Extra-buttons grid keeps its *own* nested show/hide toggle (mirrors `key_picker`'s "Show F13-F24 ▸"), since that only grows an already-inline panel, not the outer collapse-to-nothing shape that broke.
- Wired into `render_action_editor`: `ACTION_TYPES` gains `("controller_button", "Controller Button")`; the Action dropdown branch mounts the picker under a "Button" labeled row; `on_save` builds `{"trigger": ..., "type": "controller_button", "button": ...}` with the Trigger dropdown left fully selectable (unlike Profile Switch, no Fire-once lock — ticket 14 confirmed every Trigger mode applies unchanged). `action_summary()` renders `"Btn: <label>  [<trigger>]"`. No suggested-default chip, no freedom note — exactly ticket 38's round-3 answer, carried straight through.
- Macro step KeyDown/KeyUp values are *not* wired to this picker (out of scope per ticket 38's own GUI scope list, which only names the top-level Action dropdown) — but need no Daemon change either: `MacroStepDto::KeyDown`/`KeyUp` already parse any `KeyCode` string unrestricted (no allowlist on Macro steps, only on `Action::ControllerButton` itself), and the injector's new code-based routing means a hand-authored Macro step carrying a `BTN_*` gamepad code already fires on the correct device today, with zero further work — confirms ticket 43's "no new step-type work" claim rather than assuming it.
- CONTEXT.md's existing Controller entry (added in ticket 14) checked against everything built here — accurate as written, no picker-specific addendum needed, per the ticket's own "likely doesn't" prediction.
- 12 new Python tests (121 total, was 108 pre-session): a standalone `test_controller_picker.py` (8 tests: summary label, always-inline reachability, picking a named/extra button, highlight refresh, `button_css_class`, catalog-size assertion) plus 4 `test_binding_editor.py` integration tests (save round-trip, Trigger dropdown stays selectable, `action_summary`, bound-button grid label) and a `test_wire.py` round-trip test.

**Live-hardware verification not done this session** — no physical device access, matching ticket 42/44's own precedent for the sibling picker (an unattended session touching a user's live input/GUI state unasked is out of scope).
