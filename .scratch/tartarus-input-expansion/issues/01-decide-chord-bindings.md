## Question

Design **Chord** Bindings — an Action triggered when two-or-more physical Inputs are pressed simultaneously, distinct from any Binding those same Inputs carry individually. Settle at least:

- **Config representation**: how a Chord's set of physical Inputs is stored (e.g. a Binding keyed by a set of `Input`s alongside the existing per-`Input` maps) and how it composes with `Layer`/`Profile` scoping (is a Chord Base/Held-scoped the same way an ordinary Binding is?).
- **Simultaneity detection**: what counts as "simultaneous" — a timing window between the first and last Input going down, or exact same evdev event batch? What happens on near-miss timing?
- **Precedence with single-Input Bindings**: if `grid_r1c1` and `grid_r1c2` are each individually bound *and* a Chord exists on both together, what fires when both go down — does the Chord suppress the individual firings entirely, fire after them, or something else? What about a partial press (one goes down, then the other) versus release order?
- **Trigger-mode applicability**: do Fire-once/Hold-to-repeat/Toggle all apply to a Chord's Action the same way they do to an ordinary Binding?
- **Size limits**: is a Chord capped at 2 Inputs, or open-ended?
- **GUI**: how a user defines/"records" a Chord — press-and-hold the physical controls live, or a multi-select picker? (Consider `/prototype` if this needs a look-and-feel answer, not just a data-model one.)

Once resolved, add the full **Chord** entry to CONTEXT.md (currently just a reserved name — see the map's Notes).

**Correction from [Lock the v1.0 feature list](./08-decide-v1-feature-list.md)**: Synapse's "four virtual thumbstick-diagonal bindings" (Up-Right/Up-Left/Down-Left/Down-Right, each firing when two adjacent thumbstick-direction switches are pressed together) is not a separate feature to build — the thumbstick's four cardinal directions are already ordinary bindable Inputs (`CONTEXT.md:22`), so a diagonal is just an ordinary Chord over two of them. No new engineering; when this ticket resolves, add the thumbstick diagonals as a worked example/test case (and confirm the GUI affordance for defining a Chord makes this discoverable) rather than scoping it separately. Bonus: this also means simultaneous Keypress/mouse-button output for a diagonal is already achievable today via a Macro with near-zero delay between steps, independent of Chord landing at all.

## Answer

Settled via a three-round grilling session against the real `config.rs`/`dispatch.rs`/`binding_editor.py`/`command.rs` code (nothing built yet):

- **Size**: open-ended (`Set<Input>`, N≥2) — a `BTreeSet<Input>`/`HashMap` keys the same regardless of member count, and capping at 2 would forecloses future chords (e.g. Mode key + two grid keys) for no implementation savings.
- **Config representation & Layer/Profile scoping**: a Chord is Base/Held-scoped exactly like an ordinary Binding, for consistency with CONTEXT.md's existing Binding definition. Concretely: `Profile.chords_base: HashMap<BTreeSet<Input>, Binding>` and `Profile.chords_held: HashMap<BTreeSet<Input>, Binding>`, alongside the existing per-`Input` `base`/`held` maps. `Binding = {trigger, action}` is reused unchanged — a Chord is "just a Binding keyed by a Set<Input> instead of one Input," not a new Action variant, so `Action` stays `Keypress | Macro`.
- **Simultaneity detection**: a fixed **50ms** timing window between the first and last member Input going down, hardcoded as a Rust constant in `dispatch.rs` — not a persisted `Config` value or a v1.0 user setting. Exact-same-evdev-batch was ruled out: per tickets 13/16, this device reports event-driven, one report per change, so two physically-simultaneous presses essentially never land in one read. 50ms was chosen as a typical "simultaneous input" tolerance, comfortably above the device's own ~1ms per-change latency and small enough not to feel laggy on a suppressed individual Binding.
- **Precedence with single-Input Bindings**: the Chord suppresses the individual firings entirely on completion. The first member's Down is held (not fired) for up to the window; if the rest of the set joins in time, only the Chord's Action fires and neither individual Binding ever does. If the window elapses first, the pending member's individual Binding fires retroactively (delayed by the window) — this is a real, accepted latency cost on every Chord member's individual Binding, not just a corner case. Releasing any one member ends the Chord's held/toggle state as a whole; the remaining member(s) don't fall back to their individual Bindings until they're released and re-pressed fresh.
- **Trigger-mode applicability**: unchanged — Fire-once/Hold-to-repeat/Toggle all apply to a Chord's Action exactly as they do to an ordinary Binding. Hold-to-repeat's "held" state = all chord members still down; Toggle's stop condition = the same full chord going down together again, not any single member.
- **Overlapping Chord definitions**: designed away rather than arbitrated at runtime. A given Input may belong to at most one Chord per Profile/Layer — the GUI rejects (at save time) any new/edited Chord whose Input set intersects an existing Chord's set in the same Profile/Layer, with an explanation. This eliminates the ambiguity that open-ended size + suppress-on-completion would otherwise create (e.g. Chord A = `{grid_r1c1, grid_r1c2}` and Chord B = `{grid_r1c1, grid_r1c3}` racing on `grid_r1c1`).
- **GUI recording**: confirmed direction is live physical-press capture — the user presses the N physical Inputs on the device and the GUI records that set as the Chord's membership. The capture step records *membership only*, not timing — the 50ms window is not something the recording gesture measures or sets. The exact interaction (how "waiting for inputs" is shown, confirm/cancel, editing an existing Chord's membership) is a genuine look-and-feel question with no GUI precedent to copy, so it's deferred to a spawned prototype ticket rather than decided here — see [Prototype the Chord recording UX](./30-prototype-chord-recording-ux.md). That prototype also carries a debug-only adjustable slider for the 50ms window, to help converge on the right constant empirically; the slider itself never ships — v1.0 keeps the window hardcoded (see Simultaneity detection above).
- **Diagonal worked example**: falls out for free, no special-casing needed. The thumbstick's four diagonals (Up-Right/Up-Left/Down-Left/Down-Right) are ordinary 2-member Chords over adjacent cardinal-direction Inputs, using the exact same model above. The spawned prototype ticket should confirm the live-capture GUI affordance makes this discoverable.
- **Composition with analog depth** (partial answer to the "Not yet specified" analog-composition fog): a Chord made of grid keys uses each member's own already-existing per-Input actuation point (ticket 17) — Chord doesn't introduce new depth semantics, it just watches each member's already-thresholded Down/Up transitions. The broader Chord/Stepper composition questions remain fog until Stepper's own ticket settles.

**New D-Bus/Command surface implied** (mechanical consequence, not a fresh decision): `SetBinding`/`ClearBinding` are keyed by a single `Input` and can't represent a Chord. Chord needs its own pair — e.g. `Command::SetChordBinding { inputs: BTreeSet<Input>, layer, binding, reply }` / `ClearChordBinding { inputs, layer, reply }` — plus the overlap-check at save time (GUI-side, against a `GetConfig()` snapshot, or Daemon-side inside the new `SetChordBinding` handler; left to whichever ticket actually builds this).

CONTEXT.md's Chord entry has been added (see Language § Configuration); Keypress's `_Avoid_` line updated to drop "reserved."

## Correction (from [Prototype the Chord recording UX](./30-prototype-chord-recording-ux.md))

The original "**Overlapping Chord definitions**" rule above — an Input may belong to at most one Chord per Profile/Layer — breaks this ticket's own thumbstick-diagonal worked example: Up needs to sit in both Up-Left and Up-Right, Left in both Up-Left and Down-Left, and so on. Caught live while building ticket 30's recording-flow prototype and tracing through what happens when a user actually tries to define all four diagonals.

Corrected rule, settled via a short live grilling exchange: **an Input may belong to any number of Chords.** The original rule was overcautious — two Chords that merely *intersect* (share one member, each has at least one member the other lacks — exactly the diagonal shape) are not actually ambiguous under the existing "fire on first full completion within the window" dispatch model: pressing Up+Left can only ever satisfy Up-Left, since Right isn't down. The only case that stays genuinely ambiguous is a **subset/superset relationship** between two Chords' member sets (e.g. `{Up,Left}` vs `{Up,Left,ModeKey}`) — completing the smaller one is indistinguishable from being partway into the larger one. That narrower case is still rejected at save time, same "GUI rejects with an explanation" precedent as before, just a narrower trigger condition (one member set fully containing the other, not merely sharing an Input).

This was deliberately generalized to **every** Input, not scoped to the thumbstick specifically — a per-Input special case would need separate logic in both `dispatch.rs` and the GUI's conflict check for no real benefit, since the corrected rule is no more permissive than necessary anywhere else either. Considered and rejected: silently allowing subset/superset pairs too ("so what, the superset Chord just never fires") — rejected because an unreachable Chord fails completely silently with no signal to the user, the same "structurally impossible, not just tolerated" standard applied elsewhere on this map (e.g. [Design Profile Switch](./05-decide-profile-switch-action.md)'s dangling-reference refusal).

No change to simultaneity detection, precedence, trigger-mode applicability, or Config representation — `Profile.chords_base`/`chords_held: HashMap<BTreeSet<Input>, Binding>` already supports arbitrary overlapping member sets with no schema change; only the save-time validation predicate changes (from "sets intersect" to "one set contains the other"). CONTEXT.md's Chord entry updated to match.
