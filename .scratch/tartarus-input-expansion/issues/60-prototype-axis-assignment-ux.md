## Question

Prototype the **axis-assignment GUI** — the concrete look/interaction [Design Controller/Joystick axis output](./59-decide-controller-axis-output.md) deliberately left undesigned.

Ticket 59 settled the underlying shape: axis assignment is a new, parallel per-(Layer, Input) concept, mutually exclusive with that Layer's Binding/Chord-membership for the same grid key, offering one of 17 axis targets (5 unsigned single-key axes + 6 signed axes split into independently-assignable +/- halves). It reuses the key's existing Actuation/Release-point UX (tickets 19/26) as the axis's start/end thresholds — no new deadzone control needed.

Open UX questions to prototype against, per ticket 59's Answer:

- **The Axis/Digital fork**: the per-key Binding editor currently opens straight into the Action-kind dropdown (Keypress/Controller Button/Macro/Stepper/Profile Switch). Where does "this key is an axis instead" sit relative to that — a toggle above the existing dropdown, a 6th dropdown entry that swaps the whole editor body, something else? Only grid keys are eligible; the editor for every other Input (Mode key, thumbstick, wheel) doesn't need this fork at all.
- **Picking one of 17 targets**: how is the catalog presented — flat categorized list (Triggers / Sticks / Pedals), a diagram similar to ticket 38's winning Gamepad Diagram variant (now needs axis regions, not just buttons), something else? Signed axes need the two independently-assignable halves (+/-) to read clearly as two separate picks, not one.
- **Cross-key awareness**: when picking a target already claimed by another key (same signed half, or its opposite half), does the picker surface that (a toast, an inline note, nothing — since ticket 59 settled this is *allowed*, not rejected)? Mirrors the precedent in [ticket 55](./55-task-build-stepper-library-gui.md)'s steal-toast for a similar "not rejected, but worth surfacing" case.
- **Chord/exclusion visibility**: Device Overview's grid-click Chord-recording flow (ticket 30/40) needs Axis-assigned Inputs on the active Layer to be excluded from selection. How does the grid communicate "this key can't join a Chord right now" at a glance?

Per ticket 59's own precedent (14 → 38 → 43 → 45), a winning variant here spawns a build ticket, then a hardware-verification ticket.

## Answer

Three structurally different variants prototyped (Toggle+Diagram, 6th-dropdown+Category-list, Segmented+Group-then-value) on `prototype/60-axis-assignment-ux` (not `main`). **Variant B won outright on the fork mechanism and grid treatment**, but the user then asked for variant A's diagram picker in place of B's flat list, and refined that combination over four more rounds of live reaction. Final settled shape, one answer per open question:

- **The Axis/Digital fork (B's answer)**: "Axis" is simply a 6th entry in the existing per-key Action-kind dropdown (Keypress / Controller Button / Macro / Stepper / Profile Switch / **Axis**) — offered only when the Input is a grid key; non-grid Inputs (Mode key, thumbstick, wheel) never see the option at all, rather than seeing it disabled. Trigger-mode locks insensitive with a tooltip ("Axis output has no Trigger mode") the moment Axis is picked, mirroring Profile Switch's existing `trigger_dd.set_sensitive(kind != "profile_switch")` lock in the real `binding_editor.py` — no new mechanism needed, same precedent reused for a second kind.
- **Picking one of 17 targets (A's diagram, refined)**: a hand-built diagram, not a flat list — Left Stick and Right Stick each render as a 4-direction cross (Y+ / X− / X+ / Y−) with the stick's name directly above it and nothing in between; **Left Trigger sits beside the Left stick (to its left) and Right Trigger beside the Right stick (to its right)** — round 5's placement, after round 3's "trigger as an extra row above the stick" was tried and reverted. A horizontal rule sits below the two sticks, under which the remaining 7 targets split into two named groups by genre rather than by signed/unsigned shape: **Driving** (Wheel +/− with Gas and Brake inline beside it) and **Flight** (Rudder +/− with Throttle inline beside it) — round 4 collapsed each group from stacked rows to one inline row to save vertical space. Signed axes' two halves are always separate, individually clickable buttons (the stick cross's four arms; the +/− pairs), never a single control — satisfying the "read as two separate picks" requirement directly by construction. One shared purple accent (`#8e44ad`) highlights whichever target is currently picked, tying every "this is the current axis pick" affordance together visually.
- **Cross-key awareness (A's answer)**: picking a target already claimed by another key shows a one-shot banner reusing the real app's existing `.toast` convention (ticket 55's Stepper steal-toast — same CSS class, same blue tint) at the top of the picker panel: "Also assigned to `<key>` — allowed, both keys will drive this axis." Purely informational, never blocking — ticket 59 §5 already settled that sharing a target is allowed, not rejected, so the toast only ever confirms what just happened.
- **Chord/exclusion visibility (B's answer)**: Axis-assigned grid keys carry an **always-visible** purple diagonal-stripe CSS treatment on Device Overview's grid — visible at all times, not only while selecting Chord members, so the same purple accent that marks a picked target in the editor also marks an Axis-assigned key on the grid. The button itself stays fully clickable at all times (unlike variant A's grey-out-during-selection answer); clicking a striped key while selecting Chord members surfaces an inline error line ("`<key>` is Axis-assigned — can't join a Chord") instead of toggling it into the selection or disabling the button outright.

No code changes to `main` this session — design only, per this ticket's own scope.
