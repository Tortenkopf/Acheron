## Question

Build the real Chord recording flow in `binding_editor.py`/`device_overview.py`, from [Prototype the Chord recording UX](./30-prototype-chord-recording-ux.md)'s settled variant A design (round 3), against the real Daemon and Tartarus Pro. Scope:

- **Device Overview**: clicking any Input toggles it into an in-progress Chord selection (no separate recording dialog); a status line names the current selection; a "Binding →" button below the grid, disabled until ≥2 Inputs are selected and no subset/superset conflict exists with an existing Chord; "Clear selection" backs out.
- **Chords list**: lands in the reserved slot [ticket 48](./48-task-build-device-overview-nav-rail.md) already built and [ticket 49](./49-task-verify-device-overview-nav-rail-on-hardware.md) live-verified — `build_chords_placeholder()` in `device_overview.py`, always-visible beside the grid on the Grid destination only (Library shows neither grid nor this slot, confirmed live; no toggle/visibility wiring left to build, only the placeholder's content to replace). That slot: a panel/section listing every defined Chord (`{members} → {action summary}`), each with an "Edit" button (pre-loads its members into the selection and its Trigger/Action into the Binding dialog) and, per the prototype's late addition, a plain row-click that previews the Chord's members on the grid (distinct highlight color) without entering edit mode.
- **Binding dialog**: a small modal reusing the existing Trigger/Action editor UI (ticket 01/02's already-settled shape — Keypress and Macro both apply, not just Keypress like the prototype's stand-in) for the Chord's own Binding.
- **Overlap conflict UX**: when the current selection's member set is a subset or superset of an existing Chord's, disable "Binding →", name the conflicting Chord in the status line, and offer an "Edit conflicting Chord" affordance that jumps straight to it — see [ticket 01's amended Answer](./01-decide-chord-bindings.md) for the exact (narrower-than-originally-designed) conflict rule: an Input may belong to any number of Chords; only a subset/superset relationship between two Chords' member sets is rejected.
- **Daemon/D-Bus**: `Command::SetChordBinding { inputs: BTreeSet<Input>, layer, binding, reply }` / `ClearChordBinding { inputs, layer, reply }`, `config.rs`'s `Profile.chords_base`/`chords_held: HashMap<BTreeSet<Input>, Binding>` (per ticket 01), and the save-time subset/superset conflict check — decide during the build whether it lives GUI-side (against a `GetConfig()` snapshot) or Daemon-side (inside the new handler); either is consistent with existing precedent (`SetActuationPoint` validates Daemon-side, profile-name conflicts are checked GUI-side via `build_name_prompt_popover`'s error surface).
- **`dispatch.rs`**: the actual Chord-detection state machine — the ~50ms window (hardcoded constant, not a `Config` value), tracking all currently-down Inputs and, for each Chord definition whose members are all a subset of the current down-set within the window, firing it and suppressing each member's individual Binding for that press; the pending member's individual Binding fires retroactively if the window elapses without completion. Multi-membership means an Input's press may need to be evaluated against *every* Chord containing it, not just one.
- **The thumbstick-diagonal worked example**: verify live that all four diagonals (Up+Right, Up+Left, Down+Left, Down+Right) can coexist and each fires correctly and independently.

The prototype's own debug-only window-tuning slider does not ship — the ~50ms constant is fixed in `dispatch.rs` per ticket 01, informed by whatever the prototype/earlier tickets converged on empirically (nothing was actually tuned live yet; use 50ms as the starting point and adjust only if live testing on the real device shows it's wrong).

Live-hardware verification (defining a Chord, editing one, triggering overlap rejection, firing all four diagonals, Trigger-mode behavior on a Chord) is in scope for this ticket, not deferred to a separate verify ticket — matches this map's "resolving a ticket means actually building and testing against the real, connected Tartarus Pro" discipline.

## Answer

Built end to end — Daemon, D-Bus surface, and GUI — and live-verified as far as this session's tooling allows (see the gap noted at the end). 285 Rust + 258 Python tests, all green; `cargo clippy`/`cargo fmt --check` clean.

**Daemon (`daemon/src/`):**
- `config.rs`: `ChordKey` (a `BTreeSet<Input>` wrapper; `Input`/`Direction`/`WheelEvent` gained `PartialOrd`/`Ord` solely so it can live in one) marshals to/from TOML as a `+`-joined, sorted-by-`Input`'s-own-`Ord` string, mirroring `Input`'s own hand-written string-key convention. `Profile.chords_base`/`chords_held: HashMap<ChordKey, Binding>` mirror `base`/`held` exactly. `parse()`'s cross-cutting validation (ProfileSwitch-must-be-FireOnce, ControllerButton allowlist, dangling Macro/Stepper ids) now scans Chords too via a shared `profile_all_bindings` iterator, plus a new `ConfigError::InvalidChordProfileSwitch` — a Chord's Action can never be `ProfileSwitch` (nowhere to run a Profile switch from inside `fire_chord`, which has no `&mut Config`).
- `command.rs`/`dbus/mod.rs`/`dbus/wire.rs`: `Command::SetChordBinding`/`ClearChordBinding` and their `set_chord_binding`/`clear_chord_binding` D-Bus methods, mirroring `SetBinding`/`ClearBinding` but keyed by `inputs: BTreeSet<Input>` (≥2 members). `GetConfig()` serializes `chords_base`/`chords_held` (always present, even empty, matching `held`'s own convention). `dispatch::handle_command`'s `SetChordBinding` validates via a new shared `validate_binding` helper (extracted out of `SetBinding`'s own inline checks — no drift between the two), rejects a Chord `inputs.len() < 2` or a `ProfileSwitch` Action outright, and rejects a subset/superset conflict against any *other* existing Chord on the same Layer (`chord_conflict`, ticket 01's amended Answer — a plain intersection, like the thumbstick diagonals, is fine).
- `dispatch.rs` — the actual Chord-detection state machine (`ChordState`/`ChordWindow`, `CHORD_WINDOW = 50ms`): a chord-eligible Down opens (or joins) a window, firing every Chord definition whose members become fully satisfied (`fire_chord`, `chord_in_flight`/`chord_toggles` mirroring `fire`'s own `in_flight`/`toggles` but keyed by `ChordKey`); Repeat re-fires an active Hold-to-repeat Chord for any member; an early release or the window elapsing fires the still-pending member's own individual Binding retroactively (`fire_individual_retroactively`, handling `ProfileSwitch` itself since a *member's own* Binding, unlike a Chord's, can be anything); releasing *any* member force-releases/stops every Chord it's currently part of, regardless of Trigger mode. `chord_state.claimed` routes an Input's later Repeat/Up back through the Chord path even after it stops being freshly chord-eligible, so a member that resolved individually never gets mistaken for still-pending. Ticket 03's stepper-direction exclusivity ("at most one owner of a given `(stepper, direction)` at a time") now also covers Chords, both directions (`take_stepper_direction_elsewhere`/`_from_chords`), and `macro_references`/`stepper_references` (guarding `DeleteMacro`/`DeleteStepper`) now scan Chords too.

**GUI:** `binding_editor.py`'s Trigger/Action editor core was extracted into `build_action_and_trigger_fields` (returns the widget plus a `get_binding()` reader) and is reused verbatim by a new `build_chord_binding_dialog` — the small modal ticket 01 asked for, with Profile Switch filtered out of its Action dropdown (the Daemon always rejects it for a Chord; no point offering a guaranteed-failing option). `device_overview.py` gained the real Chords section (`build_chords_section`) beside the grid: a "Select Chord members" toggle (see the design decision below), a status line, "Binding →"/"Clear selection"/"Edit conflicting Chord", and the Chords list (row click previews on the grid, "Edit" re-enters selection preloaded, "×" clears). Every device button (grid, thumbstick, Mode key, wheel — a Chord's members are open-ended) gets live Chord styling/tooltips via `_chord_button_style`. `daemon_client.py`/`daemon_stub.py` gained matching `set_chord_binding`/`clear_chord_binding`.

**A real design gap, resolved mid-build via a direct question to the user:** the real grid buttons already open the per-Input Binding editor on click, but the prototype had *every* click toggle Chord selection with no other mode. Asked the user; they picked an explicit "Select Chord members" toggle — off (default) behaves exactly as before, on reroutes grid clicks to selection. **Separately, and not run past the user**: ticket 01's own Answer specifies the recording gesture as "live physical-press capture" — the user presses the real Inputs on the device — not a GUI mouse click. Building that would need a new Daemon-side signal stream (no such thing exists yet) reporting raw physical presses to the GUI while a capture mode is active, well beyond this ticket's D-Bus surface. What's shipped instead is the prototype's own click-to-toggle simplification, permanently adopted for the real GUI rather than only standing in for "no hardware in this environment" as originally scoped. This is a real narrowing from ticket 01's decided design, not just an implementation detail — flagged here for the user to weigh in on if it matters; live physical-press capture would need its own ticket.

**Code review (medium effort) caught 7 findings; 6 were real bugs, now fixed with regression tests:** a stale-but-finished `chord_in_flight` entry was permanently excluding a FireOnce/HoldToRepeat Chord from ever completing again after its first firing (`release_chord` never removes the entry, matching `fire`'s own `in_flight` convention — the completion filter needed to check `is_finished()`, not bare presence); `macro_references`/`stepper_references` didn't scan Chords, so `DeleteMacro`/`DeleteStepper` could leave a dangling reference that then failed `load_or_seed` (refused to start) on the next Daemon restart; `SetChordBinding` never enforced stepper-direction exclusivity in either direction; the GUI's Chord-edit save set the new membership before clearing the old key, so growing/shrinking membership by containment made the still-present old Chord spuriously conflict with itself; `daemon_stub.py`'s Chord key sorted alphabetically instead of by `Input`'s real `Ord`, diverging from the real Daemon for any Chord mixing Input variant kinds (e.g. Mode key + a grid key); and the Chord dialog offered Profile Switch despite the Daemon always rejecting it. Left as accepted, documented duplication (not fixed): `fire_chord` mirrors `fire`'s Trigger-mode dispatch by hand rather than a shared generic, and the subset/superset conflict rule is independently implemented in Rust, `daemon_stub.py`, and `device_overview.py` — both flagged by the review as drift risks, but each already carries a comment cross-referencing the others, matching this repo's own "three similar lines beats a premature abstraction" standard used throughout.

**Live-hardware verification not done this session**, the same recurring gap tickets 26/42/47/48 all hit: no GUI-automation/screenshot tooling exists in this environment (confirmed directly — `grim`/`slurp`/`gnome-screenshot`/`import`/`scrot` are all absent, and `main.py` always wires the real `DBusDaemonClient`, no stub-launch mode), and defining a Chord needs a human physically pressing device keys.
