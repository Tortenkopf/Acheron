# 06 — GUI polish: grid-button sizing, default-binding labels, Mode-key width

**What to build:** Three independent Device Overview (`gui/acheron_gui/device_overview.py`) fixes. User-specified with no open design question, so this is a direct build, not a grilling ticket (matches the previous map's convention for tickets that carry execution with nothing left to decide).

1. **Grid button height fits 4 wrapped lines.** `make_input_button`'s label (`f"{input_label(inp)}\n{action_summary(binding)}"`, on a `Gtk.Label(wrap=True)`) can render taller than the button's `set_size_request(w=76, h=52)` — that call sets only a *minimum* size, not a cap, so a long wrapped label pushes the button taller than its requested height today. Increase `h` enough to comfortably fit 4 wrapped lines at the current font/padding. Before hardcoding "4," verify live what the actual longest `action_summary()` string produces today (worst case: all four modifiers + a long key name + a Trigger-mode tag — `f"{chord}  [{TRIGGER_SHORT[...]}]"`) rather than trusting "seems to be the maximum" as exact. Note for whoever builds the other open tickets on this map (Chord, Profile Switch, Stepper all add new/longer summary shapes): this height may need revisiting once those land.
2. **Unbound buttons show their default (passthrough) output, not just the word "passthrough."** `action_summary(None)` today returns the bare string `"passthrough"` for any unbound Input — it doesn't say what that Input's stock keycode actually is. Add the real default label (the digit/letter/arrow the grid key or thumbstick direction emits stock) alongside "passthrough." This needs a per-Input default-keycode table on the GUI side; decide whether to hardcode a small Python table (mirroring `daemon/src/input.rs`'s `key_code_for_input` — a fixed hardware fact, same source the old map's "Enumerate physical inputs" ticket already captured) or try to fetch it from the Daemon (no existing D-Bus call exposes passthrough defaults — `GetConfig`/`GetState` don't carry them). Hardcoding is almost certainly right; note the choice explicitly rather than silently picking it.
3. **Mode key actually renders at the same width as the diamond/key-20 buttons.** `mode_btn` is already *requested* at `w=52` (matching the thumbstick diamond's lobes and key-20's paddle, all `52×40` — not the grid's `76×52`), but its single-word `"Mode"` label likely isn't wrapping, so natural-size growth renders the button wider than that 52px minimum despite the request (`set_size_request` only sets a floor). This is a hypothesis, not a confirmed diagnosis — check it live against the running GUI before fixing. If confirmed, constrain the label's actual rendered width (e.g. `Gtk.Label`'s `max-width-chars`/`width-chars`, or forcing character-level wrap) so it genuinely renders at the diamond-lobe width, then re-center it above the diamond's top lobe. `device_overview.py`'s own comment says the Mode key "sits directly above the diamond's top lobe (Left, per the rotation)" — confirm that's what "the left button" in the request refers to before treating it as settled, since the rotated diamond's screen positions don't match its Input names 1:1 (top lobe = `thumbstick_left`).
   - Related, not explicitly requested — flag rather than silently bundle in: the `.mode-key` CSS (`border-radius: 999px`) only renders a true circle when width equals height; at today's `52×40` it's a stadium/pill shape, not the "circular Mode key" the spec (from the previous map) actually calls for. Worth a one-line note to the user when this ticket is picked up, since fixing #3 touches the same box model.

No design decision blocks this ticket — build directly, confirming the three "verify live" notes above against the running GUI rather than assuming the code-reading alone is right.

## Answer

Built and verified live via a real GTK4 window on the actual display (`gui/acheron_gui/device_overview.py`, `binding_editor.py`, `action_table.py`, `inputs.py`), driven by `DaemonStub` rather than the real Daemon/hardware — this ticket is pure GUI layout with no capture-path or D-Bus surface involved, so a real rendering pipeline against realistic bindings *is* "the running GUI" for this ticket's own discipline; no physical Tartarus Pro interaction was needed.

**All three items landed, but not as originally hypothesized** — live verification (actual screenshots, not just code-reading) overturned the "just raise `h`" framing:

1. **Grid button height.** The real defect wasn't lack of vertical room — it was that plain `wrap=True` (Gtk.Label's default `WORD` mode) can't break an unbroken run like `"Ctrl+Shift+Alt+Super+F12"` (no spaces) at all, so it forces the button/Grid-cell *wider* instead of taller (confirmed live: a real Gtk-WARNING demanding 308px for a 4-modifier Binding). Fixed with `wrap_mode = Pango.WrapMode.WORD_CHAR` as a fallback — but explicitly *not* paired with `max-width-chars` to also cap width: a first pass tried that (calibrated to 7/4 chars to hold grid/mode-key buttons at their nominal 76/52px), and a live screenshot showed it mid-word-splitting the ordinary word "passthrough" into "passthr"/"ough" on *every* unbound key — clearly not "comfortably," so that cap was dropped. `h`'s default rose from 52 to 99 anyway: even ordinary short bindings need 3 wrapped lines (input number/"Mode"/arrow, the chord, the `[trigger]` tag), and 99 was measured live to comfortably cover every case tried, including the deliberately pathological one (`Ctrl+Shift+Alt+Super+KBDILLUMTOGGLE  [hold]`) — which, with width now free to grow instead of the label being squeezed, needs only 3 lines too, not the 7 a width-capped rendering would have needed. Width is left as a floor rather than a hard cap (`set_size_request`'s existing behavior, unchanged) — a Grid column/row occasionally growing past 76×99 for an extreme Binding is accepted, matching this ticket's own note about `h`.
2. **Default labels.** `action_summary()` now takes the `Input` (`inp`) and shows its stock output via a new hardcoded `INPUT_DEFAULT_LABEL` table in `inputs.py`, mirroring `daemon/src/input.rs`'s `GRID_KEYS`/`key_code_for_input` (no D-Bus call exposes this, confirmed) — e.g. `"Q"`, `"Alt"`, `"↓"`, `"Middle Click"`. `wheel_scroll_up`/`_down` (no discrete keycode there, matching `key_code_for_input`'s own `None`) get `"Scroll"`, naming the actual behavior instead. Both call sites (`device_overview.py`, `action_table.py`) updated to pass `inp`. **Revised after initial resolution, on the user's live reaction to the built GUI**: the original design (per this ticket's own text) wrapped the default in `"passthrough (X)"`; the user flagged, and this session agreed, that the qualifier word should go entirely — it's jargon the user doesn't need, it's what forced the smaller 52px buttons to overflow at all, and it's actively *wrong* once a running Daemon is in analog mode (the grid's 20 keys are synthesized from depth thresholds then, not literal evdev passthrough — only Mode key/thumbstick/wheel stay on raw evdev regardless of capture mode, a distinction the label had no cheap way to make). Dropping the word sidesteps needing that distinction at all: the label just names the actual default output, true either way. `INPUT_DEFAULT_LABEL` now covers all 28 entries in `ALL_INPUTS` (verified programmatically), so `action_summary` indexes it directly rather than falling back on a missing-key default. Not touched: `binding_editor.py`'s "Clear (passthrough)" button inside the editing popover — a different surface (full-width, not space-constrained) the user didn't flag; worth revisiting for the same wording reason if it comes up.
3. **Mode-key width.** Confirmed live, but the diagnosis in the ticket text was wrong: it isn't that `"Mode"` fails to wrap — it's that `Gtk.MenuButton`'s default `halign` is `FILL`, so inside `stick_col` (a plain `Gtk.Box`, not a `Gtk.Grid`) it stretches to the box's full cross-width (the diamond's ~160px) regardless of its own `set_size_request(52, …)` floor. A live screenshot showed an unbound Mode key rendering as a wide oval, not a small circle. Fixed with `btn.set_halign(Gtk.Align.CENTER)` in the shared `make_input_button` (a no-op for every other caller, since Grid cells already size to their own column) — the Mode key now renders at its own natural width and is centered correctly: measured live at 0.5px offset from `thumbstick_left`'s ("the top lobe") center, i.e. aligned. No extra re-centering code was needed once the stretch was fixed. The flagged-not-fixed CSS finding stands as noted in the ticket body: `.mode-key`'s `border-radius: 999px` still only renders a true circle when width equals height, and with real content (e.g. `"Mode\nCtrl+A  [hold]"`, measured 112×50px) it's a stadium/oval, not a circle — worth a follow-up if the "circular Mode key" spec detail matters, not fixed here since it wasn't one of the three requested items.

**Not requested, not touched:** the same halign/wrap findings apply structurally to any future button placed directly in a `Box` rather than a `Grid` (key-20's paddle already benefits for free, since it shares `make_input_button`) — no action needed, just noting the mechanism now exists in the shared function.

83 Python tests green both before and after the wording revision (no existing test asserted the exact `"passthrough"` string, so neither pass needed test updates). No Rust changes. Unbound buttons now render noticeably tighter than the first pass — e.g. the diamond's lobes and Mode key sit at their nominal 52px whenever unbound, only growing for a genuinely heavy Binding — since the removed qualifier word was itself the main driver of the original overflow.
