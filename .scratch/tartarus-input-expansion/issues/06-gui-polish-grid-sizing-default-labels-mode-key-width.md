# 06 — GUI polish: grid-button sizing, default-binding labels, Mode-key width

**What to build:** Three independent Device Overview (`gui/acheron_gui/device_overview.py`) fixes. User-specified with no open design question, so this is a direct build, not a grilling ticket (matches the previous map's convention for tickets that carry execution with nothing left to decide).

1. **Grid button height fits 4 wrapped lines.** `make_input_button`'s label (`f"{input_label(inp)}\n{action_summary(binding)}"`, on a `Gtk.Label(wrap=True)`) can render taller than the button's `set_size_request(w=76, h=52)` — that call sets only a *minimum* size, not a cap, so a long wrapped label pushes the button taller than its requested height today. Increase `h` enough to comfortably fit 4 wrapped lines at the current font/padding. Before hardcoding "4," verify live what the actual longest `action_summary()` string produces today (worst case: all four modifiers + a long key name + a Trigger-mode tag — `f"{chord}  [{TRIGGER_SHORT[...]}]"`) rather than trusting "seems to be the maximum" as exact. Note for whoever builds the other open tickets on this map (Chord, Profile Switch, Stepper all add new/longer summary shapes): this height may need revisiting once those land.
2. **Unbound buttons show their default (passthrough) output, not just the word "passthrough."** `action_summary(None)` today returns the bare string `"passthrough"` for any unbound Input — it doesn't say what that Input's stock keycode actually is. Add the real default label (the digit/letter/arrow the grid key or thumbstick direction emits stock) alongside "passthrough." This needs a per-Input default-keycode table on the GUI side; decide whether to hardcode a small Python table (mirroring `daemon/src/input.rs`'s `key_code_for_input` — a fixed hardware fact, same source the old map's "Enumerate physical inputs" ticket already captured) or try to fetch it from the Daemon (no existing D-Bus call exposes passthrough defaults — `GetConfig`/`GetState` don't carry them). Hardcoding is almost certainly right; note the choice explicitly rather than silently picking it.
3. **Mode key actually renders at the same width as the diamond/key-20 buttons.** `mode_btn` is already *requested* at `w=52` (matching the thumbstick diamond's lobes and key-20's paddle, all `52×40` — not the grid's `76×52`), but its single-word `"Mode"` label likely isn't wrapping, so natural-size growth renders the button wider than that 52px minimum despite the request (`set_size_request` only sets a floor). This is a hypothesis, not a confirmed diagnosis — check it live against the running GUI before fixing. If confirmed, constrain the label's actual rendered width (e.g. `Gtk.Label`'s `max-width-chars`/`width-chars`, or forcing character-level wrap) so it genuinely renders at the diamond-lobe width, then re-center it above the diamond's top lobe. `device_overview.py`'s own comment says the Mode key "sits directly above the diamond's top lobe (Left, per the rotation)" — confirm that's what "the left button" in the request refers to before treating it as settled, since the rotated diamond's screen positions don't match its Input names 1:1 (top lobe = `thumbstick_left`).
   - Related, not explicitly requested — flag rather than silently bundle in: the `.mode-key` CSS (`border-radius: 999px`) only renders a true circle when width equals height; at today's `52×40` it's a stadium/pill shape, not the "circular Mode key" the spec (from the previous map) actually calls for. Worth a one-line note to the user when this ticket is picked up, since fixing #3 touches the same box model.

No design decision blocks this ticket — build directly, confirming the three "verify live" notes above against the running GUI rather than assuming the code-reading alone is right.
