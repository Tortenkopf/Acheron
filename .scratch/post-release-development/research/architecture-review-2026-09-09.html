Architecture review — Acheron

2026-09-09 · branch dev

Six deepening opportunities in the Rust Daemon, ranked. The aim throughout: turn shallow modules — interface nearly as wide as the implementation — into deep ones, so bugs concentrate in one place (locality) and one interface change reaches every call site (leverage). Nothing here re-opens an ADR.

Orienting fact: the large line counts are test tonnage. dispatch.rs is ~1,150 lines of implementation and ~5,850 of tests (83%); config.rs, stage.rs, dbus/mod.rs the same. The friction is shape, not size — and the test tonnage is itself a symptom (candidate 4).

1 · Give the four runtime engines one DepthEngine interface

Files
daemon/src/dispatch.rs:888–904, 1030, 1085, 1122, 1007
daemon/src/stage.rs · axis.rs · analog_repeat.rs · chord.rs
.scratch/tartarus-dual-stage-keys/issues/05-interaction-sweep.md
Problem
Four engines interpret Config-aware Depth and timing, each with a different interface; the dispatch task hand-wires every one into the select! loop and re-implements teardown per engine per event — a 4×4 matrix with silent holes.
Solution
One trait DepthEngine { wants(layer); observe(&depths) -> Vec<Edit>; next_deadline(); tick(now); teardown(Reason) }. Dispatch holds Vec<Box<dyn DepthEngine>> and iterates it — one deadline arm, one teardown loop, one depth fan-out.
Wins
  • locality: teardown becomes one table
  • the ClearDeepStage orphan bug (below) can't recur
  • delete wait_for_stage_deadline (byte-copy of wait_for_chord_deadline)
  • leverage: a 5th engine is one impl, not four edits
  • interface is the test surface: one fake engine, not a spawned run()
Latent bug this hole hides. Edit::ClearDeepStage (edit.rs:727–735) pushes no Effect::StopStage — only the primary cascade-delete path does. Clearing a deep stage that currently holds a live Toggle or a value=1 Hold-to-repeat orphans that firing: stage::Engine::update's "is this still a dual-stage key?" guard then skips the Input forever. A DepthEngine teardown contract routes cascade-delete through the same teardown(Reason::StageCleared(input)) every other path uses.
Does not touch ADR-0007 — that decision keeps staged-Depth interpretation in the dispatch task and out of the capture source. This organises the four engines already living in dispatch; it moves nothing across the capture seam.

2 · One StageOp interpreter inside stage::Engine

Files
daemon/src/stage.rs:610–683, 870–909, 966–978, 1119–1154
Problem
The pure core emits an ordered Vec<StageOp>; the shell walks that list in four hand-written match op { … } bodies, each with a different "legal" subset and its own debug_assert!(false) arms for the rest.
Solution
One private fn interpret(&mut self, ops: Vec<StageOp>, deps) -> Vec<Edit>. update / feed / tick / the Quick-Skip hooks call it instead of re-deciding what each op means.
Wins
  • locality: one place maps op → action
  • the "is this a dual-stage key?" predicate resolves once, not 5×
  • EngineDeps destructured once
  • shell shrinks; the deep pure core is untouched

Before — the op-walk, written four times

stage::Engine (shell, ~820 lines)

update()
match op {`{`}…{`}`} + assert
begin_quick_skip()
match op {`{`}…{`}`} + assert
end_quick_skip()
match op {`{`}…{`}`} + assert
tick()
match op {`{`}…{`}`} + assert

Same StageOp enum, four partial readers. A new op means four edits and four asserts to re-check.

After — the callers hand the list to one reader

stage::Engine

interpret(ops, deps) → Vec<Edit>
the only place StageOp is matched
update() → interpret(…)
feed() → interpret(…)
tick() → interpret(…)
quick_skip → interpret(…)

Exhaustiveness is now the compiler's job, once.

3 · Break config::validate into named invariant groups

Files
daemon/src/config.rs:1348–~1520 (banner comments at :1433, :1509)
daemon/src/config/binding.rs (the per-Binding half — already carved, ticket 14)
gui/acheron_gui/rules.py · gui/tests/test_rules_contract.py
Problem
The whole-Config half of validate is a ~170-line wall of profiles.values().find_map(…) checks appended in ticket order, with literal // --- ticket NN additions --- banners in the source. "Which check rejects X" is a linear scan.
Solution
Five pure functions — check_references, check_actuation, check_axis, check_chords, check_deep_stages — each owning one invariant group and its ConfigError variants. validate becomes five calls.
Wins
  • locality: one invariant group, one citable region
  • the GUI mirror (ADR-0005) can name what it mirrors
  • each group table-tested through its own interface
  • the next dual-stage-sized feature appends one function, not one stratum

Before — sedimentary, deposited by ticket

// --- ticket 40 chord subset/superset ---
// --- dual-stage ticket 01 additions --- (7 checks, 7 errors)

One function, ~170 lines, read top to bottom to find anything. The interface (Config → Result) is narrow, but the implementation has no internal seams.

4 · One owner for the compiled-Action step list

Files
daemon/src/executor.rs:111–154, 173, 268–302
daemon/src/trigger.rs:495–516, 675
consumed in analog_repeat.rs, stage.rs
Problem
"Compile an Action to steps" has no single owner: trigger::compile_action sometimes calls executor::compile, which unreachable!()s on 2 of 5 Action variants. The resulting Vec<MacroStep> is a semi-transparent value four modules re-inspect and pattern-match — trigger::Slots::perform compiles steps then calls executor::single_held_key to re-classify what it just built. Interface as wide as the implementation.
Solution
An action_ir module owns construction and classification: compile(action, ctx) -> CompiledAction where CompiledAction answers is_single_held_key(), is_multi_step() etc. Consumers hold the opaque type, not a raw Vec.
Wins
  • locality: one module owns the IR and its shape
  • no unreachable!() — ctx carries the stepper cursor
  • interface shrinks: ~7 step-builders stop being pub
  • classification computed once, not re-derived at each use

5 · Split the Interface-2 device-control mechanism out of capture::analog

Files
daemon/src/capture/analog.rs (1729 lines)
imported by led.rs, main.rs, supervisor.rs, dispatch.rs:38, executor.rs:25
Problem
capture::analog is two things: the Analog capture source (observe, the grid task) and the Interface-2 hidraw mechanism (Razer frame + CRC, status-LED assert/clear, device-info read, relock, read_kernel_auto_repeat). dispatch and executor import from it purely by accident of location.
Solution
A device_control module for the mechanism; capture::analog keeps only the source and calls into it like everyone else.
Wins
  • locality: the hidraw frame format lives in one place
  • imports name what they mean
  • capture::analog is only a CaptureSource again
Why speculative
Low churn, and the payoff is legibility rather than a new test surface. Worth it only when something else opens analog.rs.

6 · Close the config_to_dict encode seam

Files
daemon/src/dbus/wire.rs (~590, config_to_dict)
gui/acheron_gui/binding_editor.py · device_overview.py (~40 hardcoded key-paths)
daemon/contract/daemon-schema.json · gui/tests/test_rules_contract.py (the pattern to copy)
Problem
config_to_dict is a single-sided encode: the Daemon writes an a{sv} tree, the GUI reads it by ~40 hardcoded key-paths (config['profiles'][p]['deep_base']…), and nothing checks the two agree. A Rust key rename passes every Rust test and breaks the GUI at runtime.
Solution
A golden shape-fixture generated from config_to_dict (like daemon-schema.json), plus a GUI contract test asserting every key-path it reads exists in that fixture — the exact mechanism test_rules_contract.py already uses for the pure legality half.
Wins
  • the wire shape becomes a checked contract, not a convention
  • a Rust rename fails a test, not a user
  • reuses an accepted pattern; no new standing machinery
Weigh against ADR-0005. That ADR accepts the hand-mirrored daemon_stub.py and tells reviews to stop re-suggesting a shared edit-validation harness. This is a narrower thing — the read shape, one direction, one golden file — and ADR-0005 already blesses exactly this mechanism (rules.py + contract fixture) for the pure half. Still: if the team reads ADR-0005 as "the whole config seam is hand-audited, deliberately," this belongs in that ADR's "declined" list instead.

Before — encode with no matching decode, no check

Rust: config_to_dict(&Config) → a{sv}
GUI: config['profiles'][p]['deep_base'][input] × ~40 paths, by hand
deep_base → deep_layer in Rust → all Rust tests green → GUI KeyError at runtime

After — a golden fixture both sides answer to

Rust #[test] → config-shape.json (generated, committed)
Rust: config_to_dict stays in step
GUI: test_config_contract asserts every path
rename → the fixture changes → the GUI contract test fails in CI

Tackle first

Candidate 1 — the DepthEngine interface

It has the most corroboration and a live defect attached. Two prior architecture reviews flagged the teardown matrix and did not act; ADR-0007 records "none of these had a generic hook to reuse — each is new machinery"; and the dual-stage post-ship corrections, per ADR-0009, "clustered on the primary↔deep repeat interaction" — exactly the seam this creates. The ClearDeepStage orphan bug is currently on dev and a teardown contract closes it structurally rather than by adding a fifth special case. Start with the teardown(Reason) half alone — one enum, one loop, the 4×4 matrix collapses — before deciding whether observe and next_deadline also belong on the trait.

Low-risk warm-up if the team wants one first: Candidate 3 — pure, self-contained, and it gives the ADR-0005 GUI mirror something to name.
