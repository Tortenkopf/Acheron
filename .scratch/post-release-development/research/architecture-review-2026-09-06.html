Fold Quick-Skip routing behind stage::Engine

daemon/src/dispatch.rs · handle_event 231–321  |  daemon/src/stage.rs · Engine 420–1008

After — one entry point for a primary edge

dispatch::handle_event

stage::Engine · ~5 pub methods

Armed / Skipped / Late phase machine · handed-off tracking · deep-repeat cadence · begin_quick_skip · is_late · primary_handed_off — all now internal

exposed: on_primary_event, update, tick, next_deadline, stop_all

Problem

Dispatch re-derives a Config predicate the engine already tracks, then interprets the engine's Armed/Late/handed-off phases across ~90 lines and three inline EngineDeps builds.

Solution

One on_primary_event(deps, event) → EventDisposition. handle_event calls it for any deep-stage grid key and never learns what a phase means.

Wins

  • interface: 10 methods → ~5
  • locality: phase interpretation joins phase storage
  • Quick-Skip machine testable end-to-end, no dispatch harness
  • the EngineDeps-built-inline-×3 smell disappears
Refines ADR-0007, doesn't contradict it. The ADR places the divert in dispatch; this keeps it there but narrows the interface it diverts through — "all staged-depth interpretation lives in stage.rs" is the ADR's own stated aim.

One teardown contract for the depth engines

daemon/src/dispatch.rs · handle_layer_switch 1032 · handle_connection_change 1078 · handle_capture_mode_change 1108 · run_effects 648

Before — three engines, three shapes, divergent teardown

Disconnect——stop_all

Nothing structural says the —'s are decisions, not bugs. Each cell is a hand-threaded &mut self.engine argument through a bespoke function.

wait_for_stage_deadline() ≡ wait_for_chord_deadline() // byte copy
if !edits.is_empty() { commit_input_edits(…) } // ×4 in select!

After — Vec<dyn DepthEngine>, one loop

trait DepthEngine

wants(cfg, layer) → InputSet
observe(snapshot) → Ops
next_deadline() → Option<Instant>
on_teardown(reason)
for e in &mut self.depth_engines {
  e.on_teardown(Reason::Disconnect); }

"Which reason each engine responds to" moves into the engine — where a unit test can pin it.

Problem

A 4th depth engine needs edits at ~12–16 non-mechanical sites because the three current engines share no interface — only the rx_depth snapshot value.

Solution

A DepthEngine contract. Even adopting only the on_teardown(reason) half collapses three near-identical transition→signal→teardown functions into one.

Wins

  • locality: teardown policy per engine, not per call site
  • the disconnect-gap questions become visible in one table
  • one deadline arm, not one per engine
  • leverage: N engines, one wiring

Raised in the 2026-09-03 review (#4) and deprioritised. Dual-stage made it concrete: stage is the third engine and the first to need a second select! arm.

Latent bug this would surface: ClearDeepStage (edit.rs 711) emits no Effect::StopStage, but the primary-cascade path does — the GUI's clear_deep_stage call can orphan a live deep Toggle that Engine::update's deep_layer guard then never releases.

Split the 638-line dual-stage editor panel

gui/acheron_gui/binding_editor.py · build_dual_stage_panel 969–1607 (⅓ of the file, ~30 nested closures)

Before — four concerns in one closure scope

build_dual_stage_panel()

After — three deep modules + a thin panel

DepthTrack(n_markers)

clamp, drag, hysteresis pairing — also replaces build_actuation_section's 1-marker bar

StageDraft

capture / dirty / commit order — no GTK, unit-testable

ConfigView

(from Candidate 4)

build_dual_stage_panel()

layout + wiring only

Problem

One function holds a read-model, a state machine, a custom widget, and I/O — all as sibling closures. Nothing is reachable from a test except by building the whole panel.

Solution

Extract DepthTrack (deep widget), StageDraft (commit machine, GTK-free), and route reads through ConfigView. The panel shrinks to layout.

Wins

  • commit sequencing testable without GTK
  • locality: clamp logic in one widget, both editors
  • build_actuation_section's bar de-duplicates
  • the plain vs dual-stage fork narrows

Split config.rs model from file lifecycle

~2600 of 3339 lines (validate, ConfigError, file lifecycle, ChordKey) are touched by 2–3 call sites, yet the whole module is a dependency of a dozen.

config::model

types + Profile accessors. What the daemon actually depends on.

config::file

parse / migrate / persist. Two call sites.

config::chord_key

the hand-written codec — parallel to the config::binding carve.

Problem

No behaviour is wrong — but the module fuses five concerns and most consumers only want the type definitions.

Why speculative

Pure navigability / compile-surface gain, no seam actually varies. Do it with Candidate 2, or not yet.

Start here

Candidate 1 — fold Quick-Skip routing behind stage::Engine

Smallest change, highest locality, and it pays down debt the most recent feature just added. stage::Engine is a genuinely deep pure core wearing a 10-method interface because dispatch reaches past it to drive the Quick-Skip phases by hand. One on_primary_event entry point makes the state machine testable end-to-end and takes the interface to ~5 methods. It's also the precondition that makes Candidate 3 tractable — a depth-engine contract is far easier to fit once stage presents one entry point instead of ten.

Then Candidate 2 (mechanical, unblocks the stub mirror and a contract test) and Candidate 4 (which Candidate 5 builds on).
